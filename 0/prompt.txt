CONTEXT
======================================================================

Nexus is an autonomous engineering system built around several existing
architectural principles:

- distrust by default;
- fail closed where authority cannot be established;
- bounded authority;
- deterministic behavior where practical;
- reproducibility;
- evidence and provenance;
- external validation;
- information-flow protection;
- canonical capabilities shared across human, agent, and automation callers;
- capability availability does not imply authority;
- authorization should apply to concrete operations/resources;
- agents should not bypass validation or security controls;
- Git is a substrate rather than the definition of the agent workflow.

Do not assume the implementation perfectly satisfies these principles.

======================================================================
RESEARCH QUESTION
======================================================================

We are considering how Nexus should manage authority when agents interact
with internal and external systems.

One architectural hypothesis is:

    Agents authenticate to Nexus and receive scoped Nexus authority.

    Nexus separately maintains the credentials or workload identities needed
    to reach external/internal execution surfaces.

    Agents normally request semantic Nexus capabilities rather than receiving
    raw provider credentials.

Example:

    Agent
      |
      | Git.Push(repo=A, ref=candidate/x)
      v
    Nexus
      |
      | authority admission
      | information-flow admission
      | execution
      v
    Git provider

The Git credential would remain inside an appropriate Nexus-controlled
execution boundary.

THIS IS A HYPOTHESIS, NOT AN APPROVED ARCHITECTURE.

Challenge it.

There may be better models.

======================================================================
CORE AUTHORITY QUESTION
======================================================================

A particularly important concern is delegation hygiene.

Nexus must not grant an agent authority merely because:

    - Nexus possesses a credential capable of the operation; or
    - some backend can technically perform the operation.

Potentially distinct concepts include:

1. what a credential technically permits;

2. what Nexus is legitimately/configured to exercise;

3. what a Nexus principal is permitted to delegate;

4. what an agent has actually been granted;

5. what a particular invocation may perform.

A tentative principle is:

    possession != authority

and:

    authority != delegability

and:

    delegation must not amplify authority

For a delegation relationship:

    parent -> child

we would expect something conceptually similar to:

    child authority
        <=
    parent's delegable authority
        <=
    parent's effective authority

But do NOT accept this formulation automatically.

Determine whether it is correct and sufficient.

======================================================================
PHASE 7: ALTERNATE-PATH AUTHORITY
======================================================================

Pay particular attention to ambient execution authority.

Suppose an agent is denied:

    Git.Push

but has:

    Process.Execute

Can it invoke Git directly?

Suppose it cannot invoke Git directly but can execute:

    curl
    ssh
    python
    node
    shell scripts

Can those reproduce the prohibited external effect?

This problem generalizes beyond Git.

Determine whether the current architecture has an invariant equivalent to:

    An invocation must not exercise ambient authority exceeding its admitted
    effective authority through an alternate execution path.

If not, determine what architectural property would be needed.

Do NOT immediately prescribe containers, Bubblewrap, Landlock, seccomp,
network namespaces, or another specific mechanism.

First define the required property.

Then discuss possible enforcement strategies and tradeoffs.

PHASE 8: AUTHORITY FRESHNESS
======================================================================

Analyze:

    T0:
        Nexus legitimately possesses external write authority.

    T1:
        Agent receives bounded write authority.

    T2:
        external provider revokes Nexus write authority.

    T3:
        Agent attempts another write.

What should happen?

Determine whether Nexus needs:

- live provider verification;
- cached authority observations;
- provider event invalidation;
- bounded staleness;
- fail-closed behavior;
- different treatment for reads and writes.

Again distinguish invariant from policy.

Do not invent a fixed cache TTL without justification.
