============================================================
D3 — VERIFIER TIMEOUT / VERIFICATION CONTRACT
============================================================

Current evidence indicates:

- RustCoreBridge.executeTool defaults to approximately 35 seconds when
  timeout_secs is absent;
- the task_completed oracle invokes run_command without an explicit verifier
  timeout;
- therefore the completion verifier inherits an incidental bridge default;
- timeout and ordinary verifier failure are not clearly distinguished to the
  agent/operator.

Investigate this first.

ESTABLISH

1. Exact timeout path from:
     task completion request
       -> oracle
       -> tool bridge
       -> Rust runner
       -> process
       -> returned/refused result.

2. Every timeout participating in that path:
   - JS bridge
   - Rust runner
   - subprocess
   - gateway/RPC if applicable
   - caller-level timeout
   - any cancellation deadline.

3. Which timeout wins under each relevant combination.

4. Whether timeout is currently distinguishable from:
   - command exits non-zero;
   - command cannot start;
   - command is killed;
   - RPC transport failure;
   - cancellation;
   - verifier genuinely reports failure.

5. Whether the verifier command continues running after the caller reports
   timeout.

6. Whether descendants are cleaned up.

7. Whether partial stdout/stderr/evidence survives.

8. Whether retry is safe.

9. Whether the session remains usable.

DO NOT begin by asking "what should the timeout number be?"

First establish the behavioral contract.

DESIGN A PROPOSED CONTRACT

A verifier timeout should be a first-class, truthful state distinct from:

  VERIFIED
  VERIFICATION_FAILED
  EXECUTION_FAILED
  CANCELLED
  TRANSPORT_FAILURE

Determine whether the existing architecture already has an appropriate
reason/status representation.

Prefer reuse over inventing a parallel status system.

PROPOSE TESTS

Design deterministic tests such as controlled verifier commands with known
durations around the relevant boundary.

Do not introduce a 45-second sleep into the normal test suite if a shorter
test can exercise configurable deadlines deterministically.

Acceptance must establish:
- correct timeout owner;
- correct process cleanup;
- distinct reason;
- preserved useful evidence;
- session remains recoverable;
- no false VERIFIED;
- no false ordinary verification failure.

Do NOT implement the fix.

D4 — CONTEXT CAPACITY / ContextBudgetError
============================================================

Do not reopen context-planner research.

The previous experiment rejected routine turn-specific rebuilding/eviction
for the current architecture and evidence envelope.

This investigation concerns ERROR AND RECOVERY SEMANTICS only.

ESTABLISH

1. Exact mutation sequence around admission:
   - when the user message enters history;
   - when context admission runs;
   - when deterministic compaction runs;
   - when ContextBudgetError is thrown;
   - which state has already changed;
   - which state is rolled back, if any.

2. Resolve the important unknown:

     After ContextBudgetError, is the submitted user message left dangling in
     conversation/session history?

Prove this behavior with a minimal deterministic fixture.

3. Determine what survives:
   - objective;
   - messages;
   - plan;
   - evidence references;
   - pending tool state;
   - current turn;
   - session state.

4. Determine current recovery behavior:
   - retry;
   - /compact;
   - /clear;
   - new prompt;
   - session restart.

5. Determine whether repeated retry can create:
   - duplicate user messages;
   - duplicated state;
   - an unrecoverable loop;
   - misleading transcript state.

6. Establish why ContextBudgetError becomes UNHANDLED_ERROR.

Do not change that mapping.

DESIGN A PROPOSED CONTRACT

Treat capacity exhaustion as a known operational condition if the evidence
supports doing so.

The desired contract should answer:

- what happened;
- what was preserved;
- whether the turn executed;
- whether retry is safe;
- what recovery actions are available;
- whether operator intervention is required.

Do not prescribe context reduction as the recovery.

Recovery may simply require changing conditions or explicit user action.

PROPOSE A DETERMINISTIC REGRESSION TEST

Use a deliberately small context limit and deterministic large input/results.

Acceptance should demonstrate:
- no over-budget inference request is sent;
- reason is distinguishable from an unknown crash;
- session remains internally consistent;
- submitted message state is well-defined;
- documented recovery behaves as claimed.

Do NOT implement the fix.

and any fallback/piped behavior that reaches the legacy readline REPL.

   - rl.question installation;

D2 — `harness run -j` STDOUT TRUNCATION
============================================================

Current observation:

- large JSON output piped from `harness run -j` can truncate around 64 KB;
- index.ts writes JSON and then invokes process.exit;
- premature exit before pipe drain is a hypothesis, NOT established cause.

Establish the cause experimentally.

Use an isolated test/reproduction that does not require product modification.

Compare, as appropriate:

- stdout attached to terminal;
- stdout redirected to regular file;
- stdout piped to fast consumer;
- stdout piped to deliberately slow consumer;
- small payload;
- >64 KB payload;
- >1 MB payload.

If practical, construct a minimal Node reproduction outside product code to
test the process.exit/pending-write hypothesis.

Distinguish:

  OBSERVED IN NEXUS

from

  REPRODUCED IN MINIMAL NODE CASE

from

  ESTABLISHED NEXUS CAUSE.

Also inspect whether the sidecar's process.exit paths share the same primitive.

Do not infer that because the source contains process.exit, it is necessarily
the cause.

PROPOSE ACCEPTANCE

A future fix should demonstrate byte-exact valid JSON for a large result
through a slow pipe and preserve the intended process exit code.

Do NOT implement the fix.
