# 1. Non-negotiable architectural requirements

## 1.1 Nexus Code is provider-independent

Nexus Code is a coding client and autonomous engineering harness.

Inference providers are external dependencies, not components of Nexus Code.

The system must operate correctly with standards-compliant inference endpoints without requiring provider modifications, additional headers, custom APIs, specialized routing logic, or Nexus-specific server behavior.

Supported provider categories include:

- Local OpenAI-compatible inference servers.
- llama.cpp-compatible endpoints.
- vLLM-compatible endpoints.
- Hosted OpenAI-compatible services.
- Anthropic-compatible services through existing adapters.
- Existing supported cloud providers.
- Future inference providers implementing recognized API contracts.

Do not make homelab-ai, its gateway, hardware, or deployment topology a dependency of client functionality.

No implementation may require changes to the homelab-ai repository.

### Provider contract

Establish or preserve a transport-neutral provider abstraction.

The client may use optional capabilities discovered at runtime, including:

- Token counting.
- Context-window metadata.
- Output-token limits.
- Tool-calling support.
- Streaming.
- Structured-output support.
- Rate-limit and retry metadata.
- Queue or capacity telemetry.
- Prefix caching metadata.
- Model identity and version metadata.

Every optional capability must have a defined fallback.

Missing provider extensions must not disable ordinary delegation, orchestration, `/loop`, `/goal`, or `/batch`.

Do not infer capabilities solely from provider names or model-name patterns.

Where capability discovery is unavailable, use documented configuration, bounded conservative assumptions, and explicit uncertainty.

Never represent estimates as observed measurements.

Provider-native tool calling and text-based tool invocation must preserve equivalent tool authorization and execution semantics.

An endpoint that supports only a narrower transport contract may provide reduced optimization, but its supported functions must remain correct.

### Provider neutrality acceptance test

The complete supported workflow must execute against a minimal mock inference provider that implements only the standard wire contract required by its adapter.

Repeat against the existing local and cloud provider fixtures.

Verify that no provider-specific changes are necessary.

# 3. Unified delegation contracts

Extend the existing delegation mechanisms without creating a competing orchestration engine.

Nexus currently distinguishes between transient in-turn subagents and durable scheduled work units. Preserve this distinction while standardizing their authority and outcome semantics.

Introduce or extend a structured delegation contract containing:

```typescript
interface DelegationContract {
  id: string;
  parentId: string;
  objective: string;

  profile: string;

  inputs: Record<string, unknown>;

  authorizedScope: string[];
  permittedCapabilities: string[];

  executionMode: "transient" | "durable";

  contextBudget?: number;
  outputBudget?: number;
  executionDeadlineMs?: number;

  modelRequirements?: {
    capabilities?: string[];
    minimumContext?: number;
    qualification?: string;
    independentOf?: string[];
  };

  dependencies?: string[];

  expectedOutputSchema?: string;

  requiresVerification: boolean;
  requiresIndependentReview: boolean;
}
```

This is a conceptual contract, not a mandatory exact schema. Reconcile it with existing types and migration requirements.

## 3.1 Authority inheritance

Effective child authority must be an intersection of:

- Parent authority.
- Role/profile authority.
- Task-specific restrictions.
- Session security policy.
- Workspace and execution boundary.
- Operator approval constraints.

A child must never be able to enlarge its own authority through a model-generated contract.

The parent cannot delegate authority it does not possess.

A child cannot grant permissions to another child.

Introduce explicit recursive delegation limits covering:

- Maximum depth.
- Maximum children per parent.
- Maximum aggregate active children.
- Maximum total resource budget.
- Maximum delegated execution duration.

These limits must be independently configurable, conservatively defaulted, and enforced at admission.

## 3.2 Delegation tool interface

Upgrade `spawn_subagent` to support explicit, validated delegation metadata.

Maintain compatibility with the existing prompt-only invocation.

For prompt-only calls, apply a conservative default profile and derive no new authority from the prompt itself.

Avoid giving the model direct control over permission grants, unrestricted tool sets, or trust boundaries.

## 3.3 Structured outcomes

Every child execution must produce a typed outcome that distinguishes:

- COMPLETED.
- FAILED.
- BLOCKED.
- CANCELLED.
- INTERRUPTED.
- UNKNOWN_EFFECT.

Represent evidence, uncertainty, actual resource usage, and outstanding obligations separately.

The parent must not interpret absence of an error as proof of successful completion.

# 7. `/loop`: bounded iterative execution

## Purpose

`/loop` repeatedly evaluates or executes a task according to a defined completion condition.

It is suitable for iterative debugging, testing, evaluation, and controlled improvement.

It must not be an unrestricted infinite agent loop.

## Required interface

Support, at minimum:

```text
/loop <objective>
/loop --until <condition> <objective>
/loop --max-iterations <n> <objective>
/loop --max-duration <duration> <objective>
/loop status [id]
/loop pause [id]
/loop resume [id]
/loop stop [id]
```

Define exact flag ordering, quoting, escaping, and conflict semantics in documentation and tests.

### Required execution semantics

Each iteration must:

1. Load the durable loop state.
2. Determine the next permitted action.
3. Validate available execution and resource budgets.
4. Execute the task.
5. Collect objective evidence.
6. Evaluate the completion condition.
7. Check for lack of progress.
8. Persist the iteration outcome.
9. Continue, pause, complete, or block.

Completion conditions must support deterministic checks, such as:

- Specific test command succeeds.
- Configured verifier passes.
- Required artifact exists and passes validation.
- Explicit acceptance criteria are satisfied.
- Maximum iteration count is reached.
- Maximum duration is reached.

Natural-language conditions may be interpreted by an agent, but an agent's assertion must not substitute for required deterministic proof.

### Safety and recovery

Implement:

- Bounded iteration count.
- Bounded execution duration.
- Cancellation.
- Pause/resume.
- Stagnation detection.
- Repeated failure detection.
- Provider recovery.
- Durable state checkpoints.
- Unknown-effect reconciliation.
- Resource accounting.

Integrate with existing execution tracking and loop detection.

Do not duplicate existing repetition detectors.

### Acceptance

An interrupted loop must resume from the last trustworthy state without silently duplicating an effectful operation.

A repeated failing verifier must not execute indefinitely.

A loop must never mark itself successful solely because its maximum iteration count was reached.

# 8. `/goal`: durable objective-driven execution

## Purpose

`/goal` manages a durable engineering objective across multiple tasks, iterations, and interruptions.

It is not simply a long-running prompt.

It should reuse the existing objective ledger, operation scheduler, durable state, and acceptance system.

## Required interface

Support, at minimum:

```text
/goal <objective>
/goal status [id]
/goal list
/goal show <id>
/goal pause [id]
/goal resume [id]
/goal cancel [id]
/goal requirements [id]
/goal evidence [id]
```

The default target for omitted IDs must be unambiguous.

If multiple goals are eligible and no active goal can be resolved safely, request explicit selection rather than choosing arbitrarily.

### Required semantics

A goal contains:

- Immutable original objective.
- Requirement ledger.
- Authorized scope.
- Work-unit graph.
- Task dependencies.
- Resource requirements.
- Progress evidence.
- Verification obligations.
- Outstanding operator decisions.
- Completion status.

The system must distinguish:

- Work attempted.
- Work implemented.
- Work verified.
- Work accepted.
- Work blocked.

Do not conflate these states.

### Goal decomposition

Nexus may decompose a goal into independent work units.

The scheduler must validate dependency graphs, including cycle detection.

Independent work can run concurrently when authority, workspace isolation, and resource admission permit it.

A completed subtask does not imply completion of the parent goal.

### Goal completion

A goal is successful only when:

1. Required work units are complete.
2. Required verification gates pass.
3. Evidence is available and current.
4. Authorized scope has not been violated.
5. Required independent review is complete.
6. No blocking decisions remain.
7. The objective ledger supports a successful disposition.

Operator-approved descoping must use existing explicit authority mechanisms.

The model cannot silently reduce requirements.

### Recovery

A goal must survive process termination and restart.

Recover the dependency graph, operation state, context references, approvals, outstanding tasks, and verification obligations.

Maintain compatibility with existing durable operation records.

Do not silently reinterpret older records under different semantics.

# 9. `/batch`: controlled parallel or sequential task execution

## Purpose

`/batch` executes a declared collection of independent or dependent tasks under one bounded execution policy.

It must support both sequential and parallel execution.

A batch is not equivalent to spawning as many agents as possible.

## Required interface

Support, at minimum:

```text
/batch <spec-file>
/batch run <spec-file>
/batch validate <spec-file>
/batch status [id]
/batch list
/batch pause [id]
/batch resume [id]
/batch cancel [id]
/batch results [id]
```

The specification format must be documented and schema-validated.

Reuse the existing operation-specification format if practical.

Avoid introducing a second incompatible workflow language.

### Batch task model

Each task should support:

- Unique ID.
- Objective.
- Dependencies.
- Specialist profile.
- Authorized scope.
- Required capabilities.
- Preferred execution mode.
- Verification criteria.
- Expected output schema.
- Resource requirements.

### Required scheduling behavior

Implement:

- Dependency-aware scheduling.
- Bounded concurrency.
- Fair resource admission.
- Per-resource concurrency constraints.
- Retry and backoff.
- Failure propagation.
- Cancellation.
- Independent workspace handling.
- Aggregated results.
- Durable execution state.

The batch must not exceed safe workspace concurrency merely because inference capacity is available.

Likewise, separate worktrees do not imply that unlimited inference parallelism is beneficial.

### Workspace conflict protection

Tasks modifying overlapping files or shared execution resources must not run concurrently unless the existing isolation and merge mechanisms can safely support that operation.

Use the repository's worktree, ownership, claim, and boundary mechanisms.

Conflicting outputs must be reconciled explicitly.

Do not resolve conflicting edits with last-writer-wins semantics.

### Batch outcomes

Support explicit terminal states including:

- COMPLETE.
- PARTIAL.
- BLOCKED.
- CANCELLED.
- FAILED.

A batch with one successful task and one blocked required task must not report COMPLETE.

Preserve individual task receipts.

### Optional execution modes

Support or provide a clearly scoped design for:

- Fail-fast.
- Continue-independent.
- Sequential.
- Dependency-parallel.

Defaults must be documented and tested.

# 11. Resource-aware scheduling without provider coupling

Extend the existing resource registry and convergence scheduler.

Do not build a second scheduler.

Distinguish:

1. Number of active agents.
2. Number of admitted inference requests.
3. Number of available inference resources.
4. Number of effectful workspace operations.
5. Available context capacity.
6. Provider rate or concurrency limits.

Concurrency must be governed by available evidence and configured limits.

Do not assume a fixed relationship between GPU count and inference concurrency.

### Admission policy

Consider:

- Provider eligibility.
- Advertised or configured concurrency limits.
- Observed rate limiting.
- Available model context.
- Required capabilities.
- Model qualification.
- Active operation dependencies.
- Workspace exclusivity.
- Configured cost and execution budgets.

Provider-specific queue, cache, and device metrics may improve decisions if available.

They are optional inputs, not prerequisites.

Without reliable capacity telemetry, operate conservatively using client-observed latency, failures, explicit configured limits, and bounded adaptive admission.

A provider's lack of token-counting support must not produce fabricated exact usage.

### Adaptive scheduling

Investigate whether adaptive concurrency improves task throughput.

If implemented, make it bounded, reversible, and backed by measurable signals.

Measure both throughput and correctness.

Do not maximize requests per second at the expense of successful engineering outcomes.

# 12. Recovery and lifecycle correctness

Audit and reconcile the transient and durable execution paths.

Introduce consistent semantics for:

- Cancellation requested.
- Cancellation acknowledged.
- Interrupted execution.
- Process termination.
- Provider timeout.
- Unknown side-effect outcome.
- Work-unit retry.
- Parent termination.
- Child completion after parent cancellation.
- State persistence failure.
- Restart and recovery.

A cancelled request is not proof that its effect was cancelled.

Where an action may have executed before interruption, record UNKNOWN_EFFECT until reconciliation determines whether it is safe to retry.

Prevent stale child outcomes from completing a cancelled or superseded parent.

Use durable execution identities, idempotency markers, or reconciliation procedures where appropriate.

Do not pretend that arbitrary shell commands are intrinsically idempotent.

Avoid replaying irreversible actions without sufficient evidence or explicit operator authorization.

Preserve the original objective and acceptance ledger across recovery.
