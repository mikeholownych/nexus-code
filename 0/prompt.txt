# Nexus v1.1.2: Non-Progress Recovery and Execution-State Continuity

You are operating inside the Nexus Code repository as a senior principal engineer responsible for agent orchestration, execution reliability, recovery mechanisms, and regression prevention.

Your assignment is to investigate, design, implement, test, and independently validate improvements to Nexus's non-progress detection and recovery behavior.

**This is an implementation assignment, not a documentation-only exercise.**

## 1. Incident Context

During a live Nexus dogfooding session, the engineering agent repeatedly inspected repository files despite having already acquired the relevant information.

Observed behavior:

- The agent inspected `cli/src/doctor.ts` and `cli/test/doctor.test.ts`.
- The agent explicitly recognized that it needed to stop re-reading files.
- Subsequent reasoning repeatedly regenerated nearly identical plans.
- Equivalent file reads continued without meaningful progress.
- Nexus detected repeated `read_file` observations with unchanged results.
- Two recovery instructions failed to produce a materially different approach.
- The workspace remained unchanged.
- Nexus eventually stopped execution with `too many steps without progress`.

Representative evidence:

```text
The agent repeated read_file with an unchanged result:
Nexus told it to change approach (2 of 2).

Stopped at too many steps without progress

repeated read_file 3 times with an unchanged result
on an unchanged workspace after 2 recovery notes
```

Initial assessment:

- Non-progress detection: functioning for this scenario.
- Bounded termination: functioning.
- Recovery instruction effectiveness: insufficient.
- Execution-state continuity: potentially defective.
- Semantic equivalence detection: potentially incomplete.
- Recovery escalation: insufficiently enforced.

These are hypotheses, not established root causes. Verify them against the implementation and available session evidence.

## 2. Primary Objective

Improve Nexus so that detecting non-progress leads to a constrained, evidence-driven change in execution strategy rather than repeated advisory instructions.

Nexus must distinguish among:

1. New information acquired.
2. A meaningful change in the agent's working hypothesis.
3. A productive execution action.
4. Repeated observation of existing information.
5. Repeated planning without state advancement.
6. Legitimate, intentional reinspection following a material state change.

**Success means improved task completion and recovery effectiveness, not merely fewer tool calls.**

Do not weaken existing loop detection or termination safeguards to make the agent appear more successful.

## 3. Repository and Baseline Discovery

Before implementation:

1. Inspect the current repository state and branch.
2. Identify existing uncommitted, staged, and untracked changes.
3. Identify the current v1.1.2 roadmap and Continuous Evaluation and Regression Intelligence workstream.
4. Locate the orchestration loop, tool execution pipeline, progress detection, recovery instructions, context management, session persistence, and termination logic.
5. Identify existing tests and regression fixtures covering non-progress, duplicate observations, and recovery.

Preserve all pre-existing changes.

Do not reset, discard, overwrite, or commit unrelated work.

Avoid repeatedly reading entire large files. Prefer targeted searches, symbol-level inspection, and bounded file ranges.

Record the baseline before modifying behavior.

## 4. Required Engineering Work

### 4.1 Semantic Observation Identity

Investigate how Nexus determines that a tool observation has already been seen.

Design and implement semantic equivalence detection sufficient to recognize materially redundant observations across tool invocation variants.

Examples:

```text
read_file cli/src/doctor.ts
cat cli/src/doctor.ts
sed -n '1,500p' cli/src/doctor.ts
head -500 cli/src/doctor.ts
```

These may provide equivalent observations even though the tool names and arguments differ.

Requirements:

- Normalize resource identities and file paths.
- Account for inspected content ranges.
- Track content fingerprints where practical.
- Distinguish exact duplication from substantial overlap.
- Account for workspace revisions and content changes.
- Avoid treating legitimate rereads after file modifications as duplicates.
- Avoid broad semantic similarity rules that incorrectly classify different evidence as identical.
- Keep fingerprint and observation metadata bounded.
- Do not retain redundant raw file contents unnecessarily.

Investigate existing infrastructure before introducing new abstractions.

### 4.2 Structured Recovery Escalation

Replace repeated advisory-only recovery with a bounded escalation mechanism.

Target conceptual states:

```text
NORMAL
  |
  v
NON_PROGRESS_DETECTED
  |
  v
RECOVERY_ADVISORY
  |
  v
RECOVERY_CONSTRAINED
  |
  +--> PRODUCTIVE_PROGRESS --> NORMAL
  |
  +--> NO_VIABLE_ALTERNATIVE --> TERMINATED
  |
  +--> RECOVERY_EXHAUSTED --> TERMINATED
```

Adapt state names and implementation to the existing architecture.

Requirements:

- First occurrence may produce an advisory.
- Repeated equivalent observations must trigger enforceable constraints.
- Nexus must reject equivalent unproductive observations during constrained recovery.
- Tool denial must be deterministic and explainable.
- Denied tool calls must not execute.
- Denial alone must not count as productive progress.
- Denied calls must not reset stagnation counters.
- Recovery must remain bounded.
- Existing step, token, time, and tool budgets must remain enforceable.
- Do not introduce an unbounded loop of rejected actions.

### 4.3 Recovery Context Contract

When entering constrained recovery, provide the agent with compact, structured context containing:

```text
RECOVERY_REQUIRED

Current objective:
[Known task objective]

Previously acquired evidence:
[Relevant observations already available]

Repeated observations:
[Resources, ranges, and fingerprints]

Current workspace state:
[Known revision or change marker]

Last meaningful progress:
[Evidence-backed progress event]

Unresolved question:
[Specific remaining information requirement, if known]

Disallowed operations:
[Equivalent observations already proven unproductive]

Permitted next actions:
[Alternative evidence acquisition or execution paths]

Recovery budget:
[Remaining attempts and applicable limits]
```

Do not fabricate an unresolved question or infer progress from the model's own claims.

If the unresolved question is not known, require the agent to identify it.

Reuse existing session context and evidence mechanisms where possible.

### 4.4 Execution-State Continuity

Investigate whether the agent is repeatedly reconstructing the same plan because relevant execution state is lost, compacted, omitted, or not incorporated into subsequent turns.

Implement the minimum necessary improvements to preserve:

- Current objective.
- Completed investigative steps.
- Evidence already acquired.
- Open questions.
- Active execution hypothesis.
- Last meaningful progress.
- Recovery state.
- Explicitly disallowed repetitive operations.

Do not create an entirely new planning subsystem unless existing architecture demonstrably cannot support the requirement.

Context compaction and session resume must preserve recovery-critical state.

The agent must not be able to escape recovery constraints merely by triggering compaction, resuming a session, or switching between equivalent tool interfaces.

### 4.5 Progress Classification

Introduce or improve progress classification so Nexus does not equate tool execution with useful work.

At minimum, distinguish:

```text
OBSERVATION_NEW
OBSERVATION_DUPLICATE
OBSERVATION_OVERLAPPING
HYPOTHESIS_UPDATED
ARTIFACT_MODIFIED
VALIDATION_EXECUTED
VALIDATION_PASSED
VALIDATION_FAILED
RECOVERY_ACTION
RECOVERY_DENIED
NO_PROGRESS
```

These are conceptual categories. Reuse established event types where appropriate.

Important constraints:

- A model statement claiming new understanding is not independently sufficient evidence of progress.
- A changed command string is not necessarily a new observation.
- A failed validation may constitute useful progress when it produces new diagnostic evidence.
- A file modification is not automatically productive if it is unrelated or repeatedly reverted.
- Legitimate read-only tasks must be able to complete without workspace changes.
- Repeated reads may be legitimate when the underlying artifact or relevant assumptions change.

Do not build an arbitrary scoring system unless deterministic rules cannot meet the requirements.

### 4.6 Recovery-Aware Tool Enforcement

Place enforcement at the appropriate execution boundary.

Constraints must apply before the tool action executes, regardless of how the model phrases the intended operation.

Investigate bypass paths involving:

- Native file-reading tools.
- Shell commands.
- Equivalent command substitutions.
- Tool aliases.
- Batched tool calls.
- Session resume.
- Context compaction.
- Worker/model changes.

**Do not claim universal semantic equivalence across arbitrary shell commands unless it is genuinely implemented and independently tested.**

For operations that cannot be reliably classified before execution, explicitly document the enforcement boundary and implement conservative handling that preserves legitimate work.

Do not silently claim complete mediation where only partial interception exists.

## New finding (Medium): identical writes bypass recovery

**Location:** `cli/src/agent.ts:5558`, used at `cli/src/agent.ts:5644` and `cli/src/agent.ts:5674`.

**Cause:**
