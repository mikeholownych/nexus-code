DESIGN REQUIREMENT 1
ORTHOGONAL OUTCOME SEMANTICS

Do NOT solve the problem with one increasingly large enum that conflates execution,
engineering outcome, verification, and acceptance.

The implementation must distinguish at least these dimensions conceptually:

EXECUTION STATE

Examples:

  COMPLETED
  INTERRUPTED
  FAILED
  BLOCKED
  LIMIT_REACHED

ENGINEERING / VERIFICATION OUTCOME

Examples:

  VERIFIED
  UNVERIFIED
  NOT_ESTABLISHED

OPERATOR ACCEPTANCE

Examples:

  ACCEPTED
  NOT_ACCEPTED
  NOT_REQUESTED

These names are candidate vocabulary, not immutable API requirements.

Inspect the existing domain model before choosing exact names.

The important invariant is orthogonality.

For example, Nexus must be capable of representing:

  execution: COMPLETED
  outcome: UNVERIFIED
  acceptance: NOT_REQUESTED

without calling that failure and without falsely calling the engineering result
verified.

Likewise:

  execution: BLOCKED
  outcome: NOT_ESTABLISHED
  reason: REPOSITORY_STATE_CHANGED

must be representable without pretending the task succeeded or necessarily
terminating all possible investigation.

And:

  execution: INTERRUPTED
  outcome: NOT_ESTABLISHED

must not become TASK COMPLETED.

Do not prematurely design every future state.

Implement only what this slice requires while preserving room for later states.

STRUCTURED TURN RESULT

`runTurn` must no longer communicate its semantic result merely by:

- returning void
- throwing/not throwing
- printing text
- whether the model stopped calling tools

Introduce a structured result sufficient for callers to know:

- execution state
- engineering/verification outcome
- reason where applicable
- whether final model output is complete
- verification evidence/status where applicable
- interruption state
- step-limit state
- inference failure state

Thread the authoritative semantics through the relevant existing callers.

At minimum:

  AutonomousAgent
  ApplicationCore.runTask
  harness run output
  REPL end-of-turn reporting
  session/durable state where applicable

Do not create independent competing interpretations at each UI surface.

One semantic result should project outward.

EXIT SEMANTICS

Define process exit behavior deliberately.

At minimum:

- inference failure must not exit 0 as successful work
- step-limit exhaustion must not masquerade as verified completion
- interruption must not masquerade as completion
- verified completion can report success
- completed-but-unverified must be represented honestly

Do not invent Unix exit-code complexity beyond what is useful.

Document the chosen contract and test it.

MODEL TEXT IS NOT COMPLETION PROOF

A model returning prose without tool calls means the model stopped producing tool
actions.

It does NOT inherently mean:

- requested work succeeded
- validation passed
- engineering outcome was demonstrated
- operator accepted the result

Represent that distinction.

Do not print `TASK COMPLETED` merely because the model emitted final text if Nexus
does not possess evidence supporting that statement.

DESIGN REQUIREMENT 2
RELIABLE CANCELLATION

Introduce one cancellation authority for each active turn.

Prefer an AbortController/AbortSignal or an equivalent mechanism appropriate to the
existing architecture.

Cancellation must propagate far enough to prevent Nexus from continuing to admit
new work after the operator interrupts the turn.

At minimum:

- first Ctrl-C while a turn is running requests cancellation
- Nexus immediately marks the turn as cancellation-requested/interrupted
- no NEW tool dispatch may begin after cancellation is observed
- inference request is aborted where supported
- tool execution receives/checks cancellation where safely possible
- the agent loop checks cancellation between operations
- the REPL returns to a usable prompt after bounded cleanup
- partial work is represented honestly
- session/evidence records the interruption

Ctrl-C while idle should retain deliberate exit behavior.

Do not promise instantaneous termination of an already-executing external effect if
the underlying operation cannot safely be interrupted.

Instead distinguish:

  cancellation requested
  no further work admitted
  outstanding operation settling/terminated
  turn interrupted

The operator's stop request is an authority event, not merely a UI keystroke.

REGRESSION PROOF

The prior slow-loop scenario must become a regression test.

After the first interrupt is accepted, demonstrate that no additional tool mutation
is dispatched.

Do not weaken this by merely hiding subsequent output.

DESIGN REQUIREMENT 3
STREAM INTEGRITY

A partially received model response must not be treated as a complete model answer.

Inspect the actual protocol used by the current gateway/client.

Define the minimum positive completion evidence supported by that protocol, such as:

- terminal finish_reason
- [DONE]
- another explicit protocol completion condition

Do not assume a specific marker without checking current protocol behavior and
existing fixtures.

Handle distinctly:

- clean completed stream
- connection/read failure before completion
- provider error frame
- timeout
- malformed event
- intentionally aborted request

Preserve partial text for diagnosis if useful, but do not promote partial text to a
complete answer.

If performing a bounded retry:

- define when retry is permitted
- preserve correlation/provenance
- avoid duplicate unsafe tool effects
- do not retry client-originated semantic/protocol errors as though another endpoint
  will necessarily fix them

If the existing fallback path issues a new request with a new correlation identity,
correct that behavior where required by this slice.

Do not broaden this into generalized provider failover redesign.

DESIGN REQUIREMENT 4
VERIFIER-BACKED COMPLETION

Remove command-text heuristics as evidence that validation occurred.

This behavior is specifically unacceptable:

  run_command "echo checking tests"

must not clear the verification obligation merely because the command contains the
word "test" or "check".

A verification obligation may be cleared only by evidence tied to the actual
verifier selected/discovered/configured for the task and a successful result from
that verifier.

Determine the smallest architecture-compatible mechanism for associating:

  candidate/change
    →
  required verifier
    →
  verifier invocation
    →
  result
    →
  verification evidence

Reuse existing receipts/candidate/validation mechanisms where appropriate rather
than creating an unrelated validation subsystem.

NO-VERIFIER STATE

A repository with no applicable verifier is not automatically:

- verified
- failed
- permanently dead

Represent it honestly as an unverified engineering outcome with an explicit reason.

Do not guess `npm test` merely because no better verifier exists unless that behavior
is explicitly justified by repository evidence.

The model may continue safe investigation if useful and authorized.

Eventually returning:

  execution: COMPLETED
  outcome: UNVERIFIED
  reason: NO_APPLICABLE_VERIFIER

or equivalent is valid.

TEST STRATEGY

At minimum prove:

   → inference failure represented structurally
   → process does not claim successful completion
   → exit semantics reflect failure

2. Truncated stream
   → partial text not accepted as complete
   → structured inference failure

3. Mid-stream provider error
   → not silently ignored
   → structured inference failure

4. Step-limit loop
   → LIMIT_REACHED or equivalent
   → not verified completion

5. Model gives up
   → model stopping is distinguishable from verified completion

6. False verifier:
     write_file
       →
     run_command "echo checking tests"
       →
     task_completed

   → completion gate remains unsatisfied

7. No applicable verifier
   → honest UNVERIFIED result
   → no fabricated verifier success
   → no false TASK COMPLETED

8. Ctrl-C during delayed mutating trajectory
   → one interrupt requests cancellation
   → no new mutation dispatched afterward
   → turn records INTERRUPTED
   → REPL returns to usable prompt

9. Existing positive multi-prompt REPL behavior remains functional.

10. Clean complete stream remains accepted normally.

Also run existing relevant unit/integration tests.
