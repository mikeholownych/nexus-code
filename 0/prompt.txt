## Generator approach
- **How it works:** it opens `cli/tsconfig.json` through `typescript/unstable/sync`, resolves `SidecarEvent`, `SidecarCommand` and `PROTOCOL_VERSION` in `src/protocol.ts`, and walks the checker's types. Nothing is hand-written or regex-parsed.

- **Descriptions:** JSDoc on types and properties is carried into `description`.
- **Determinism:** definitions, properties, `required`, enum values and variants are all sorted. Two consecutive runs gave the same sha256 (`b2747ba8…b66a`), and the file contains no absolute paths.
- **Unsupported types:** a function, a TS enum, or a tuple with optional or rest elements stops the generator with an error naming the property.
- **`--check`:** exits 1 naming the file when the schema is stale, and also when the ledger is stale.

API calls it depends on:
- `API({cwd})`, `updateSnapshot({openProjects})`, `Snapshot.getProjects`, `Project.checker`

## Parity design

- **Samples:** the generator reads the checked-in schema and writes a minimal and a full sample per message. It adds one extra full sample per alternative where a field is a union of shapes, so every `ApprovalReview` kind is covered. `--check` and a TypeScript test fail on drift, and every sample validates against the schema.
- **Events, TS to Rust:** `schema_samples_parse_as_their_own_event_variants` parses every event sample with `parse_event` and rejects `Event::Unknown` and `Review::Unknown`.
- **Event type sets:** the Rust event names must equal the schema's, with no allowlist needed. The Rust names are read from the `#[serde(rename)]` attributes via `include_str!`, because Rust cannot list enum variants; the test asserts every variant carries a rename.
- **Event fields:** top-level field names are taken from the derived `{:#?}` output. Rust may read no field the schema lacks, and the schema fields Rust does not read must equal `EVENT_FIELDS_NOT_READ` exactly (11 events, mostly `turn_id`). This is what makes a new optional TS field fail on the Rust side. It checks top-level fields only; nested structs are covered by parsing, not by field accounting.
- **Commands, Rust to TS:** I took the checked-in fixture route. `rust_commands_are_the_checked_in_fixture_and_published_commands` asserts the fixture is byte-for-byte what `encode_command` produces for one representative of every variant (`provider.connect` with and without its optional fields). `protocol_parity.test.ts` validates each line against the schema and requires `parseCommand(line)` to equal the line minus `v`, which also catches a renamed optional field.
- **Command sets:** the representatives must equal the scanned `Command` variants, which must be a subset of the schema's commands; the remainder must equal `COMMANDS_NOT_SENT = ["answer"]`.
- **Why this route:** no stdout plumbing between test runners, no new dependency, and each language's own test fails with a precise message. The cost is two test-only introspection tricks (source scan and Debug-format parsing). The alternative was `cfg_attr(test, derive(Serialize))` on production types, which is outside the allowed edit area.

## Input contract

- **`--input-json &lt;file|-&gt;`:** reads `{ "schema_version": 1, "task": "&lt;text&gt;" }`. It must be a JSON object, `schema_version` exactly 1, `task` a non-empty string (trimmed).
- **Authority:** only `task` is read. I mapped no other member onto options.
- **Plain stdin:** read as the task only when there is no argument, no `--input-json`, no `--resume` or `--fork-session`, and stdin is not a terminal.
- **Bounds:** 1,048,576 bytes and valid UTF-8; larger input is rejected, not truncated.
- **Usage errors (exit 2):** argument plus `--input-json`, an invalid document, an unreadable file, or empty stdin. The message goes to stderr and stdout stays empty.
- **With `--resume`:** `--input-json` is allowed and supplies the prompt, as an argument does today.

## 3. CLI contract

```
nexus verify [--worktree &lt;path&gt; | -w &lt;path&gt;] [--base &lt;ref&gt;] [--head &lt;ref&gt;]
             [--verifier &lt;cmd&gt;] [--deliverable-file &lt;path&gt;]... [-y|--yes | --approve-verifier &lt;sha256&gt;]
             [--approve-verification-edit &lt;path&gt;]... [--review] [--objective &lt;text&gt;|--objective-file &lt;f&gt;]
             [--timeout-secs &lt;n&gt;] [--receipt &lt;file&gt;] [-j|--json]
```

- **Modes.** `--worktree` alone verifies the working tree against `HEAD`, or against `--base`. `--base` with `--head` verifies two commits. In both cases both trees are materialised into scratch directories so the caller's checkout is never written.
- **Why scratch directories.** `prepareBaselineTestsCopy` writes under `&lt;workspace&gt;/.nexus/verify/` (`independent_check.ts:785`). Run it on the scratch head, not the user's tree.
- **Verifier selection.** `--verifier` gives source `configured`. Otherwise discover from the base tree, never the head. A discovered verifier needs `-y` or `--approve-verifier &lt;digest&gt;` (the `describeVerifier` digest); otherwise the verdict is BLOCKED with the command and digest printed. This mirrors headless review mode (`spine_handlers.ts:201-203`).
- **Reviewer.** Off by default. `--review` requires a configured model and an objective; with no model the verdict is BLOCKED (`review_unavailable`). Without `--review` the receipt records `review: NOT_RUN`.

**Verdict rules** (computed outcome, then mapped; the reviewer and guard can only lower):

| Verdict | When | Exit |
|---|---|---|
| VERIFIED | Outcome `VERIFIED`: passed, tests executed, definition bound, deliverable-bound, and configured or independent. No unapproved guard finding. With `--review`, the reviewer said ACCEPT. | 0 `ok` |
| REGRESSION_FREE | Outcome `REGRESSION_FREE` | 2 `unverified` |
| UNVERIFIED | No applicable verifier, zero tests executed, or an empty diff (`NOTHING_TO_VERIFY`) | 2 `unverified` |
| UNVERIFIED | Outcome `NOT_ESTABLISHED`: verifier or enforced type-check failed or timed out; or the reviewer said REJECT | 1 `failed` |
| BLOCKED | Verifier not approved; an unapproved verification-config edit or detected weakening under mode `approve` or `block`; an untrusted checkout (`trustedGitArgs` throws); `--review` without a model; incomplete scan bounds | 3 `blocked` (new) |
| usage or bad ref | | 2 `usage` |
| SIGINT | | 130 |

- An empty diff is not 0. `run` gives `NOT_REQUIRED` → 0, but here the caller chooses the base.

## 4. Security analysis for G-3

**Trust model to document.** The process launcher (argv and env) is the operator. The repository content, especially the head, is untrusted. VR-1 cannot defend against a hostile launcher; it can make every verdict-affecting input visible in the receipt. So structure the core as `verifyChange(request, operatorContext)`, with the request limited to worktree, base and head, so VR-2 can expose only the request.

| Attack | Existing protection | VR-1 must add |
|---|---|---|
| Head redefines the verifier (`package.json` test script, Makefile, conftest) | `snapshotVerifierDefinition` and `verifierDefinitionChangedSince` (`independent_check.ts:183, 601`); the agent refuses at `spine_handlers.ts:140-168` | Discover and bind from base; a definition change is never VERIFIED and is a guard finding |
| `--verifier 'echo ok'` or fabricated output | `hasExecutedTests` (zero tests → UNVERIFIED); deliverable binding by imports in pre-existing tests, not by output text (`tester.ts:1785-1790`); inline programs are unbindable (`independent_check.ts:106`) | Record the verifier source and digest in the receipt. Residual risk: a launcher-supplied script that prints a fake runner summary |
| Weakened, skipped or deleted test | The independence rule (section 1) | Run base tests against head code; add an explicit weakening finding (section 5) |
| Repository policy relaxes the guard | `off`, `record` and `allow` are honoured only when trusted (`security.ts:229`) | Load policy from the base scratch directory; record `NEXUS_TRUST_WORKSPACE` |
| Env: `NEXUS_TYPECHECK=off`, timeout, passthrough, `PATH` | Verifier env scrub; `toolSha256` (`tester.ts:174`) | Record the names that were set; with `--strict-env`, refuse `NEXUS_TYPECHECK=off` (decision) |
| Base chosen so the diff is empty, or base equals head | None | `NOTHING_TO_VERIFY`, exit 2; the receipt binds base and head commits and trees; the action takes base from the event |
| Symlinks or a planted `.git` | `trustedGitArgs` (`git.ts:40`); symlink refusal in snapshots (`independent_check.ts:204`) and in `isSafeWorkspaceFile` (`tester.ts:990`) | Materialise without following links that leave the tree |

## 7. Risks and open decisions

1. **Base environment parity.** A bare base checkout has no installed dependencies, so the base run fails for environmental reasons and fakes a fail-before. Default: materialise base as a copy of the head worktree with tracked files replaced by base content and dependency directories symlinked (the pattern at `independent_check.ts:787-830`). 2. **Verifier failure.** Verdict UNVERIFIED, but which exit code? Default: 1, matching `run`'s `NOT_ESTABLISHED`.
3. **What BLOCKED covers.** Default: approval needed, unapproved config edit or weakening, untrusted checkout, reviewer unavailable. A plain modification of an existing test is recorded only; the independence rule already caps it.
4. **Weakening heuristic.** It is regex-based and will misfire. Default: findings always appear in the receipt, and `--approve-verification-edit &lt;path&gt;` clears BLOCKED but never restores VERIFIED.
5. **Discovered verifier without `-y`.** Default: BLOCKED with the digest, as in `run`.

## Materialisation, bounds, cleanup
- **Scratch root:** a realpath'd `mkdtemp` under the temp directory, holding `base/`, `head/`, `head-pristine/`, scratch index files and a scratch object directory.
- **Commit side:** `read-tree` into a scratch index, then `checkout-index --prefix`.
- **Working tree side:** `git add -A` (excluding `.nexus`) into the scratch index, with objects written to the scratch object directory and the repository's own as an alternate, then `write-tree`. The resulting tree id is what is materialised and recorded. In the test the caller's checkout, `.git` included, hashes identically before and after.
- **Bounds:** 20,000 files and 512 MiB per tree, checked before anything is written. Git calls time out at 30 s or 120 s, and each verifier run at `verifierTimeoutSecs` (at most three runs). A breach or a submodule is BLOCKED.
- **Cleanup:** a `finally` in `verifyChange` plus a process `exit` hook.
- **Interrupt latency:** `runVerifierShell` is synchronous and `timeout` puts the verifier in its own process group, so an interrupt is acted on only when the running verifier ends. Fixing that needs an async runner in `tester.ts`.

## Receipt
`--json` and `--receipt &lt;file&gt;` write the same document, `schema_version` first. It contains:
- `verdict`, `outcome`, `reason`, `detail`, `exitCode`
- `base` and `head` (`ref`, `commit`, `tree`, `workingTree`), `changedFiles`, `changedFileCount`
- `verifier` (`command`, `source`, `evidence`, `digest`, `approval`, `script`) and `deliverables`
- `runs`, one entry per verifier process with phase, pass/fail, exit code, whether tests ran, output sha256 and a redacted tail for a failed run
- `baseline` and `verification` (the evidence the outcome was derived from)
- `typecheck`, `guard`, `review`, each `{status: "NOT_RUN", detail}`
- `linkedDependencyDirs`, `limits`, `environment` (names only), `nexusVersion`, `startedAt`, `durationMs`

A usage error or an interrupt prints an error document: `{schema_version, error, exitCode}`.

## Guard trust
- The policy comes from `new SecurityManager(&lt;base scratch dir&gt;)` and is always treated as untrusted. A base policy can tighten (`mode: "block"`, `extra`) and never relax (`off`, `record`, `allow` are ignored).
- The head's `.nexus-security.json` is never read as policy; it is a `policy` finding.
- `NEXUS_TRUST_WORKSPACE` is not honoured. It is deleted from `process.env` for the duration of the `SecurityManager` constructor and then restored, and its name is recorded in `environment`. This is a workaround for the constructor having no trust parameter; please review it.
- Under base mode `block`, `--approve-verification-edit` does not clear BLOCKED.
- Modes `off` and `record` are unreachable, since the policy is never trusted.
- A new test file is free, matching `security.ts` `verificationEditDecision` (`if (!exists &amp;&amp; found.class === "test_file") return null`).
- Weakening kinds: `removed`, `skipped`, `fewer-assertions`, `neutered` (from `NEUTERING_TEXT` over added lines), `unverifiable-change`. A renamed test file reads as deleted plus added, so it blocks.
- `guard.complete` is false for an unreadable or over-256 KiB file, or more than 1000 findings.

## 2. Bundle format

**A directory, not an archive.** Node's standard library has `zlib` but no tar or zip writer. The repo only validates tar (`cli/src/tar_safety.ts:105`) and extracts with the system binary (`:377-383`). The release archive is built by shell `tar` (`scripts/package-linux.sh:228-230`) beside a `MANIFEST.sha256` (`:212`), and upgrade backups are directory copies (`cli/src/upgrade.ts:1102-1118`). A directory needs no dependency, and one `tar` afterwards gives a single file that verifies after extraction.

```
&lt;out&gt;/
  manifest.json
  manifest.sig.json            only when signed
  session/export.json, export.md
  receipts/validation-receipts.json, last-turn.json, verify-&lt;n&gt;.json
  verification/attempts.json, config-attempts.jsonl
  evidence/provenance.json, findings.json, diffs/&lt;name&gt;.diff
  flights/&lt;flightId&gt;.flightlog
  traces/trace.jsonl           opt-in
```

**Manifest** (`AuditManifest`, snake_case as in the brief):

- `schema_version: 1`, `format: "nexus-audit-bundle/1"`, `bundle_id` (32 random hex), `created_at`.
- `nexus: { version, commit, dirty }` from `getBuildIdentity()` (`cli/src/build_identity.ts:24-45`).
- `subject: { kind, task_id, session_id, store, workspace_path, workspace_sha256, status, updated_at, at_rest }`.
- `redaction: "standard" | "strict"`.
- `files[]: { path, bytes, sha256, role, chain }`, sorted by `path`, each linked to the previous with `linkRecord`. This is the unit's "hash chain".
- `files_head: { seq, hash }`.
- `chained_logs[]: { path, kind, records, status, head?, closed?, source?, selection? }`, where `source` is `{ records, head?, closed, bytes, sha256, complete }`.
- `omitted[]: { artefact, reason }`.
- `root_sha256`.

**What is hashed.**
- File `sha256`: the file's raw bytes.
- File-entry link: `linkRecord`'s definition (`cli/src/core/hash_chain.ts:19,44-58`).
- `root_sha256`: SHA-256 of `canonicalJson(manifest without root_sha256)` in UTF-8.
- `manifest.json` on disk: exactly `canonicalJson(manifest) + "\n"`. Verify rejects any other byte form, so the reported `manifest_sha256` (SHA-256 of those bytes) is well defined. Both commands print it; it is the value to record elsewhere.

**Signature**, detached, in `manifest.sig.json`: `{ schema_version: 1, algorithm: "ed25519", signed_file: "manifest.json", manifest_sha256, public_key_sha256, signature }`.
- Signed bytes: `"nexus-audit-bundle-signature/1\n"` followed by the exact bytes of `manifest.json`. The prefix stops the operator's key being used to sign something else.
- `public_key_sha256` is the SHA-256 of the key's SPKI DER.
- The public key is not stored in the bundle. The verifier gets it only from `--public-key &lt;file&gt;`; the envelope's fingerprint is a hint for the error message and is never trusted.

**Published contract (PF-2 pattern).**

## 3. CLI contract

```
nexus audit export &lt;id&gt; [--store tasks|sessions] [--out &lt;dir&gt;] [--sign-key &lt;file&gt;]
      [--flight &lt;id&gt;]... [--receipt-file &lt;file&gt;]... [--include traces]
      [--redact standard|strict] [-w &lt;workspace&gt;] [--json]
nexus audit verify &lt;bundle-dir&gt; [--public-key &lt;file&gt;] [--expect-manifest-sha256 &lt;hex&gt;] [--json]
```

- `&lt;id&gt;` must be exact and pass the persistence-name pattern before any path is built. An id found in both stores needs `--store`.
- `--out` defaults to `./nexus-audit-&lt;id&gt;-&lt;UTC stamp&gt;` and must not exist.
- `-w` overrides the workspace used to locate flights (default: the subject's recorded workspace).

`AUDIT_EXIT_CODES`, same row shape as `RUN_EXIT_CODES` and `VERIFY_EXIT_CODES`, mirrored in the manual by a table test like `cli/test/verify_command.test.ts:42-58`:

| Code | Name | When |
|---|---|---|
| 0 | `exported` | The bundle was written. |
| 0 | `intact_signed` | Every file matches and the signature is valid for the key given. |
| 0 | `intact_unsigned` | Every file matches; there is no signature. |
| 1 | `tampered` | Any integrity failure: file altered, missing, extra or unsafe; manifest malformed or inconsistent; a chained log that does not match its recorded head; signature invalid; or a key was given and the signature is absent. |
| 1 | `error` | The command itself failed. |
| 1 | `option_parse` | The command line could not be parsed. |
| 2 | `signature_unchecked` | Files match and a signature is present, but no `--public-key` was given. |
| 2 | `unsupported_version` | The bundle's `schema_version` is newer than this build reads. Nothing was checked. |
| 2 | `usage` | Invalid option or combination, unusable key file, `--out` exists, or the path is not a bundle directory. |
| 2 | `subject_not_found` | No saved task or session has that exact id. |
| 130 | `interrupted` | SIGINT or SIGTERM. |

Verify wording, one stable `finding.kind` per class. Text goes to stdout; `--json` prints only the document.

| Class | Text |
|---|---|
| Intact and signed | `INTACT, SIGNED: all N files match the manifest, and the manifest is signed by the key you supplied (sha256 &lt;fp&gt;).` |
| Hash only | `INTACT BY HASH ONLY: all N files match the manifest. This bundle is NOT SIGNED: anyone able to write it could have replaced its files and the manifest together. To rule that out, compare the manifest hash &lt;hex&gt; with one recorded at export.` |
| Signature not checked | `FILES MATCH, SIGNATURE NOT CHECKED: the bundle carries a signature (key sha256 &lt;fp&gt;) and no --public-key was given.` |
| `signature_invalid` | `SIGNATURE INVALID: manifest.json does not match its signature under the key you supplied.` |
| `signature_key_mismatch` | Same, plus `the bundle names a different key (sha256 &lt;fp&gt;)`. |
| `signature_missing` | `NOT SIGNED: you supplied a public key and the bundle has no signature.` |
| `file_altered` | `ALTERED: &lt;path&gt; (expected sha256 &lt;a&gt;, found &lt;b&gt;; expected &lt;n&gt; bytes, found &lt;m&gt;).` |
| `file_missing` | `MISSING: &lt;path&gt; is listed in the manifest and is not in the bundle.` |
| `file_unexpected` | `UNEXPECTED: &lt;path&gt; is in the bundle and not in the manifest.` |
| `unsafe_entry` | `&lt;path&gt; is a symbolic link or is not a regular file; it was not read.` |
| `manifest_malformed`, `manifest_not_canonical`, `manifest_root_mismatch`, `manifest_chain_broken` | Each names `manifest.json`; the last reuses `describeChain`'s text (`cli/src/core/hash_chain.ts:128-137`). |
| `log_head_mismatch` | `&lt;path&gt;: its records end at record &lt;seq&gt; (&lt;hash&gt;); the manifest recorded &lt;n&gt; records ending at &lt;hash&gt;. Records are missing from the end, or the log was replaced.` |
| `log_chain_broken` | `describeChain` output for that log. |
| `unsupported_version` | `This bundle is schema_version N; this nexus reads up to 1. Nothing was checked.` |

A chained log that was not closed at export, or that is a bounded excerpt, is reported as a note and is not a failure. Verify reports every finding up to a cap of 100, never only the first.

## 4. Security analysis (G-3, G-5)

**With write access to an unsigned bundle.**
- Detected: a changed byte in a payload file or the manifest; a removed or added file; a chained log edited or cut without recomputing the manifest.
- Not detected: a wholesale rewrite (files, links, `root_sha256`), which verifies as `intact_unsigned`. Unless the verifier supplies `--expect-manifest-sha256` or a key, nothing in the bundle stops this. The tool says so in every unsigned result.

**With a signature and the verifier's own copy of the public key.**
- Any change to `manifest.json` invalidates the signature, and any payload change mismatches the signed manifest.
- Removing the signature to downgrade is caught, because `--public-key` with no signature is `tampered`.
- A re-signed forgery fails under the verifier's key.
- Signing does not prove the content was true at export, or that the exporter's stores were untampered beforehand: a log's tail cut before export is exported as-is. Time is only the exporter's `created_at`.

**Path traversal and links.**
- Verify enumerates the real tree with `lstat` and compares it with the manifest's path set. It never opens a path because the manifest names it, so `../x`, absolute paths and duplicates surface as `file_missing` or `manifest_malformed`.
- Manifest paths must be relative POSIX, with segments matching `[A-Za-z0-9._-]{1,160}`, no `.` or `..`, depth at most 4, and unique ignoring case.
- A symlink or special file is a failure and is not read. Files are opened with `O_NOFOLLOW` and must `fstat` as regular files.
- Do not reuse `openVerified`: it requires the files to be owned by the caller (`cli/src/safe_fs.ts:110-112`), which would stop an auditor verifying a read-only copy.
- Zip-slip does not apply; the tool extracts nothing.

**Private key.**
- Read once through a descriptor. Refuse a non-regular file, anything over 16 KiB, or any group or world permission bit (`mode &amp; 0o077`), naming the `chmod 600` fix.
- Accept unencrypted PKCS#8 PEM whose `asymmetricKeyType` is `ed25519`. A passphrase-protected key gets a fixed usage error.
- Recommendation: do not support passphrases in v1.3. A flag leaks through `ps`, and a prompt breaks unattended use.
- Zero the buffer after use. Never write the key, its path or a parser error into the bundle, the output or a log; only the fingerprint is recorded.

**Snapshot rule.**
- Export may run beside a live session, because clients hold a shared lease (`cli/src/core/client_lease.ts:72-79`).
- State comes from one guarded load. Each log is read once into memory, cut at its last newline, then hashed and written from that buffer. The source is never read a second time.
- Write to `&lt;out&gt;.partial-&lt;random&gt;` (0700, files 0600), manifest last, then rename.
- A subject that is not at rest sets `at_rest: false` and prints a warning.

**Secrets into the bundle.**
- `standard` (default): every generated JSON or Markdown file goes through `redactForPersistence`, then `assertNoSensitivePersistenceContent` (`cli/src/core/persistence_protection.ts:380-392`).
- Chained logs, diffs and verify receipts cannot be re-redacted without breaking their hashes. They are scanned; a positive finding puts the file in `omitted[]` with the reason and leaves it out.
- `strict`: drops message bodies (role, length and SHA-256 remain), archived history, diffs, flight bodies (heads remain), attempt excerpts, and replaces the workspace path with its hash.
- Export never invokes `git` in the workspace.

**Verify bounds.** Each over-limit condition is a named failure, not a crash.
- `manifest.json` at most 4 MiB; at most 10,000 files; 256 MiB per file, hashed as a stream; 2 GiB in total.
- At most 1,000,000 records and 4 MiB per line in a chained log.
- JSON nesting at most 64, checked before `canonicalJson`, which recurses (`cli/src/core/hash_chain.ts:30-42`). `RangeError` is caught as a backstop.

**G-3.** The command takes no input from a model, client, hook or plugin, and reads only state stores by validated id plus files the operator names.

## Manifest members and hash definitions
Members: `schema_version` (1), `format` (`"nexus-audit-bundle/1"`), `bundle_id`, `created_at`, `nexus {version, commit, dirty}`, `subject {kind, task_id, session_id, store, workspace_path, workspace_sha256, status, updated_at, at_rest}`, `redaction`, `files[] {path, bytes, sha256, role, chain {seq, prev, hash}}`, `files_head`, `chained_logs[] {path, kind, records, status, head?, closed?, source?, selection?}`, `omitted[] {artefact, reason}`, `root_sha256`.

- **File `sha256`**: SHA-256 of the file's raw bytes, lowercase hex.
- **File entry link**: `linkRecord({path, bytes, sha256, role}, previous)`, so `hash` is SHA-256 of `` `${seq}\n${prev}\n${canonicalJson(entry without chain)}` ``, with `prev` = `CHAIN_GENESIS` for the first. Entries are sorted by path in code-unit order.
- **`files_head`**: `{seq, hash}` of the last entry's link.
- **`root_sha256`**: SHA-256 of `canonicalJson(manifest without root_sha256)` as UTF-8.
- **`manifest.json` on disk**: exactly `canonicalJson(manifest) + "\n"`.
- **`manifest_sha256`**: SHA-256 of those bytes.
- **Chained log `head`**: `{seq, hash}` of the last record's link as `verifyChain` reads the bundled bytes (one JSON object per line, blank lines skipped, an unparseable line counted as `null`).

## What changed
- **`durable?: boolean`, default true, on `writeAuditBundle`.** When true it fsyncs each payload file, then `manifest.json`, then each directory of the partial tree and the partial directory itself, renames into place, then fsyncs the output's parent. When false it issues no fsync. The module comment documents it in one sentence.
- **Reuse from `durable_file.ts`.** Directory fsyncs use the imported `fsyncDirectoryDurably`; that file is not edited. `writeFileDurably` and `withDurableSync` did not fit: the first writes via temp-and-rename, takes a string and is not an exclusive create, and the second only affects that module's own writers. File fsync is therefore one `fsyncSync` on the descriptor already open.
- **No replace at rename.** Node has no no-replace rename, so the writer creates the final name exclusively just before the rename. Anything already there, including an empty directory that appeared after the first check, fails with `EEXIST` and is left as it was. If the rename itself then fails, the placeholder is removed only if still empty.
- **Race documented.** The module comment now says verifying a bundle that someone is modifying concurrently is out of scope, because `O_NOFOLLOW` guards only the last path component.
- **Spy extended** in `cli/test/helpers/audit_fixture.ts`: it returns ordered events, maps each `fsyncSync` to the path its descriptor was opened with, and re-syncs the named exports of `node:fs` so calls made inside `durable_file.ts` are seen.
- **Two new tests**; all other writes in the tests pass `durable: false`.
  - The default-durable test asserts an fsync for each of the 10 payload files, the manifest, the 6 subdirectories and the partial directory, all before the rename. It also checks the manifest's fsync comes after every payload's, the parent's fsync comes after the rename, the total is exactly 19, and `durable: false` gives 0.
  - The destination-appears test creates an empty directory at the output mid-write and asserts `EEXIST` with that directory untouched.
