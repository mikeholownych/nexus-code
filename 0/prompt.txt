# Terminal Agent Mission: Nexus Code Engineering Invariants, Execution Authority, and Failure Semantics

## Role

You are a principal software architect, senior systems engineer, and independent production-readiness auditor specializing in autonomous AI engineering systems, durable workflow execution, distributed systems, and failure recovery.

You are working directly in the **Nexus Code** repository:

https://github.com/mikeholownych/nexus-code

Your assignment is to independently audit, design, implement, and validate engineering improvements based on seven patterns associated with mature, production-quality code.

**This is an authorized engineering implementation assignment, not a research-only exercise.**

You are authorized to inspect and modify the codebase, execute tests, create regression tests, run local integration environments, implement migrations where necessary, and perform controlled fault-injection experiments.

Do not stop after producing recommendations. Implement justified improvements and provide evidence of their correctness.

Do not assume architectural deficiencies exist merely because this assignment identifies possible failure modes.

---

# 1. Mission Objective

Establish and verify five core engineering guarantees:

1. Invalid lifecycle states and transitions are rejected at authoritative boundaries.
2. Consequential state mutations have explicit ownership and enforceable authority.
3. External side effects have identifiable execution, retry, recovery, and reconciliation semantics.
4. Interrupted or ambiguous operations cannot silently become duplicate or falsely successful operations.
5. Critical architectural assumptions are encoded in executable constraints, tests, or durable engineering documentation.

Apply these guarantees to Nexus Code's actual architecture, not an imagined replacement architecture.

Prioritize correctness, determinism, recoverability, auditability, and backwards compatibility.

Performance optimizations are secondary and must not weaken correctness.

# 3. Audit Domain A: Invalid States and Lifecycle Integrity

Investigate how Nexus represents:

- Tasks and objectives.
- Agent sessions.
- Execution steps.
- Tool invocations.
- Reviewer decisions.
- Acceptance criteria.
- Retries.
- Escalations.
- Paused sessions.
- Compaction and resumed context.
- Provider failures.
- Cancelled or interrupted operations.
- Final completion status.

Identify whether multiple independent fields can produce contradictory states.

Examples include:

- A task marked complete while required validation failed.
- A cancelled operation subsequently marked successful.
- A reviewer rejection coexisting with an accepted state.
- A paused session still executing consequential tools.
- A failed operation being retried after an irreversible external effect.
- A resumed execution that no longer satisfies its original authorization context.

These are hypotheses. Verify whether each can actually occur.

## Required work

1. Map the existing state model.
2. Identify authoritative state writers.
3. Identify transitions and preconditions.
4. Document prohibited transitions.
5. Determine whether enforcement exists at the mutation boundary.
6. Add missing validation or transition guards.
7. Add regression tests proving invalid transitions are rejected.

Where appropriate, prefer explicit transition operations over arbitrary status mutation.

Avoid converting state representation without a demonstrated benefit.

## Acceptance criteria

- Invalid transitions fail deterministically.
- Rejected transitions do not produce partial authoritative mutations.
- Existing valid transitions continue to work.
- Transition failure reasons are inspectable.
- Critical lifecycle invariants are covered by automated tests.

# 4. Audit Domain B: Ownership Versus Accessibility

Determine which components have authority to modify:

- Orchestrator state.
- Task completion.
- Agent execution status.
- Tool authorization.
- Retry decisions.
- Reviewer acceptance.
- Execution evidence.
- Recovery checkpoints.
- Provider routing and fallback decisions.

Distinguish between reading state, proposing a transition, and committing a transition.

A component that can inspect a decision should not automatically have authority to make that decision.

## Critical scenario: Reviewer authority

Investigate whether a reviewer agent can directly cause a task to be accepted or completed.

The intended separation is:

1. Reviewer evaluates the work.
2. Reviewer produces evidence and a recommendation.
3. The authoritative orchestration layer evaluates the evidence against the acceptance contract.
4. The authoritative layer commits or rejects the state transition.

If Nexus already implements an equivalent mechanism, verify it.

If it does not, implement the minimum necessary enforcement.

## Additional concerns

Investigate concurrent state writers, stale-state updates, lost updates, asynchronous race conditions, and recovery processes that bypass normal transition rules.

Where concurrency can affect authoritative transitions, evaluate optimistic concurrency, version checks, or transaction-level protections appropriate to the existing persistence architecture.

## Acceptance criteria

- Every critical state transition has an identifiable authority.
- Unauthorized state mutation attempts are rejected.
- Concurrent transitions cannot silently overwrite incompatible decisions.
- Reviewers cannot elevate recommendations into authoritative acceptance without the required validation.
- Recovery paths do not bypass normal invariants.

# 5. Audit Domain C: External Side-Effect Semantics

This is a critical-priority workstream.

Inventory all operations capable of producing persistent or external effects.

Examples:

- Filesystem writes.
- Shell commands.
- Git commits, branch changes, and resets.
- GitHub issue or pull-request creation.
- Network requests.
- External API operations.
- Database mutations.
- CI/CD interactions.
- Deployment operations.
- Credential or configuration modifications.
- Agent-generated scripts.

Classify operations based on their actual semantics.

At minimum, distinguish:

- Read-only operations.
- Repeatable operations with verified idempotency.
- Mutating operations with reconciliation support.
- Mutating operations with uncertain retry safety.
- Potentially irreversible operations.

Do not infer safety from a tool name, HTTP method, or the agent's description of an operation.

## 5.1 Operation identity

Investigate whether consequential tool executions possess stable identifiers that survive:

- Process restarts.
- Session resumptions.
- Retries.
- Orchestrator failover, if supported.
- Model-provider fallback.
- Context compaction.

If identifiers are missing or regenerated during retry, determine the risks and implement appropriate durable operation identity.

## 5.2 Execution records

Evaluate whether consequential operations preserve sufficient information to reconstruct:

- Who or what initiated the operation.
- Which task and execution attempt initiated it.
- Which authorization applied.
- Which normalized arguments were supplied.
- Which tool or execution adapter was used.
- When execution began.
- Whether execution was acknowledged.
- What evidence establishes the outcome.
- Whether a retry is safe.
- Whether reconciliation is necessary.

Do not log secrets unnecessarily.

Use hashes or controlled references when recording sensitive inputs.

Do not claim an audit trail is immutable unless the implementation actually enforces or verifies that property.

## 5.3 Authorization boundary

Inspect whether authorization is checked immediately before side-effect execution.

Determine whether authorization is bound to the actual operation and arguments or merely to an earlier generic approval.

Assess whether resumed or modified operations can reuse stale authorization.

Implement missing enforcement where justified and consistent with the existing architecture.

## Acceptance criteria

- Consequential side effects are identifiable.
- Retry behaviour reflects actual operation semantics.
- Authorization cannot silently become detached from the executed operation.
- Executions remain traceable across retries and resumptions.
- The system does not claim success solely because a tool invocation was issued.

# 6. Audit Domain D: Unknown Outcomes and Recovery Correctness

This is the highest-priority technical investigation.

Investigate what happens when an external operation succeeds but Nexus fails before recording its result.

Example:

1. Nexus requests a tool operation.
2. The tool completes a repository mutation.
3. The process terminates before the result is persisted.
4. Nexus resumes.
5. The previous attempt appears incomplete.
6. Nexus considers retrying the same operation.

Determine whether the existing implementation can distinguish:

- Operation not started.
- Operation started.
- Operation succeeded and acknowledged.
- Operation failed with a confirmed outcome.
- Operation outcome unknown.

Do not assume every lifecycle needs exactly these five states. Use the existing model if it captures equivalent semantics.

## Required investigation

Evaluate:

- Durable operation identity.
- Write-ahead execution intent.
- Acknowledgement persistence.
- Idempotency keys.
- Reconciliation mechanisms.
- Retry eligibility.
- Concurrent recovery workers.
- Repeated or duplicated tool responses.
- Cancellation races.
- Timeout ambiguity.
- Partial filesystem mutations.
- Process termination during execution.
- Provider failure after tool-call generation.
- Resume after context compaction.

## Recovery rule

**An unknown external outcome must never be interpreted as confirmed failure merely to justify automatic retry.**

Where an operation is safely reconcilable, implement or verify reconciliation.

Where idempotency can be enforced, use an appropriately scoped stable identifier.

Where neither is possible, prevent automatic repetition and surface the unresolved state for an authorized decision.

Do not impose a universal retry policy across semantically different tools.

## Fault-injection requirements

Build deterministic tests that interrupt execution at meaningful boundaries:

- Before operation dispatch.
- After durable intent persistence.
- After external execution but before local acknowledgement.
- During result persistence.
- During reconciliation.
- During concurrent retry or recovery attempts.

Include scenarios where the external effect occurred despite the caller receiving an error or timeout.

Use subprocess termination, controlled adapters, fault hooks, or test doubles as appropriate.

Avoid timing-only tests when deterministic synchronization is possible.

## Acceptance criteria

- Unknown outcomes remain distinguishable from confirmed failure.
- Unsafe automatic retries are blocked.
- Duplicate external effects are prevented where the system claims that guarantee.
- Reconciliation produces evidence-backed outcomes.
- Concurrent recovery does not bypass operation ownership.
- Crash-recovery tests reproduce the original failure mode and demonstrate the correction.
- All guarantees are scoped accurately. Do not claim exactly-once execution unless proven for the relevant operation and failure model.

# 7. Audit Domain E: Duplication and Premature Abstraction

Investigate whether Nexus has accumulated abstractions that combine semantically distinct workflows.

- Agent profiles.
- Tool adapters.
- Provider integrations.
- Model-routing components.
- Reviewer workflows.
- Retry policies.
- Recovery handlers.
- Session persistence.
- Compaction and memory management.

Look for abstractions with growing numbers of flags, conditional branches, or unrelated responsibilities.

Also identify duplicated implementations that genuinely share stable behaviour.

## Decision rule

Do not refactor merely because code is duplicated.

Determine whether the duplicated concepts change for the same reasons.

If two implementations are likely to evolve independently, preserve the distinction.

If repeated code represents a stable shared contract, consider a narrow abstraction.

Every proposed refactoring must identify:

- The current maintenance or correctness problem.
- The demonstrated common semantics.
- The expected axis of independent change.
- The tests preserving behaviour.

Avoid broad cosmetic refactoring.

# 15. Non-Negotiable Engineering Principles

Apply these principles throughout the assignment.

**Evidence before architecture.** Do not implement structures justified only by hypothetical future requirements.

**Correctness before performance.** Never weaken recovery, authorization, or acceptance guarantees to increase throughput.

**Authority must be explicit.** Observing or recommending a state transition is not equivalent to owning it.

**Unknown is not failed.** A missing acknowledgement does not prove an external operation did not occur.

**Retries require semantics.** A retry is safe only when the operation's actual effects and reconciliation guarantees justify it.

**Recovery is part of execution.** A workflow is not complete merely because its happy path succeeds.

**Documentation is not enforcement.** Critical invariants must be protected by the system wherever practical.

**Tests must exercise failure.** A system that passes only successful-path tests has not demonstrated recovery correctness.

**Do not replace working controls without evidence.** Strengthen the existing architecture rather than creating competing frameworks.

**Report limitations accurately.** An unverified guarantee is not a proven guarantee.

## Findings

**F1. VERIFIED_DEFECT (Medium): `operation resume` and `decide` drive from state loaded outside the lock, so concurrent writers can lose updates.**
- `operation_cli.ts:298` calls `store.load(id)` with no lock. `drive()` then calls `driveOperation` (`operation_runner.ts:696-704`), which only then calls `store.acquire`. It never reloads, and `OperationStore.save` (`operation_runner_persistence.ts:51`) has no version or compare-and-swap check.
- The `decide` path has the same shape. `applyOperatorDecision` loads, saves and releases the lock, then `drive` re-acquires with the returned in-memory state.
- By contrast, `message`, `checkpoint` and `restore` do `acquire` then `load` correctly (`operation_cli.ts:386-388`, `484-487`).
- Scenario: `resume X` loads a mid-run snapshot while driver A is running. A finishes the operation (`COMPLETE`) and releases the lock. `resume` then takes the lock and runs on the stale snapshot. `reconcileInterruptedRuns` flips RUNNING units to RUNNABLE and bumps `unknownResumes`, completed units can be re-executed, and the first `save()` overwrites A's COMPLETE record.
- Expected invariant: load the state after taking the lock.
- Tests: `operation_lock.test.ts` covers lock reclaim only, not the stale-load window.

**F2. VERIFIED_DEFECT (Low-Medium): `operation run` with an explicit `spec.id` silently replaces an existing operation record.**
- `operation_cli.ts:266` and `validateOperationSpec` (86-100) check only the id's shape.
- `OperationStore.save` (`operation_runner_persistence.ts:56-81`) overwrites `operation: op` wholesale, including receipts and history.
- Scenario: a second `run` with the same id wipes a COMPLETE or BLOCKED operation, and in isolated mode `ensureIntegrationWorktree` runs against the old pair.
- Expected invariant: refuse when `hasTaskState(id)`.
- Tests: none found.

**F3. VERIFIED_CONTROL_GAP (Low-Medium): the operation document's status is not validated or integrity-bound at load.**
- `validateOperationState` (`core/operation_schema.ts:89-135`) checks structure only. It does not check that the operation and unit status values are valid, that the status is consistent with the units (COMPLETE operation with an incomplete required unit), or that a COMPLETE unit has a `result`.
- `runOperation` (`operation_runner.ts:138`) returns immediately for a stored `COMPLETE`, and the CLI exits 0 (`operation_cli.ts:221`).
- Separately, `printStatus` dereferences `u.result!` (`operation_cli.ts:193`), so a COMPLETE unit with no result would crash it.
- The task store sits outside the workspace. I found no file-level protection or MAC, but I did not trace sandbox reach into `~/.nexus`, so exploitability is UNVERIFIED.
- Tests: `operation_schema.test.ts` covers the structural checks only.

**F4. PARTIALLY_ENFORCED (Low): no cross-process exclusivity for agent task/session state.**
- Operations have a lock. Agent tasks do not: only the in-process `activeTurn` check at `agent.ts:6480`.
- `checkpointDurableState` (`agent.ts:1679-1765`) reads `existing`, then calls `saveTaskState` with the whole document. Writers are serialised by the flock but nothing checks a version, so two processes resuming the same task id get last-writer-wins.
- The message log is hash-chained, but `appendValidatedMessages` diffs against whatever is on disk and appends, so divergence is not detected.
- I found no per-task lock via grep. The client lease is shared.
- Tests: `task_state_v2.test.ts` and `state.test.ts` cover atomicity and recovery; a two-writer test was not found.

**F5. PARTIALLY_ENFORCED (Low): task `status` is not validated on save.**

**F6. PARTIALLY_ENFORCED (Low): the cancel-versus-completion race, and `scheduler.apply` accepting a result for a unit that is not RUNNING.**

## Domain F: are OpenAI-compatible endpoints treated as interchangeable?

Mostly yes, with a few explicit exceptions.

- **Tool calling is assumed, never probed.** `protocols/index.ts:21` sets `nativeTools:false` for openai-chat, so `supportsNativeTools()` (`client.ts:749`) is true unless the operator sets `NEXUS_NATIVE_TOOLS=off` or `omitParams` lists `tools`. `doctor --deep` (`doctor.ts:567`) sends `tools=[]`, so nothing tests tool calling.
- **Context window and request counting are explicit.** `discoverAdvertisement` (`client.ts:1337`) reads `/models`, fingerprints the server kind (gateway, vllm, llamacpp, ollama) and probes `/tokenize`. Each number is labelled with its source (`provider_capabilities.ts`).
- **Server-specific grammar and strict schema** are enabled only after identity verification. Grammar rejection is tracked per endpoint (`client.ts:973`).

- **Tokenizer:** one calibrated estimator (`tokens.ts`) serves all models. This is labelled, so ALREADY_ENFORCED.

### Failover

Failover exists only on the legacy endpoint path. Provider connections are pinned (`client.ts:694`, `1166`).

- **Authorization is checked per endpoint: ALREADY_ENFORCED.** `executeWithFailover` (`client.ts:1219`) checks cloud authorization per endpoint, and egress runs per endpoint. A credential is bound to its origin (`credentialFor`, `client.ts:1184`).
- **Tests covering it:** `egress.test` CTX-006, `cloud_providers.test:287`, `provider_fixes.test:60`, `project_env_allowlist.test`, `credential_boundary.test`.
- **In-request failover is limited to failures where nothing executed on the server, and only for temporary conditions** (`client.ts:527`). Unknown-execution failures go through the recovery controller, which is bounded by `maxUnknownReplays`.
- **Capability checks before switching: none.** Details are F1 and F2.

### Findings

**F1. VERIFIED_CONTROL_GAP (medium): failover and the availability probe never check capabilities.**
- `client.ts:1236` sends the same `this.model` and the same request, admitted against the primary's limits, to the fallback.
- `probeEndpointAt` (`client.ts:1670`) calls any status below 500 other than 408/429 "available". That includes 401, 403 and 404.
- `probeAvailability` (`client.ts:1643`) then sets `activeEndpointIndex` permanently.
- Scenario: the primary dies mid-request (unknown execution), the recovery controller probes the alternate, and the alternate returns 401 or 404 on `/models`. It becomes active, the resubmit fails with 401 (not failover-eligible, `client.ts:1247`), and the turn stops. Later steps also start on that endpoint, because nothing returns to the primary.
- Context size is only corrected afterwards: a rejection becomes `CAPACITY_REJECTED`, then a compaction retry (`agent.ts:7121`). `refreshCapabilities` re-keys on the active endpoint at the next step (`agent.ts:3404`).
- Tests: `provider_recovery.test:306`, `provider_status_plain.test:264`, `server_kind_cache.test:186`, `tool_grammar_wire.test:174`. None covers a probe answering 401 or 404 on the alternate, or a fallback with a smaller window or no tools.

**F2. VERIFIED_CONTROL_GAP (low): learned parameter rejections are client-wide, not per endpoint.**
- `unsupportedParams` (`client.ts:632`, `1028`) is filled by `withParameterRetry`. A 400 is not failover-eligible, so the retry stays on endpoint A.
- Scenario: A rejects `max_tokens` or `stream_options`; after failover to B those are omitted too, so B's output cap is lost. Grammar rejection, by contrast, is per endpoint, which shows the intended design.
- Tests: `local_request_params.test` covers the drop but not a later failover.

**F3. VERIFIED_CONTROL_GAP (low to medium): planner and coder clients inherit the main connection's fallback endpoints.**
- `agent.ts:1260-1277` spreads `...config`, so `fallbackEndpoints` is kept. When `plannerEndpoint` or `coderEndpoint` is set, `provider` is undefined and the constructor appends the main fallbacks (`client.ts:694`).
- Scenario: a planner endpoint serving model P fails to connect, and the request for P goes to a fallback that serves the main model. The outcome is a 404, or a different model answering under the same id. Only the receipt's `effectiveModel` shows it.
- `operation_account_identity.test` covers only credential identity.

**F4. VERIFIED_DEFECT (medium): subagents never discover provider capabilities.**
- `refreshCapabilities` is called only from `runTurnImpl` (`agent.ts:6972`) and the forced path in `measureAdmission` (`agent.ts:3508`). `runSubagent` (`agent.ts:8081-8180`) has neither.

No abstraction should be added, removed, or consolidated solely because of line-count reduction or visual similarity.

# 4. Engineering Principle B: Preserve Visible Control Flow

## Objective

Prevent excessive function extraction or indirection from hiding consequential execution behaviour.

Focus particularly on:

- Orchestration.
- Authorization.
- Tool execution.
- Retry decisions.
- Recovery.
- State transitions.
- Reviewer acceptance.
- Provider fallback.
- Session resumability.

## Investigation

Trace important execution paths end to end.

Determine how difficult it is to establish:

- Where authorization occurs.
- Where an operation becomes externally observable.
- Where durable execution intent is recorded.
- Where a retry decision is made.
- Where an unknown outcome is reconciled.
- Where authoritative state is committed.
- Where a reviewer recommendation becomes an acceptance decision.
- Where execution can be cancelled.
- Where fallback changes the selected provider.

Identify excessive forwarding layers, trivial wrapper methods, and fragmented control flow.

## Required distinction

A longer function is not automatically defective.

A short function is not automatically maintainable.

Function boundaries should represent coherent responsibilities, meaningful contracts, or independently testable behaviour.

Do not combine separate security or transaction boundaries merely to make a workflow easier to read.

## Implementation

Where justified:

- Remove redundant forwarding indirection.
- Consolidate fragmented but coherent control flow.
- Extract meaningful responsibilities that are currently mixed.
- Make consequential decisions discoverable.
- Preserve explicit failure paths.
- Improve names and interfaces where they reduce ambiguity.

Avoid broad stylistic rewrites.

## Acceptance

A reviewer must be able to trace the important execution sequence without discovering hidden side effects or undocumented decision boundaries.

Existing authorization, recovery, and lifecycle guarantees must remain enforced.

# 5. Engineering Principle C: Explicit Decisions Over Clever Dispatch

## Objective

Evaluate whether generalized dispatch mechanisms obscure important domain decisions.

Inspect:

- State-based dispatch.
- Tool registries.
- Agent selection.
- Model selection.
- Retry policies.
- Recovery handlers.
- Reviewer routing.
- Authorization decisions.
- Fallback logic.

Registries and plugin systems are not inherently problematic.

The concern is whether their use hides critical behaviour or makes missing cases difficult to detect.

## Required investigation

Determine:

1. Whether dispatch is exhaustive where required.
2. Whether unsupported states fail safely.
3. Whether missing handlers are silently ignored.
4. Whether configuration can bypass important invariants.
5. Whether consequential branches remain discoverable.
6. Whether runtime registration changes authorization semantics.
7. Whether generic interfaces conceal different provider guarantees.

Pay particular attention to silent optional dispatch, implicit defaults, and fallback selection.

## Implementation

Where justified:

- Introduce exhaustive handling.
- Reject unsupported states explicitly.
- Strengthen handler contracts.
- Expose consequential decisions.
- Add missing-case regression tests.
- Remove unnecessary indirection.

Do not replace a sound extensible registry with a large conditional structure merely to appear more explicit.

## Acceptance

Important decisions must be traceable and unsupported conditions must produce defined behaviour.

No material execution decision should silently disappear because a handler or configuration entry is missing.

# 6. Engineering Principle D: Preserve Architectural Reasoning

## Objective

Ensure important implementation decisions remain understandable after the original author or agent session is gone.

Investigate how Nexus currently preserves:

- Architectural decisions.
- External API constraints.
- Provider-specific behaviour.
- Recovery limitations.
- Historical failure conditions.
- Compatibility guarantees.
- Rejected alternatives.
- Intentional duplication.
- Security assumptions.
- Performance trade-offs.
- Known correctness limitations.

## Important distinction

Code should express enforceable behaviour.

Tests should establish observable guarantees.

Documentation should preserve reasoning that code alone cannot explain.

Agent memory should support discovery and continuity, but must not become the sole authoritative source of critical engineering constraints.

## Required work

Identify existing mechanisms for:

- Architecture decision records.
- Repository documentation.
- Path-scoped agent instructions.
- Durable engineering memory.
- Regression evidence.
- Change rationale.

Reuse existing conventions.

Do not introduce a new architectural-decision framework unless the repository lacks a suitable mechanism and the deficiency is consequential.

## Implementation

Where justified:

- Document non-obvious constraints close to the relevant code.
- Link important decisions to regression tests.
- Record why an apparently simpler implementation is unsafe.
- Identify intentionally independent implementations.
- Preserve rationale for provider-specific workarounds.
- Update relevant agent instructions.
- Remove or correct stale architectural explanations.

Include provenance where available, such as relevant issue, commit, upstream specification, or reproduced incident.

Clearly distinguish verified constraints from assumptions.

## Lifecycle requirement

Architectural rationale must be reviewable when its associated code changes.

Do not create an append-only collection of obsolete explanations.

Where practical, connect rationale to affected code paths and tests so changes can trigger review.

## Acceptance

Critical non-obvious constraints are discoverable without relying on the original developer's memory or a historical agent conversation.

# 7. Engineering Principle E: Strengthen Invariants Before Adding Defensive Complexity

## Objective

Identify defensive logic that repeatedly compensates for invalid states admitted elsewhere.

Inspect:

- Input validation.
- Session state.
- Task lifecycle.
- Persistence.
- Execution checkpoints.
- Recovery.
- Tool authorization.
- Acceptance.
- Provider responses.
- External integration boundaries.

## Investigation

Look for repeated guards against the same invalid condition.

Determine whether those conditions can be prevented at a more authoritative boundary.

Examples to investigate, not assume:

- Completed tasks without valid acceptance evidence.
- Invalid state combinations.
- Missing execution identifiers.
- Tool responses detached from their initiating operation.
- Recovery checkpoints referring to nonexistent execution attempts.
- Retry requests lacking operation identity.
- Provider fallback that violates task requirements.
- Reviewer approval disconnected from the reviewed artifact.

For every case, determine whether upstream enforcement already exists.

## Implementation

When appropriate:

- Add transition-level validation.
- Strengthen schemas or constructors.
- Enforce persistence constraints.
- Tighten execution contracts.
- Reject contradictory states before persistence.
- Add invariant tests.

Do not indiscriminately remove downstream defensive checks.

Legacy data, partial upgrades, corrupted persistence, external inputs, and distributed failures may require validation at multiple trust boundaries.

## Acceptance

Invalid states are rejected at the earliest authoritative boundary that can enforce the relevant invariant.

Necessary defensive checks remain in place.

No invalid-state prevention mechanism relies exclusively on agent prompt compliance.

# 8. Engineering Principle F: Every Architectural Layer Must Justify Its Existence

## Objective

Identify architectural layers that introduce indirection without providing meaningful separation.

Examine:

- Controller or command interfaces.
- Application services.
- Orchestration services.
- Domain components.
- Repository interfaces.
- Persistence adapters.
- Tool adapters.
- Provider adapters.
- Agent abstractions.
- Middleware.
- Execution wrappers.

## Architectural boundary test

For each candidate layer, determine whether it:

1. Owns a distinct responsibility.
2. Enforces an invariant.
3. Protects an authorization boundary.
4. Encapsulates different transaction or failure semantics.
5. Isolates an independently changing dependency.
6. Establishes a useful testing seam.
7. Supports an actual architectural requirement.

A layer that merely forwards arguments is a candidate for removal, not automatic technical debt.

It may still serve a legitimate compatibility, instrumentation, or extension purpose.

## Implementation

Where evidence supports simplification:

- Remove unnecessary forwarding layers.
- Consolidate redundant interfaces.
- Preserve meaningful domain boundaries.
- Maintain backwards compatibility.
- Retain existing instrumentation and evidence hooks.
- Reduce circular or unnecessary dependencies.
- Update affected tests and documentation.

Avoid making the architecture flatter at the expense of authority separation, testability, or failure containment.

## Acceptance

Every material layer retained or introduced has an identifiable purpose beyond adherence to a design pattern.

# 9. Engineering Principle G: Evaluate Actual Change Cost

## Objective

Develop a practical, evidence-based method for evaluating whether a change improves maintainability.

Do not rely on a single numeric clean-code score.

Do not assume that fewer lines, fewer classes, lower cyclomatic complexity, or reduced duplication automatically means improvement.

## Evaluation dimensions

Assess material refactors across:

### 9.1 Change locality

How many modules must be understood or modified to implement a coherent requirement?

### 9.2 Coupling

Does changing one concern unexpectedly affect another?

### 9.3 Control-flow transparency

Can an engineer determine the consequential execution path without excessive indirection?

### 9.4 Invariant preservation

Does the change preserve lifecycle, authorization, recovery, and acceptance guarantees?

### 9.5 Regression exposure

How much unrelated behaviour is at risk?

### 9.6 Testability

Can the modified behaviour be tested deterministically?

### 9.7 Operational diagnosability

Can failures be localized and explained using available evidence?

### 9.8 Rationale discoverability

Can maintainers establish why important constraints exist?

## Required methodology

Use before-and-after evidence when changing architecture.

Where useful, assess a representative maintenance scenario against the existing design and the proposed design.

Measure concrete effects such as:

- Files and modules affected.
- Call-path complexity.
- Dependency changes.
- Additional state transitions.
- Required regression scope.
- New configuration or extension mechanisms.
- Impact on failure-path visibility.

Do not treat these measurements as universally comparable or authoritative in isolation.

## Acceptance

Architectural improvements must be supported by a defensible explanation of how they reduce actual engineering risk or maintenance cost.

A refactor that merely improves superficial metrics does not satisfy this requirement.

# 11. Continuous Evaluation and Regression Intelligence

Integrate this work with the existing evaluation infrastructure.

Inspect the current implementation before adding new mechanisms.

Develop representative evaluation scenarios that distinguish beneficial refactoring from harmful refactoring.

At minimum, consider:

### Scenario A: Wrong abstraction

Two similar implementations have different domain semantics.

A coding agent is asked to eliminate duplication.

Expected behaviour:

The agent preserves independence unless shared semantics are demonstrated.

### Scenario B: Excessive extraction

A coherent execution workflow is fragmented into many trivial wrappers.

Expected behaviour:

The agent recognizes the navigational cost and avoids or reverses unnecessary indirection without collapsing meaningful boundaries.

### Scenario C: Hidden side effect

A refactor moves externally observable actions behind an apparently harmless helper.

Expected behaviour:

The review identifies the obscured recovery or authorization semantics.

### Scenario D: Missing invariant

Several downstream functions contain guards for a state that should be prohibited upstream.

Expected behaviour:

The agent identifies the authoritative boundary and strengthens it while preserving necessary defence in depth.

### Scenario E: Unnecessary architectural layer

A new service is introduced that merely forwards existing calls.

Expected behaviour:

The agent evaluates whether the layer protects any independent responsibility before retaining it.

### Scenario F: Lost rationale

A cleanup removes a non-obvious guard or workaround whose purpose relates to a historical failure.

Expected behaviour:

The agent discovers or preserves the supporting rationale and associated regression protection.

### Scenario G: Misleading improvement

A refactor reduces line count and duplication but increases coupling or regression exposure.

Expected behaviour:

The review evaluates the actual trade-off instead of accepting superficial improvements.

### Scenario H: Correct deliberate abstraction

Several implementations genuinely share one stable invariant.

Expected behaviour:

The agent recognizes that consolidation is justified and does not blindly prefer duplication.

## Evaluation requirements

Each scenario must include:

- Input repository fixture or controlled code example.
- Task instruction.
- Relevant architectural constraints.
- Expected acceptable behaviours.
- Known unacceptable behaviours.
- Validation method.
- Regression evidence.

Where possible, use deterministic checks.

For qualitative engineering decisions, acknowledge that a reviewer model's judgment is not conclusive evidence.

Avoid grading against one preferred implementation when multiple designs legitimately satisfy the requirements.

Run the scenarios through actual Nexus workflows where the environment supports them.

Report which evaluations were performed against real execution and which were limited to isolated fixtures.

## C. Dispatch

- **MCP and plugin tools cannot execute through the spine.**
  - Classification: VERIFIED_DEFECT (static trace). Severity: medium-high.
  - Evidence:
