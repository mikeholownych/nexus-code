# Terminal Agent Mission: Nexus Code Skills Architecture Independent Verification and Remediation Planning

## Role and Mandate

You are acting as an independent Principal Software Architect, Security Engineer, and Runtime Reliability Auditor reviewing the Nexus Code repository.

Your mission is to **complete the previously limited skills architecture audit, independently verify every material finding, execute the necessary tests and adversarial experiments, and develop an implementation-ready remediation plan for any demonstrated gaps.**

You have full authorization to inspect the repository, execute tests, build binaries, create temporary fixtures, instrument execution paths, and perform controlled adversarial testing.

Do not restrict your investigation to static analysis.

Do not implement the proposed production feature changes during this mission. The objective is to establish an accurate baseline, prove or disprove the findings, and prepare a technically defensible engineering plan.

Repository: `https://github.com/mikeholownych/nexus-code`

Previous audit baseline: `3c54e6014c2ea5281f642fdd53ac20605f2b24ae`

Audit the current repository HEAD. Record the exact commit and identify changes since the previous audit that materially affect the findings.

---

## 1. Operating Principles

Follow these requirements throughout the engagement.

### 1.1 Independent verification

Treat the previous audit as a collection of hypotheses, not authoritative conclusions.

For every finding:

- Locate the relevant implementation.
- Trace the complete execution path.
- Identify enforcement points and bypass routes.
- Inspect existing tests.
- Execute relevant tests.
- Construct additional experiments where existing tests are insufficient.
- Determine whether the finding is confirmed, partially confirmed, disproven, or unresolved.
- Record supporting and contradictory evidence.

Do not accept comments, documentation, test names, or intended architecture as proof of runtime behavior.

### 1.2 Evidence standard

Distinguish between:

- **SOURCE_CONFIRMED:** Directly established by source inspection.
- **TEST_CONFIRMED:** Established by executed tests with recorded results.
- **ADVERSARIAL_CONFIRMED:** Established by a controlled negative-path experiment.
- **INFERRED:** Supported by evidence but not directly demonstrated.
- **UNVERIFIED:** Insufficient evidence.
- **DISPROVEN:** Contradicted by verified evidence.

A passing unit test establishes only the behavior exercised by that test.

A security control is not considered proven merely because its happy path succeeds.

### 1.3 Repository safety

Inspect `AGENTS.md` and applicable repository instructions before executing work.

Respect existing worktree and concurrency controls.

Use a dedicated audit worktree and isolated temporary state.

Never overwrite unrelated work.

Use isolated `HOME`, configuration, and state directories for tests.

Do not expose credentials, inference gateway tokens, private configuration, or sensitive runtime data.

No production deployments, public releases, merges, tags, or publication are authorized.

Local temporary changes required for instrumentation and experiments are authorized. Keep these isolated from production branches.

### 1.4 No architectural assumptions

Do not assume:

- Skills require a new authorization engine.
- Skill execution identity is entirely absent.
- Existing receipts cannot establish attribution.
- Current execution controls are bypassable.
- Skill metadata must be the source of authority.
- Existing qualification infrastructure cannot be reused.
- The previously identified priorities remain correct.

Determine these matters from evidence.

# 3. Independently Revalidate Previous Findings

## F-01: Skill Capability Contracts

Previous hypothesis:

Skill frontmatter is used primarily for discovery metadata and does not define enforceable per-skill permissions.

Investigate:

- All supported frontmatter fields.
- Skill metadata parsing.
- Capability declarations.
- Runtime policy configuration.
- Existing authority grants.
- Tool-group constraints.
- Role-specific allowlists.
- Possible skill-specific restrictions implemented elsewhere.

Determine:

1. Can a skill declare permitted capabilities?
2. Can those declarations influence actual tool admission?
3. Can the runtime independently enforce them?
4. Does a skill declaration ever expand existing authority?
5. Can a skill invoke tools outside its intended procedural scope?
6. Are restrictions maintained across delegated execution?

Do not conclude that per-skill authorization is missing until all existing enforcement mechanisms have been examined.

## F-02: Skill-to-Execution Attribution

Previous hypothesis:

Activation injects instructions, but downstream tool calls are not bound to a persistent skill execution identity.

Trace:

`skill discovery → selection → activation → context injection → model response → tool dispatch → execution spine → authorization → execution receipt → durable state`

Determine whether the runtime records:

- Skill name.
- Skill source.
- Activation identity.
- Content identity.
- Associated task identity.
- Subsequent tool calls.
- Delegated tool calls.
- Approval decisions.
- Completion and verification evidence.

Test whether these relationships survive:

- Session restart.
- Context compaction.
- Model fallback.
- Subagent delegation.
- Failed tool execution.
- Interrupted execution.
- Recovery from partial state.

Distinguish between information inferable from conversational history and structured, enforceable, durable execution attribution.

## F-03: Skill Integrity and Version Binding

Previous hypothesis:

The skill content is not cryptographically pinned to the execution that activated it.

Investigate:

- File hashing.
- Content identity.
- Session snapshots.
- Tool output preservation.
- Existing integrity mechanisms.
- Skill file reload behavior.
- Changes during an active task.

Test:

1. Activate a skill.
2. Modify its source file.
3. Continue the execution.
4. Restart the session.
5. Resume the task.
6. Determine which content version governs the execution.

Repeat with:

- Symlink target changes.
- Duplicate skill names.
- Global and workspace skill precedence.
- Removed skills.
- Changed skill metadata.

Record whether existing behavior creates a time-of-check/time-of-use ambiguity.

## F-04: Skill Trust and Supply Chain

Previous hypothesis:

Global installation location establishes trust without independently validating the publisher or contents.

Inspect:

- Global skill loading.
- Workspace trust.
- Symlink handling.
- Trust transitions.
- Source origin retention.
- Skill installation and updates.
- Prompt-injection defenses.
- External skill compatibility.

Evaluate these threat scenarios:

- Malicious globally installed skill.
- Compromised skill dependency.
- Symlink redirected outside the expected installation root.
- Trusted workspace containing malicious instructions.
- Skill body attempting to impersonate operator or system authority.
- Skill requesting secret exposure or unauthorized egress.
- Skill changed after trust approval.

Determine which protections are actually enforced and which depend on the user's installation decisions.

Do not conflate workspace trust, content integrity, publisher identity, and execution authority.

## F-05: Skill Lifecycle Qualification

Previous hypothesis:

The current skill system lacks an integrated qualification, revocation, and regression lifecycle.

Inspect existing capabilities for:

- Version management.
- Dependency tracking.
- Qualification status.
- Automated skill testing.
- Compatibility checks.
- Change detection.
- Regression obligations.
- Revocation.
- Rollback.
- Evidence retention.
- Resume compatibility.

Identify which capabilities already exist and could be reused.

Explicitly distinguish a missing mechanism from a mechanism that exists but has not been integrated with skills.

# 4. Additional Security and Reliability Investigation

The audit must go beyond the five previous findings.

## 4.1 Authorization composition

Determine the effective authority model across:

- Operator/session grants.
- Full-access mode.
- Review mode.
- Read-only mode.
- Workspace trust.
- Agent roles.
- Subagents.
- Capability registry.
- Resource confinement.
- MCP integrations.
- Plugins.
- Shell execution.
- Skill activation.

Identify precedence rules and contradictory configurations.

Verify whether authorization is evaluated against normalized tool arguments at the point of execution.

Investigate whether tool arguments can change after approval or admission.

Test whether authorization can be bypassed through alternative tools that produce equivalent side effects.

Particular attention must be given to shell execution, because shell commands can perform operations that are not represented by a simple filesystem capability.

## 4.2 Trust-boundary analysis

Identify all transitions where lower-trust material enters higher-trust processing.

Examples include:

- Skill descriptions entering the system prompt.
- Skill bodies entering model context.
- Tool outputs entering subsequent model requests.
- Retrieved documentation becoming execution guidance.
- MCP descriptions becoming callable tools.
- Subagent outputs influencing the parent agent.

Determine whether sanitization, provenance labeling, and authorization enforcement remain distinct.

Do not treat prompt sanitization as an execution security boundary.

## 4.3 Fail-open behavior

Inspect handling of:

- Missing policy configuration.
- Invalid configuration.
- Unknown capabilities.
- Failed authorization hooks.
- Unavailable approval handlers.
- Corrupted skill metadata.
- Unavailable skill files.
- Missing receipts.
- Interrupted persistence.
- Recovery using obsolete authority.
- Unregistered or dynamically discovered tools.

Classify observed behavior as fail-open, fail-closed, degraded, or explicitly operator-authorized.

Assess impact according to actual deployment modes rather than assuming all default behavior is a security defect.

## 4.4 Evidence integrity

Investigate whether the system can reconstruct:

- The selected skill.
- Its exact instructions.
- Its authorization context.
- Its execution identity.
- Every tool invocation.
- Every admission decision.
- Every approval.
- Resource mutations.
- Verification results.
- Recovery events.
- Final task disposition.

Determine which records are durable, which are ephemeral, and which are merely logged.

Identify redaction requirements so stronger evidence capture does not inadvertently persist secrets.

# 6. Controlled Adversarial Experiments

Design and execute isolated experiments to test the actual enforcement boundaries.

At minimum, investigate:

| ID | Scenario | Required observation |
|---|---|---|
| ADV-01 | Skill requests unauthorized capability | Admission and execution behavior |
| ADV-02 | Skill requests out-of-scope filesystem access | Resource confinement behavior |
| ADV-03 | Skill attempts unauthorized shell side effect | Whether the shell path bypasses intended restrictions |
| ADV-04 | Skill instructions attempt authority escalation | Model behavior versus runtime enforcement |
| ADV-05 | Skill source modified after activation | Content identity and execution continuity |
| ADV-06 | Skill symlink target replaced | Trust and integrity behavior |
| ADV-07 | Skill delegated to a subagent | Authority inheritance and attribution |
| ADV-08 | Skill execution interrupted and resumed | Persistence and authority restoration |
| ADV-09 | Skill revoked during a task | Revocation and continuation behavior |
| ADV-10 | Malicious tool output influences skill execution | Injection containment and tool authorization |
| ADV-11 | MCP/plugin produces equivalent unauthorized side effect | Consistency across execution paths |
| ADV-12 | Approval granted for one argument set, then arguments changed | Approval-to-execution binding |

Where the requested security property does not currently exist, document the experiment as a baseline characterization rather than automatically reporting a test failure.

Use temporary fixtures and disposable resources.

Do not direct destructive tests against real infrastructure or credentials.

Record negative results and unexpected behavior unaltered.
