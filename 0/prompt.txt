**Blockers**

1. **`eval/t3.mjs:90-98` (driver), deferred steering corrupts the probe.**
   - The sidecar answers a steer that arrives while the turn is finishing with `deferred`. It then starts a follow-up turn with no idle state (`sidecar.ts:387-390`), and that turn emits its own `turn.result`.
   - The driver treats the first `turn.result` as the objective's and sends the probe immediately. The sidecar rejects it with `BUSY` (`sidecar.ts:316-320`).
   - The follow-up's own `turn.result` then arrives in `probe` phase and is taken as the probe result. The follow-up's `assistant.delta` text becomes `probeText`.
   - The outcome is `probeUnanswered`, a gate FAIL. This is fail-closed, but it makes a normal steering race fail the workload. Any steer sent near the end of the turn can trigger it.
   - Fix: after `turn.result`, if any steer ack is `deferred` and not yet followed by `applied` and its `turn.result`, wait for that result. Also retry the probe on `BUSY`. Count `steps` and the objective's `turn.result` from the first turn only.

2. **`eval/t3.mjs:176`, false-absence can be gamed or measured on a mutated workspace.**
   - Answering "present" for every fact gives `falseAbsences = 0` and `falsePresence` is not gated. `eval/T3.md` says so explicitly.
   - The probe turn has tools and `--yes`, so the agent can create or delete the fact files while answering. `exists` is read after the probe. The probe also lets the agent re-inspect the filesystem, so it tests honesty, not memory across compactions.
   - Fix:
     - Record `exists` for each fact, and the constraint inputs, when the objective's `turn.result` arrives, before the probe is sent.
     - Gate `falsePresence` as well, or make every fact set include mandatory absent facts and require a minimum correct-absent rate.
     - State plainly in `eval/T3.md` that the probe re-inspects.

3. **`eval/score.mjs`, the gate does not enforce the 8×5 shape.**
   - With a single eligible run, `ineligible === 0`, `falseAbsences === 0` and `steeringRate &gt;= 0.95` yield PASS. REQ-QUAL-109 needs 8 tasks × 5 runs.
   - Fix: require distinct T3 task ids &gt;= 8 and &gt;= 5 runs each (or a `--expect-tasks`/`--expect-runs` parameter recorded in the manifest), otherwise `gate = FAIL`.
   - Also, `steeringItems` excludes records with no `t3` result. That is fail-closed only because the ineligible count already fails the gate. Use the task's declared steering count, so the printed rate cannot read as more than the gate truly measures.
