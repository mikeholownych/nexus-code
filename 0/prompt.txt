### One more issue: completion semantics

I would also be careful with the proposed deterministic reconciliation rules:

> CHANGE = non-empty diff in declared scope + verifier not regressed.  
> REPORT/VERDICT = final report artifact exists. :chatgpt-content-reference{index="7"}

That's useful as an **initial experimental definition**, but I wouldn't canonize it as Nexus completion semantics.

A non-empty diff establishes that a change artifact exists. It doesn't necessarily establish that the requested change exists. Likewise, existence of a report file doesn't necessarily establish that the requested report was produced.

We have intentionally relaxed **correctness**, not the identity of the deliverable.

For example, if the request is “add `--foo` to command X” and Nexus changes an unrelated README, a non-empty in-scope-ish diff should not become COMPLETED simply because tests don't regress.

The report actually recognizes this tension when it says a wrong but non-empty fix may count as COMPLETED during this phase. :chatgpt-content-reference{index="8"} I think that goes slightly too far.

Our distinction should remain:

**mediocre/wrong implementation of the requested deliverable** can count as completion for this phase.

**different deliverable** cannot.

We don't need sophisticated semantic correctness checking yet, but the spike should preserve that distinction rather than designing it away.
