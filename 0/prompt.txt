CONTEXT

Nexus is approaching the point where it is intended to be dogfooded for real
engineering work using a local inference appliance.

The inference service itself has undergone substantial qualification. This task is
NOT an inference benchmark or inference-host review.

The question is now whether Nexus, as the client/orchestration/product layer, is
coherent, reliable, observable, recoverable, and usable enough for sustained real
engineering sessions.

A recent example of the kind of issue that matters:

The REPL could instantiate and successfully execute one agent run, but afterward
silently ceased being useful for another run. The primitive worked, but the
interactive lifecycle did not support sustained use.

Another class of behavior we care about:

A protected operation encounters an unexpected repository HEAD. Stopping the
protected mutation may be correct, but if safe read-only investigation can determine
whether the discrepancy is relevant, the desired behavior is not necessarily to
terminate the entire engineering objective immediately.

Containment should constrain unsafe action. It should not unnecessarily terminate
safe investigation or recovery.

These are examples only. Do not anchor the assessment around them.

ENGINEERING PHILOSOPHY

Use these principles when evaluating the implementation:

- Distrust by Default.
- Trust but Verify.
- Evidence Changes What We Know.

A baseline is a known state supported by the evidence available at that time.
Engineering progress is:

  establish baseline
      →
  act on current knowledge
      →
  test assumptions
      →
  push boundaries
      →
  observe consequences
      →
  update knowledge
      →
  establish a stronger baseline

Prior evidence does not become invalid merely because the system evolves.
Its applicability may change when relevant state changes.

Tests are evidence instruments, not the purpose of the product.

A PASS is not automatically good engineering.
A FAIL is not automatically bad engineering.

The objective is to determine whether the product actually does what it is intended
to do, within a deliberately understood operating envelope.

Unexpected does not automatically mean invalid.
Unknown does not automatically mean unauthorized.
Novel does not automatically mean unsafe.

Fail closed where proceeding could violate a protected invariant.
Elsewhere, prefer bounded investigation, recovery, reassessment, and continued
progress where evidence and authority permit.

A failed precondition should stop the operation whose safety depends upon it.
It should not automatically terminate the larger objective when safe,
authorized investigation can resolve the uncertainty.

Agents advise.
Evidence constrains.
Experiments discriminate.
The operator decides.
Decisions remain revisable.

DOGFOODING READINESS

Evaluate whether Nexus currently supports sustained interactive engineering rather
than isolated successful invocations.

Specifically investigate:

1. INTERACTION LIFECYCLE

Can an operator:

- start Nexus
- execute multiple tasks in one session
- inspect progress
- recover from an invocation failure
- cancel or interrupt appropriately
- continue after tool/validation/model errors
- understand whether Nexus is working, waiting, blocked, failed, or finished
- deliberately exit

Look for silent termination, dead states, orphan state, stale state, blocking input,
lost input, lifecycle ambiguity, and restart-only recovery.

2. STATE AND TRAJECTORY LEGIBILITY

Determine whether the operator can understand:

- current objective
- active agent
- selected capability/model
- current operation
- tool activity
- validation activity
- dependencies
- unresolved uncertainty
- evidence acquired
- reason for reassessment
- reason for stop/block
- completion status

Distinguish information that exists internally from information actually projected
to the operator.

3. TUI / HUMAN INTERACTION

Assess the current terminal interaction architecture.

Determine:

- whether a TUI framework is already present
- current rendering/event architecture
- whether rendering can block execution
- whether input can be lost or blocked during model/tool activity
- whether streaming output is handled coherently
- whether long sessions degrade interaction
- whether state is structured or flattened into transcript/log text
- whether resize, redraw, scrolling, focus, cancellation and exit are handled
- whether multiple concurrent agents/tasks can be represented
- whether TUI state is a projection of canonical Nexus state or risks becoming a
  second source of truth

Do NOT optimize for visual decoration.

Evaluate whether a performant, state-aware TUI would materially reduce operator
comprehension and decision latency.

4. FAILURE AND RECOVERY

Trace representative failure paths:

- inference request failure
- malformed model output
- tool failure
- validator failure
- changed repository state
- stale evidence
- dependency failure
- interrupted execution
- provider unavailable
- unexpected but potentially recoverable state

Determine whether Nexus distinguishes:

  OPERATION_BLOCKED
  INVESTIGATION_REQUIRED
  REQUALIFICATION_REQUIRED
  OPERATOR_DECISION_REQUIRED
  EXTERNAL_REMEDIATION_REQUIRED

Look specifically for places where:
