# Nexus Code v1.3.1 implementation plan for reviewed workflows

**Status:** Draft for scope review. **Target:** `release/v1.3.1`. **Source baseline:** `18066d24e3902f2a635b12dcd8c9c02fe56d6610`, the local `origin/release/v1.3.1` tracking ref inspected for this draft. **Input:** `docs/superpowers/specs/2026-11-27-Nexus_Code_Claude_Features_Implementation_Spec.md` (provided in the owner's checkout).

This plan extends [the v1.3.1 release plan](PLAN.md). Keep its WP-131-01 through WP-131-11 and G-1 through G-9 obligations. Target verification, reviewed planning, and opt-in knowledge suggestions for v1.3.1. Release scope expansion and any scope reduction remain owner decisions. Focused advice and simplification receive a reuse assessment after the core work. Side questions, interval polling, unconstrained agent chat, and new skill, hook, worktree, or scheduling systems remain deferred under this spec. Existing release packages for hooks and skills retain their own acceptance criteria.

## 3. CF-00 baseline and contract checklist

- Trace manual batch, team, objective iteration, operator verification, unattended driver, and integration entry points to their completion decisions. Identify exact validation, approval, usage accounting, evidence persistence, resume and export calls. Characterize which consumers need changes. Preserve legacy behavior unless an existing gate is shown to misreport completion.
- Trace knowledge writes from operator, model, plugin and protocol paths, and reads from prompt construction, context inventory, export and audit. Identify repository and worktree identity sources and existing private-state, retention and redaction facilities.
- Resolve limits for graph size, dependencies, draft and review output, inference budgets, check count, elapsed time, output capture and knowledge retention using existing product limits where applicable. Set deterministic tests at the limit and immediately beyond.
- Record the authority for check selection, immutable verifier inputs, normalization and digest versioning, final candidate identity, policy changes on resume, output truncation, conditions, and waiver semantics. Inspect existing operator approval/evidence for exact-candidate waivers. If coverage is absent, reuse that authority with a scoped receipt or keep waivers disabled and record the resulting spec gap.
- Treat stored input and model output as untrusted data at every boundary. Freeze compatibility fixtures for existing batch files, operation records, integration evidence and knowledge entries. Include an unknown-version and partial-record case for each new durable record.

## 4. CF-C1 and CF-C2 verification lifecycle (§6)

1. Normalize required, conditional and advisory check definitions with stable IDs and purposes, approved verifier identity or command, canonical worktree-relative directory and scope, applicable limits, expected outcome and failure handling. Pin trusted evaluator inputs through the existing candidate/evaluator mechanisms. Evaluate conditional applicability from accepted deterministic criteria, persist its basis, and block on unknown applicability for a potentially required check. Record skipped checks explicitly. A new check contract becomes mandatory wherever declared or required by policy.
2. Reuse existing executors and sandbox/approval/command policy. Match check definition digest, verification run, worktree identity and candidate identity at execution and consumption. Include the base and applicable tracked, untracked and material dependency inputs through existing candidate mechanisms. Use a stable isolated snapshot or an equivalent validated execution boundary. Verify identity again after execution and immediately before the gated transition. Invalidation includes relevant check configuration and dependency changes. Unit receipts cannot certify the combined integration tree.
3. Persist run intent before dispatch and a finalized receipt after capture. Record check and candidate bindings, result, timestamps, process exit information, redaction and truncation flags, digest and bounded output reference. Publish success only after required evidence is durable and readable. Coordinate state and receipt writes under existing ownership/locking. Retain attempt history and make replay idempotent. A crash before durable result, malformed receipt, missing evidence, or interrupted external effect enters reconciliation or blocks. Rerun only when existing approval and retry rules permit it.
4. Centralize the required-check decision at unit acceptance, integrated candidate acceptance and terminal completion. Apply it on resume, retries and immediately before merge/publication under existing runner and Git guards. Required failure, timeout, cancellation, truncation, unavailable verifier, missing/invalid receipt, stale binding or persistence failure blocks the affected candidate. Keep advisory failures visible. Operator waivers, where supported, bind actor, reason, accepted scope, check and exact candidate, and appear separately from passes. Hook/plugin responses and model output cannot issue or alter receipts or grant authority.
5. Expose required and applicable checks before execution and show attempt history, failing output references, invalidation reasons and waiver details in status/results, session output and redacted audit/export. Preserve legacy receipt readability. A legacy receipt with insufficient binding cannot satisfy the new contract. Reuse historical state migration and interrupted-effect reconciliation with WP-131-02/06.

**Exit evidence:** Valid receipts allow completion at the exact candidate. Failures at dispatch, capture, storage, restart and integration all preserve a blocked or unknown result. Mutating the tree, evaluator inputs or accepted check definition after success invalidates the previous evidence. A new integrated tree requires its own applicable checks. Cancellation stops the owned process and leaves an accurate durable outcome. Existing manual verifier and batch paths retain tested behavior.

## 5. CF-A1 and CF-A2 reviewed objective planning (§4)

1. Extend the shared batch workflow with proposal, inspect/edit and explicit accept/run actions. Proposed syntax is `/batch plan <objective>`, `/batch plan show <draft-id>` and `/batch plan accept <draft-id> <digest>`, with validated import/export for editing. Resolve parsing and existing reserved-name collisions in CF-00. Preserve `/batch <spec-file>`, explicit run/validate, and lifecycle actions. Keep generated drafts recognizable and reject unaccepted draft envelopes at executable entry points, including direct operation input and resume. Loading and explicitly running a legacy operator-authored spec keeps its current semantics.
2. Generate a strict bounded proposal through an existing provider-neutral inference path with cancellation, context limits and usage accounting. Use only explicitly selected or pre-collected, policy-filtered context. The planner receives no tool dispatch. It launches no check, worktree, executable operation, install or external action. Treat resource requests as eligibility requirements, with endpoints, credentials and policy drawn from trusted config. Persist only normalized proposals in the requested private draft facility and record actual resource and fallback.
3. Validate strict shape and bound counts before normalization. Reuse batch and operation validation for IDs, edges and cycles. Each unit carries title, stable ID, objective, role, required/advisory status, dependencies, read/write class, scope, isolation, resources, criteria, checks/evidence and output/handoff references. The graph carries final criteria, risks, assumptions and unresolved questions. Canonicalize paths and reject workspace escapes, ambiguous scopes and unsafe parallel writes. Order overlapping writes explicitly. Use isolated worktrees for independent concurrent writes and explicit handoffs for their outputs. A required unit cannot depend implicitly on an optional one. If criteria or dependencies remain ambiguous, return clarification with a reason and no runnable plan.
4. Use qualified, context-fitting local resources first and policy-permitted cloud fallback only through existing routing. Record actual selected model, resource identity, fallback reason and policy decision. When independent review is required, enforce distinct qualified identity under existing semantics, including rejecting aliases that do not satisfy independence. Missing eligible reviewers block acceptance where required. Store findings and review provenance against the reviewed digest. Material edits invalidate that review. Review identifies missing dependencies, parallel write risks and weak or untestable criteria. Review can never approve.
5. Render the normalized graph with all checks, scopes, assumptions and blocking findings. Bind explicit operator approval to the displayed digest, repository/worktree and relevant base identity. Under existing operation admission locking, revalidate trusted configuration, eligibility, paths and policy, and atomically associate the accepted snapshot with one durable operation. Double submissions and restart recover that operation without duplicating execution. Changed plan bytes or assumptions that invalidate the binding require redisplay and acceptance. Resume loads the immutable snapshot and rechecks current policy without regeneration or silent changes. Cancellation and restart use existing scheduler and Git semantics. Optional outcomes remain visible and cannot satisfy required dependencies or acceptance.

**Exit evidence:** The same normalized snapshot is shown, accepted, persisted and executed. Invalid inputs create no operation or worktree. Proposed or edited unaccepted drafts cannot enter execution through any supported route. Test submit/restart races, provider failure, cancellation, reviewer scarcity and local/cloud policy decisions. Required units and CF-C2 verifications control completion.

## 6. CF-B1 and CF-B2 evidence-linked knowledge (§5)

1. Add opt-in extraction after terminal work or on an explicit operator request. A bounded no-tool call proposes conventions, architecture, dependency facts, troubleshooting findings or rules from selected records. Keep model suggestions in private candidate storage. Review compares evidence, source class and conflicting claims. Record conflicts and uncertainty explicitly. Suggestions do not alter prompt context or authorization.
2. Persist candidate → reviewed → promoted, rejected or expired, with explicit deletion and duplicate suppression keyed by repository, proposal digest and evidence revision. Allow rejection/expiry from pending review. Review and promotion are operator actions. Promotion uses the existing operator-only write path and records the accepted wording and provenance as operator-reviewed unverified. Make transitions atomic or recoverable under store ownership. Retain bounded tombstones after deletion or expiry to prevent resurfacing on identical evidence. A new evidence revision must be visible when a proposal recurs.
3. Bind repository/workspace/worktree scope and relevant paths to session, operation, unit, candidate/commit and evidence IDs as available. Preserve explicit source classes for operator, model, tool and verified evidence, creation/update time, validation status, freshness, invalidation predicates, retention and content/evidence digests. Resolve references through operator-accessible saved records, apply redaction before persistence and export, and make secret-bearing, personal or protected content ineligible for promotion. Recheck redaction and references at promotion. Missing provenance defaults to rejection or review-only unverified under explicit policy. An evidence reference does not verify the extracted claim.
4. On reads and transitions, recompute freshness when repository/worktree scope, relevant paths, dependency/version inputs or candidate validity change. Record stale or unknown with a reason. Exclude cross-scope and stale entries from active injection. Surface unknown entries explicitly and apply the accepted prompt policy. Keep legacy entries marked unverified without fabricating provenance. Expose lifecycle actions and provenance in operator views, context inventory, session export and audit. Reflect retention or deletion in source availability and never present a dangling reference as current evidence.

**Exit evidence:** Direct model or extension calls cannot promote. Suggestions never mutate operator knowledge. Review, promotion, rejection, expiry, deletion and stale marking survive restart. Test conflicting evidence, tampered/missing provenance, secret handling, concurrent review, repository/worktree separation, source pruning, and legacy entries. Promoted rules carry no tool authority.

## 7. CF-D secondary quality workflows (§7)

- Compare a bounded read-only consultation using the existing independent reviewer role against a dedicated command on selected task, diff, plan and failure inputs. Score actionable findings with references, correctness, uncertainty and false positives against independent adjudication. Require actual distinct qualified resources for independent consultations. A consultation has no approval, edit or completion authority. If the existing role meets the acceptance criteria, document the invocation and close the slice through reuse.
- After functional acceptance, trial a proposal-only simplification skill on duplication, complexity and unnecessary abstraction. Require file references and a behavior-preserving rationale. Evaluate churn, actionable findings and regression risk. Any operator-approved follow-up is ordinary scoped implementation, creates a changed candidate and re-runs applicable required checks. Preserve required behavior and test coverage.

## 9. Release and reporting (§9–10)

- For each TypeScript slice run `npm --prefix cli run build` and affected tests. For a focused test, run `cd cli && HOME=$(mktemp -d) node --import tsx --test test/<name>.test.ts`. Use a throwaway home and matching XDG paths for test and probe runs. Use Node 22 and 24 for process/runner changes. Build Rust with an isolated target directory when affected. Use a snapshot and the `SUITE` claim for full test runs. Take `GATEWAY` before any inference run. Keep secrets out of artifacts and retain failed run records.
- Run `make test-ci` at the integrated candidate and the applicable protocol, hostile denial, unattended recovery, audit, docs and packaging gates from the parent plan. Required CI conclusions are successful for `test-matrix (22)`, `test-matrix (24)` and `linux-x86_64` on the current PR head and merge candidate as appropriate. Serialize same-subsystem merges and verify release branch CI after each one. Record the exact tested SHA and run identifiers. Preserve the owner-controlled merge, version-only stable promotion, tagging and publication process.
- Update command help and targeted manuals with draft/approved states, compatibility, output and retention behavior, operator actions, invalidations and failure examples. Keep docs and machine-readable outputs aligned. Explicitly document disabled or pending capabilities. Record slice evidence under `docs/evidence/v1.3.1/` and aggregate release disposition in `docs/releases/v1.3.1-READINESS.md`.
- The final implementation report lists the baseline and tested SHAs, spec divergences, reuse map, requirements by slice and their disposition, changed files and state/schema changes, exact test/eval commands and results including failures, and links to cancellation/restart, stale-state, resource independence, local-first and verification-binding evidence. Document remaining risks and each release gate as passed, failed, blocked or pending with supporting evidence.
- Keep plan execution unavailable until CF-C2 and CF-A2 are qualified together. Stop release promotion on missing in-scope acceptance evidence or failing required CI. Record an explicit owner disposition for any scope change. Recheck the parent release plan obligations before requesting an RC or a stable tag.
