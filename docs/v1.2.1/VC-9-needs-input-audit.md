# VC-9: headless needs-input audit

Date: 2026-11-18. Base: origin/main `b1b74858` (file:line below are at that commit; the glue added by this change is listed in the last column).
Reference: Anthropic 2026 agentic coding trends report, trend 4 (agents that learn when to ask for help).

A headless run has no operator (`onConfirm` absent). This lists every place it needs a human decision, what happens today, and what this change does about it. Outcomes today: **stalls** = the model gets a plain error and carries on or the turn ends with nothing structured; **guesses** = a decision is made on the operator's behalf. No path ended BLOCKED with a question before this change (`grep needs_input cli/src` found nothing).

The shared shape added: turn `execution=BLOCKED`, `reason=NEEDS_INPUT`, `needsInput = { id, kind, prompt, subject, options[approve|decline] }` (`cli/src/core/needs_input.ts`, `cli/src/core/turn.ts`), and `nexus run --resume <task> --answer <id>=approve|decline`.

## Behaviour notes

- A question stops the turn at the call that raised it; later calls in the same batch are reported as not executed.
- An answer is bound to the decision: the id is a digest of the tool and arguments (1, 2), the path and tool (3), or the command and script digest (4-6). A different action gets a different id and asks again.
- `approve` covers the one action. `decline` is recorded for the run and the action is refused without asking again.
- Exit code stays 1 for BLOCKED; machine consumers read `turn.reason` and `turn.needsInput` (`--json`, stream-json `result`).
- Answers live in the invoking process. Resuming without `--answer` asks again.

## Rows 7 and 8, done 2026-11-21 (owner gate decision for v1.2.2)

Both were left as design decisions. The owner made them required for v1.2.2; the decisions taken and what was built:

**8, blocked requirement.** Decision: the contract changes for `nexus run` only (`config.surface === "headless"`, top-level agent). There the turn ends `BLOCKED / NOT_ESTABLISHED / NEEDS_INPUT` with `needsInput.kind = "blocked_requirement"` instead of `COMPLETED / NOT_ESTABLISHED / REQUIREMENTS_INCOMPLETE`; the durable task status therefore becomes `failed` instead of `completed`, and the exit code stays 1. The REPL, the sidecar, operations and library callers keep `REQUIREMENTS_INCOMPLETE` (an operator or a client is there to read the blocker), and so do requirements that are only still open, or descoped and awaiting acceptance. The answer is free text: the question's only option is `reply`, given as `--answer <id>=reply:<text>` (2000 characters at most, refused rather than cut). The id is a digest of the requirement id and the stated reason. The resumed run passes the reply to the model with an instruction to reopen the requirement or record it descoped; the harness does not change the requirement itself, so a model that leaves it blocked for the same reason gets the same question again. Several blocked requirements: the first is `needsInput`, the others `furtherNeedsInput`. Code: `buildBlockedRequirementQuestion`, `parseOperatorAnswers`, `replyNote` (`cli/src/core/needs_input.ts`), `buildTurnResultImpl` (`cli/src/core/run_turn.ts`). Tests: `cli/test/vc9_blocked_requirement.test.ts`.

**7, steering conflict.** Decisions: (a) an `unresolved` conflict may be decided after the fact (`resolveSteeringConflict` accepts `unresolved` as well as `pending`; nothing was applied in the meantime, and a decided conflict is never decided twice); (b) the sidecar delivers the BLOCKED turn as an ordinary `turn.result` carrying `needsInput`, and gains one command, `answer` (`question`, `option`), for clients with no live approval prompt; resending the steering and deciding at the prompt still works. Behaviour: a turn that would otherwise report completion, during which a conflict ended undecided (nobody could be asked, or the turn closed first), ends `BLOCKED / NEEDS_INPUT` with `kind = "steering_conflict"`, options approve and decline, id bound to the steering message. An interrupted or failed turn keeps its own result. At the next turn's start an answer is applied (approve: the requirements are descoped as accepted and the steering is queued, once; decline: nothing changes) and conflicts without an answer are marked `carried`, so only the turn that left a conflict undecided reports it. Code: `buildSteeringConflictQuestion`, `carryUnresolvedConflicts` (`cli/src/core/objective.ts`), `cli/src/protocol.ts`, `cli/src/sidecar.ts`. Tests: `cli/test/vc9_steering_conflict.test.ts`.

Limits, stated plainly: answers live in the invoking process (as for rows 1 to 6); a new objective starts a new ledger, so an old conflict can no longer be answered; the Rust TUI shows the BLOCKED turn but has no key for `answer` (resend the steering there); a descoped requirement awaiting acceptance in a headless run is still `REQUIREMENTS_INCOMPLETE`, not a question.

## Subagents (row 14)

A headless in-turn subagent (`spawn_subagent`, depth 1) that needs a decision records the question on itself (`subagentQuestions`), stops at the call that raised it (it does not wait, take the decision or route around it) and returns it in `SubagentResult.needsInput`. The parent records it through `acceptSubagentQuestions`: the first becomes `TurnResult.needsInput`; further distinct questions go to `TurnResult.furtherNeedsInput` in order, never overwriting the first; a parent-originated question already recorded stays first. The turn ends BLOCKED / NEEDS_INPUT as for any question. On `--answer`, the parent hands its answers to each subagent it spawns (`setOperatorAnswers`), so the re-spawned child meets the same id and proceeds (approve) or is refused without asking (decline). Interactive runs pass the operator's confirm handler to the child as before and record nothing.

Limits, stated plainly: the child is not resumed, it is spawned again from the model's next `spawn_subagent` call, so work it did before the question is redone (workspace changes it already made stay); resume depends on the model delegating the same way again. Questions are listed only when one call raised several (a batch stops at the first recorded question, so a second `spawn_subagent` in the same batch does not run). Subagents cannot spawn subagents, so there is no deeper level. Tests: `cli/test/vc9_subagent_needs_input.test.ts`, which also covers the requirement-verifier approval (`runRequirementVerifier`) on its own.
