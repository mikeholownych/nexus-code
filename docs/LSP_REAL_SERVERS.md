# Real language servers (CS-6)

`cli/src/lsp.ts` (the `lsp_diagnostics`, `lsp_hover` and `lsp_definition` tools) is tested in the ordinary suite against `cli/test/fixtures/fake_lsp_server.mjs`. `cli/test/lsp_real_servers.test.ts` also runs the product's own `LspBridgeManager` against real servers on fixture projects written to a temporary directory. Navigation cases use a three-source-file import/re-export chain (or equivalent package-level call chain) and require hover and definition to resolve through that project. The `lsp-real-servers` workflow runs it weekly (Monday 04:17 UTC) and on demand. It is not a required check.

Per server the test asserts that a file with one deliberate error yields `status: "ok"` with an error diagnostic whose message names it; a clean file yields `status: "ok"` with an empty list (a published report, which is not `unavailable`); and a manager whose server cannot start yields `unavailable`. The extended lifecycle test also verifies trust and read-only refusal before launch, diagnostics and incremental fixes in a 64-source-file fixture, and that a killed server does not leave stale clean diagnostics visible. It then starts a fresh manager and confirms the changed workspace can be diagnosed again.

| Server | Command the product starts | Fixture error | Needed to run |
|---|---|---|---|
| typescript | `typescript-language-server --stdio` | `const n: number = "..."` under `strict` | `typescript`, `typescript-language-server` |
| python | `pyright-langserver --stdio` | `x: int = "..."` | `pyright` |
| rust | `rust-analyzer` | `let x: i32 = "..."` in a Cargo project | `rust-analyzer` |
| go | `gopls` | `var x int = "..."` in a module | `gopls` |

## Skip versus fail

The server is looked up on the PATH the product gives a language server (`buildLspEnvironment`: absolute entries only, none inside the workspace), and where the server has a `--version` mode it is run under that same environment. A server that is absent, or present but not runnable there, SKIPS with the reason. `NEXUS_LSP_REQUIRE` turns that into a failure: `1` (or `all`) requires every server, a comma list (`typescript,python`) requires those. Ids: `typescript`, `python`, `rust`, `go`. The workflow sets `typescript,python`; rust-analyzer and gopls are best-effort installs there, so their cases run when the install worked and skip otherwise.

```sh
npm i -g typescript typescript-language-server pyright   # or put their bin directory on PATH
cd cli && node scripts/run_tests.mjs test/lsp_real_servers.test.ts
NEXUS_LSP_REQUIRE=1 node scripts/run_tests.mjs test/lsp_real_servers.test.ts   # missing server = failure
```

The suite runs under a throwaway HOME, so a tool installed only for the current user (`pip install --user`, `~/.cargo/bin` reached through the real HOME) is invisible. The workflow installs with `npm -g`, and sets `RUSTUP_HOME` and `CARGO_HOME` for the rustup proxy. The real-server workflow pins Node 22.22.1, Go 1.27.4, Rust 1.95.0 with its rust-analyzer component, gopls v0.24.0, TypeScript 5.6.3, typescript-language-server 4.3.4, and pyright 1.1.390. All four servers are required; an installation or startup failure fails the run.

## What it found

The first real run showed the default launch commands for TypeScript, JavaScript and Python were missing `--stdio`; both servers print a usage error and exit without it, so `lsp_diagnostics` for those files was always `unavailable` in practice. Fixed in `getServerForFile`; a test that needs no server pins the arguments.

## What it does not cover

- The trust and sandbox gates with a real server (they are tested with the fake server; a gated manager never starts one).
- A larger real project: navigation uses three source files, but there is no large workspace-wide diagnostics fixture, incremental-edit sequence, or server crash/restart scenario.
- Server versions other than the pinned ones (typescript 5.6.3, typescript-language-server 4.3.4, pyright 1.1.390; gopls (`@latest`: v0.16.2 stopped building on a newer runner Go on 2026-11-18) and the runner's rust-analyzer are unpinned).
- Hosted-runner result (manual run 44323291710 on `3732d911`, 2026-11-18): **typescript-language-server, pyright and gopls passed** (a deliberate error reported, a clean file a real empty report, a broken server `unavailable`), which also confirms on real servers that the default launch needs `--stdio`. **rust-analyzer failed**: the product reported "not installed or failed to start" although the rustup proxy answered `--version` in the test's probe. The cause is not diagnosed (it needs a host with the rust-analyzer component to reproduce); the Rust case therefore runs as a `todo` (reported, not failing the job) unless `NEXUS_LSP_REQUIRE` names it, and the workflow requires `typescript,python,go`. A manual run of that change on its branch (run 44323915622) completed successfully: 5 pass, 0 fail, 1 todo (Rust).
- **rust-analyzer (2026-11-18, reproduced locally in an isolated rustup home):** two separate problems, both fixed. (1) *Setup:* the workflow added the component to the toolchain pinned by the repository's `rust-toolchain.toml`, but the product launches the server in a fixture directory outside the repository, where rustup uses the **default** toolchain, which had no rust-analyzer ("failed to start" in about 150 ms); the test's `--version` probe ran from the repository and could not see it. The probe now runs in the fixture directory and the workflow adds the component from a directory with no override. (2) *Product behaviour:* `lsp_diagnostics` used to return on the first `publishDiagnostics`, which rust-analyzer sends **empty** before it has loaded the Cargo project and analysed types, so a file with a type error was reported clean. A server can now be marked `awaitProgress` (rust-analyzer is, in the built-in table): the client advertises `window.workDoneProgress`, answers the server's own requests (`window/workDoneProgress/create`, `workspace/configuration`, ...), tracks `$/progress`, and after the first publish waits until the server's progress has ended and been quiet for 1.5 s (or, if it reports none, a 4 s grace), always within the caller's timeout. Server-free tests (`lsp_progress.test.ts`) pin it with a fake staged server (four mutations each fail a test); the real-server case passes locally against rust-analyzer 1.100.0 (about 13 s for a first call on a tiny crate).
- **Hosted validation of this change:** manual run 44334778543 on the branch (2026-11-18): typescript-language-server, pyright, gopls and rust-analyzer all pass (6 tests, 0 fail, 0 todo; Rust about 18 s). Earlier runs of the same workflow found the setup mismatch (44323291710), the empty-first-publish behaviour (44332636397) and a `gopls@v0.16.2` build break on the runner's newer Go (now `@latest`).
- **Three-file navigation extension:** hosted run [44606102675](https://github.com/mikeholownych/nexus-code/actions/runs/44606102675) on commit `99c6049f` (2026-11-19) passed all 10 tests with `NEXUS_LSP_REQUIRE=typescript,python,go,rust`: all four real servers passed the diagnostics and navigation cases, with 0 failures, skips, or todos. This is a small three-source-file chain, not evidence for large-project behavior.
- **Hover and definition (CS-6 follow-up):** each real server is asked, through the product, to hover and go to the definition through a three-source-file project (positions are 1-based, as `lsp_hover` and `lsp_definition` take them); the call is retried until the case timeout because servers answer only after analysis, and the definition must point into the defining file. This checks a small import/re-export chain; it does not establish behavior on large projects.
- The lifecycle case runs against all four pinned real servers. Its generated project has 64 source files; it is a bounded scale check, not a performance benchmark or evidence for arbitrarily large repositories. Crash recovery is checked by starting a fresh `LspBridgeManager`; automatic restart within an already-running manager is not asserted.
- **Cost and limit:** a first Rust diagnostics call on a large crate can take as long as the project load, and is bounded by the caller's timeout, after which the existing "published no diagnostics" `unavailable` applies. Later calls return as soon as progress is quiet. A change to an already-open file is not waited on separately: the latest published list is returned.
