# Nexus Code v1.0.0 Release Notes & Migration Guide

**Maturity:** Stable release (v1.0.0).

This release delivers the complete Nexus Code client architecture with comprehensive boundary hardening, process ownership, workspace trust enforcement, and egress protection.

---

## 1. Security & Untrusted Input Boundary Hardening (PLAN-03)

### Workspace `.env` Isolation & Allowlist (REQ-SEC-110)
- **Problem addressed (PRV-01):** Workspace `.env` files previously loaded with `override: true`, allowing untrusted repositories to manipulate `NODE_TLS_REJECT_UNAUTHORIZED`, proxy configurations, credential variables, timeouts, and fallback endpoints.
- **New behavior:** Project `.env` files are parsed into an isolated `EffectiveConfig` layer and are **never** assigned to `process.env`.
- **Allowed project keys:**
  - `LOCAL_LLM_ENDPOINT`
  - `LOCAL_LLM_MODEL`
  - `LOCAL_LLM_TASK_CLASS`
  - `NEXUS_CONTEXT_LIMIT`
  - Any key starting with the documented prefix `NEXUS_PROJECT_*`
- **Ignored project keys:** All other environment keys—including `NODE_*`, `*_PROXY`, `HOME`, `PATH`, `SSL_*`, provider credentials (`OPENAI_API_KEY`, etc.), `LOCAL_LLM_API_KEY`, `LOCAL_LLM_TIMEOUT_MS`, and `LOCAL_LLM_FALLBACK_ENDPOINTS`—are ignored with startup notices and flagged in `nexus doctor`.
- **Escape hatch:** For transition during pre-1.0 release evaluation, `NEXUS_LEGACY_PROJECT_ENV=1` is supported as a temporary operator override.

### Migration Guide for Project `.env` Keys

If your project `.env` contains settings that are now ignored, migrate them to your operator configuration:

| Setting in project `.env` | Where to move it |
| :--- | :--- |
| Provider API keys (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, etc.) | `~/.config/nexus/config.env` or shell environment |
| Appliance API key (`LOCAL_LLM_API_KEY`) | `~/.config/nexus/config.env` |
| Proxy settings (`HTTPS_PROXY`, `HTTP_PROXY`, `NO_PROXY`) | Shell profile or `~/.config/nexus/config.env` |
| Custom CA certs (`NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`) | Shell profile or `~/.config/nexus/config.env` |
| TLS settings (`NODE_TLS_REJECT_UNAUTHORIZED`) | Operator shell environment (caution: disables certificate validation) |
| Local LLM timeouts (`LOCAL_LLM_TIMEOUT_MS`) | `~/.config/nexus/config.env` |
| Fallback endpoints (`LOCAL_LLM_FALLBACK_ENDPOINTS`) | `~/.config/nexus/config.env` or CLI `--fallback` |

To inspect which keys in your current workspace are ignored, run:
```bash
nexus doctor
```

### Destination Locality Classification (REQ-SEC-111)
- Locality is derived from parsed IP literals and CIDRs (loopback `127/8`, `::1`; RFC-1918 `10/8`, `172.16/12`, `192.168/16`; CGNAT `100.64/10`; link-local; IPv6 ULA `fc00::/7`).
- Hostnames are treated as external destinations by default unless the host is `localhost`, matches the operator-configured local endpoint, or is explicitly declared in `NEXUS_LOCAL_ORIGINS`.
- DNS resolution is explicitly never used to grant locality (preventing DNS rebinding bypasses).
- Operators running local LAN or Tailscale inference servers can declare them local via:
  ```bash
  # in ~/.config/nexus/config.env or shell environment:
  NEXUS_LOCAL_ORIGINS="gpubox:8000,lan-llm.home"
  ```

### SSRF-Safe Outbound Fetching (REQ-SEC-112)
- `fetch_web` enforces `safeFetch`: DNS resolution pinning, manual redirect handling up to 5 hops (with per-hop IP validation against private/loopback/CGNAT/link-local/ULA CIDRs), and a streaming response body cap of 5 MB.

### Workspace Trust: Skills & Knowledge (REQ-SEC-113, REQ-SEC-114)
- Workspace trust now gates workspace skill directories (`skills/`, `.nexus/skills/`, `.claude/skills/`) and workspace knowledge (`.nexus/knowledge.json`).
- In untrusted workspaces, workspace skills are listed by `/skills` as "untrusted (not loaded)" and cannot be activated via `/skill <name>` or `activate_skill`. Run `nexus trust .` to trust the workspace.
- Injected system prompt blocks from skills and knowledge include explicit provenance metadata: `[source: <path>] [trust: <state>]` (CTX-001).
- Automatic knowledge extraction (`autoExtract`) is disabled by default (DEC-15). It can be enabled with `NEXUS_KNOWLEDGE_AUTOEXTRACT=1`, which issues a notification when new rules are persisted.
- `--read-only` mode never creates `.nexus/` or writes knowledge files.

### Plugin Architecture & EXT-004 Auditing (REQ-SEC-115, REQ-SEC-116, REQ-SEC-117)
- Plugins execute in-process with full user authority. The legacy worker-thread sandbox claim has been removed, and `executeSandboxed` deleted.
- The undocumented foreign plugin directory `~/.config/opencode/plugins` has been removed. Plugins are only loaded from `~/.config/nexus/plugins/`, `~/.nexus/plugins/`, and trusted workspace directories.
- Any plugin middleware rewrite of tool arguments or results is cryptographically recorded with before and after SHA-256 digests in both `~/.nexus/audit.log` and the session flight log (EXT-004).

### Protected Path Hardening (REQ-SEC-118)
- File protection rules now match `.env*` prefixes (e.g. `.env`, `.env.local`, `.env.production`), `id_rsa*`, and `id_ed25519*` case-insensitively across path components and canonical targets resolving symlinks.
- Protection is enforced across all file read, write, and edit tools (`read_file`, `batch_read`, `edit_file`, `patch_file`, `write_file`, etc.). Path protection remains advisory for `run_command`.

### Web Search Honesty (REQ-PRV-108)
- `search_web` returns `success: false` and empty results when no search hits are found (no fabricated results). Its search destination is disclosed on first use and gated by egress disclosure.

## 2. Safe Execution Defaults & Approval Integrity (PLAN-01, DEC-01 Option C)

### Approval Mode Independent of Folder Trust (amended DEC-01)
- **Problem addressed (SEC-01):** Folder trust and tool authority were coupled, making workspace trust silently change the approval posture.
- **New behavior:** Tool permission mode is independent of workspace trust and defaults to `review` in every folder. `--mode auto` selects autonomous writes and command execution while keeping first-use egress approval per origin. `--yes` and `NEXUS_APPROVAL_MODE=auto` select full access and bypass all approval prompts, including egress.
  - **Scripts and CI:** Automated scripts, test runners, and CI environments that must not prompt should pass `--yes` or set `NEXUS_APPROVAL_MODE=auto`.
- **Trusting your own repository:** Run `nexus trust .` (or `nexus trust <path>`) to load project instructions and workspace integrations. Trust does not change tool permission mode.
- **Posture flags:**
  - `--approve` / `--mode review`: Enforces review posture regardless of workspace trust.
  - `--mode auto`: Allows writes and commands without approval; prompts before first egress to each origin.
  - `--yes`: Enables full access, including egress without approval.
  - `--read-only` / `--mode read-only`: Enforces read-only posture (no file writes or mutating commands).

### Startup Posture Banner (REQ-TUI-102)
- At session start, both the interactive REPL and the Rust TUI display an explicit posture banner:
  ```
  mode: review · sandbox: off · workspace: untrusted (nexus trust .)
  ```
- `nexus doctor` outputs the active posture tuple (`mode`, `sandbox`, `trusted`).

### REPL Approval Hardening (REQ-SEC-103)
- Approvals in `InteractiveRepl` use a hardened `[y/N/d/a]` prompt.
- **Lone Enter defaults to No:** Pressing Enter with an empty buffer safely rejects the proposed action (`N`).
- **Input grace period & typing protection:** Input buffered within the first 400 ms of prompt display is discarded to protect against typed-ahead steering input or pastes answering the prompt by accident.
- **Approve-all confirmation:** Selecting `a` (approve all later actions) prompts for explicit confirmation: `Type 'all' to confirm approving all later actions for this session:`.

### TUI Approval Panel Alignment & Narrow Terminal Polish (TUI-09, TUI-10)
- **Spatial arrow key alignment (TUI-09):** Approval panel buttons are laid out horizontally: `Approve` (left) · `All later` (center) · `Deny` (right). Left arrow (`←`) focuses `Approve` on the left, and Right arrow (`→`) focuses `Deny` on the right.
- **Narrow terminal compact hints (TUI-10):** Under 60 columns (e.g. 40×14 terminal), approval panel instructions switch to compact short-form hints (e.g. `←→ choose, enter · esc denies`), ensuring all directions fit without line wrapping or truncation.

### Read-Only HOME Masking & Path Confinement (REQ-SEC-104)
- When running in `--read-only` mode with `bwrap` container sandboxing, `$HOME` is mounted with `--tmpfs $HOME`, completely masking `~/.ssh`, shell profiles, and user dotfiles from `run_command`.
- Without `bwrap`, read-only command execution enforces path confinement: commands referencing `~`, `$HOME`, environment variable expansions (`$`), absolute paths outside the workspace, or escaping `..` sequences are refused.

### Direct Argv Sandbox Spawning (REQ-SEC-109)
- Command sandboxing builds arguments directly as an array (`argv`) and spawns the container sandbox process without passing through a host shell (`sh -c` / `bash -c`). This eliminates shell metacharacter quoting vulnerabilities on workspaces with complex paths (e.g. spaces, single quotes).

### Destructive Command Tripwire Tokenization (REQ-SEC-108)
- The destructive-command denylist is parsed with POSIX shell-words tokenization in both TypeScript and Rust, eliminating false positives (`rm -rf ./build`, `rm -rf /tmp/x`, `grep reboot`, `echo shutdown`, `chown -R me /srv`).
- **Tripwire notice:** The command denylist is a **convenience tripwire** to catch obvious mistakes, **not a security boundary**. Known bypasses (such as `find / -delete`, `/bin/rm -rf /`, `rm -r -f /`, or Python rmtree calls) are documented non-goals that pass through the tripwire; the sandbox (`--sandbox`) and approval posture (`review`) form the security boundary.

### Verifier Execution Gating (REQ-SEC-119)
- Automated verifier executions (`run_tests`, `/test`, completion oracles) are classified as `exec` capabilities.
- In review mode, the first verifier execution is gated by an approval prompt displaying the exact command and the resolved test script body (extracted from `package.json` `scripts.test`, Makefile recipes, or `Cargo.toml`). Folder trust does not authorize verifier execution.

## 3. Packaged Product Parity & Unified Launcher (PLAN-06)

### Unified Launcher Grammar (REQ-REL-101, DEC-02, DEC-14)
- **TTY default:** Launching `nexus` with no arguments in a terminal opens the live Ratatui TUI (`nexus-tui`), connecting via a local JSON-RPC protocol to the sidecar agent.
- **Headless & non-TTY fallback:** When run in scripts, pipes, or without a TTY (e.g. `</dev/null`), `nexus` opens the command-line REPL.
- **Explicit REPL:** `nexus repl` (or `nexus --repl`) explicitly launches the REPL with full option forwarding (`-m`, `-r`, `--approve`, `--yes`).
- **Checkout parity:** `harness.sh` is simplified to execute the Node CLI directly with `NEXUS_HOME` unset, ensuring identical grammar between development checkouts and binary release packages.

### Explicit `run` Subcommand for Free Text (REQ-REL-104, DEC-14)
- Non-interactive tasks from the terminal now require the explicit `run` subcommand:
  ```bash
  nexus run "Explain the system architecture" --read-only
  ```
- **Error on unknown commands:** Unknown subcommands (such as `nexus notacmd`) are rejected immediately with an unknown command error instead of being silently interpreted as free-text agent prompts.

### Single-Source Versioning & Core Handshake (REQ-REL-103)
- Version numbers are synchronized from root `package.json` across CLI manifests, `core/Cargo.toml`, and the binary build identities via `scripts/sync-version.mjs`.
- The core RPC protocol includes an initial `hello` handshake validating matching versions and protocol compatibility before execution begins.
- CI release workflows assert version consistency across all artifacts.

### Diagnostic Hardening & Packaged Remedies (REQ-DX-101 to REQ-DX-104)
- `nexus doctor` runs with clean stderr and no unhandled event listener warnings.
- Diagnostic remedies in packaged installs guide operators to reinstall or update user paths (`~/.local/bin`), never referencing developer build tools like `make` or `harness.sh`.
- Sensitive data redaction preserves full filesystem paths, exempting absolute paths while sanitizing credential patterns.
- `nexus doctor` checks `~/.config/nexus/config.env` permissions, warning if group- or world-readable and offering an automated `0600` chmod repair.
- `tui.launch` verifies real launchability by probing `nexus-tui --live --check`.

### Hardened Installer (REQ-REL-105)
- Strict SemVer tag regex validation runs before any network requests.
- When no stable release exists, the installer queries releases and offers an actionable prerelease hint (`no stable release yet; latest prerelease is vX — rerun with NEXUS_VERSION=vX`).
- Reinstallation validates the installed tree against `MANIFEST.sha256` and automatically repairs damaged installations, or forces re-extraction with `NEXUS_FORCE=1`.
