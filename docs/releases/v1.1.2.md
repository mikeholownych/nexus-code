# Nexus Code v1.1.2

**Maturity:** Release notes for Nexus Code v1.1.2, which ships **with known limitations** that the owner accepted explicitly. They are listed in full below, and the [qualification record](v1.1.2-qualification.md) carries the evidence and the open items. The tag is created after the release pull request merges; these notes describe the source that is tagged.

v1.1.2 delivers the WP-1101 to WP-1108 roadmap that was originally planned for v1.1.0, with WP-1107 delivered in reduced form (see below). The v1.1.0 release failed and published no release files, and v1.1.1 is the published predecessor. Version numbers are immutable, so the roadmap work is assigned to v1.1.2. No `v1.1.2-rc.*` tag was ever published; the candidates that carried those names are superseded.

## What is in this release

- **WP-1101, local OpenTelemetry tracing.** GenAI spans for turns, model requests, tool dispatch and compaction, written locally with payload-free attributes. Trace output is confined to the approved trace directory.
- **WP-1102, flight-recorder credential redaction.** Credential redaction across traces, CLI errors and debug journals.
- **WP-1103, versioned evaluation datasets.** Datasets with separate examples and oracles and regression and benchmark splits; candidate prompts do not carry oracle paths or commands.
- **WP-1104, standalone `nexus eval`.** A packaged command with dataset selection, run count, an isolated home and structured score output. It runs outside the repository checkout.
- **WP-1105, deterministic code evaluators.** AST, build, typecheck, diff-boundary and JSON-repair evaluators and tool-call syntax telemetry (`toolCallSyntax`). **The evaluators are a library: no dataset task uses them yet.** See the limitations below.
- **WP-1106, single-step loop mode.** `--step`, and `/step` in the REPL and the TUI, pause after one agent turn for operator confirmation.
- **WP-1107, bounded tool schemas (reduced scope).** A bounded schema compiler for the four harness tools, and strict function schemas on the **vLLM request path only**. llama.cpp and Ollama requests keep their native tool schemas: no grammar or format constraint is sent for them, and the hybrid reasoning grammars from the roadmap are not implemented. The 99.5% valid-tool-call target was **not measured** against live providers; see below.
- **WP-1108, dependency modernisation.** The pending Dependabot updates were triaged and merged. `cargo deny` is clean, there are no deprecated npm packages, and a CycloneDX SBOM is generated.
- **Non-progress recovery.** A bounded recovery state machine for repeated unproductive tool calls, with state-based same-step progress and unique tool-call ids ([#398](https://github.com/mikeholownych/nexus-code/pull/398)).
- **Specialist orchestration and independent review.** Specialist roles with tool allow-lists, an evidence-based review boundary for operation units, and redaction of credential-named keys in review evidence ([#396](https://github.com/mikeholownych/nexus-code/pull/396), [#401](https://github.com/mikeholownych/nexus-code/pull/401)).

## Fixed

### A crash-resumed unit no longer receives a multi-message prompt's later messages twice

When a work unit's prompt carried two or more operator or inter-unit messages, and Nexus stopped after submitting that prompt but before the unit's result was saved, resume recognised only the **first** message as already submitted. Every later message from that prompt was injected into the unit's conversation again.

Resume now recognises each message in a submitted prompt's messages block, whatever its position. Matching is still limited to prompts that Nexus issued (`isSubmittedUnitPrompt`, from v1.1.1), so marker text in model output, tool output, or files cannot suppress a message.

- Impact in v1.1.1: the duplicated message was advisory context only. No message was lost, and no `TurnResult`, verification, or acceptance outcome was affected.
- Regression coverage: the post-prompt crash test in `cli/test/operation_release_review.test.ts` carries two messages and asserts that each appears once in the durable history and is acknowledged once.

### Correction to the v1.1.1 notes

The v1.1.1 notes say that a recipient receives undelivered messages "at most once". That holds for prompts carrying a single message. For prompts carrying several messages, v1.1.1 could re-inject the second and later messages after a post-submission crash. v1.1.2 makes the statement hold in both cases. `docs/releases/v1.1.1.md` carries a matching addendum.

## Known limitations (owner waiver)

Independent reviewers examined the release source and returned REQUEST CHANGES on the WP-1105 evaluator work and on the WP-1107 provider work. The owner decided to ship v1.1.2 with the findings below open, and to fix only one of them (the `typecheck_clean` diagnostic pattern, commit `2dbe565b`). Nothing in this list has been fixed in this release. The review reports are on [PR #402](https://github.com/mikeholownych/nexus-code/pull/402).

### Not measured

- **Constrained decoding, gate G1.1-4: NOT MET, NOT MEASURED.** The target is at least 99.5% valid tool-call JSON across supported provider endpoints. Strict function schemas are connected on the vLLM request path and tested locally with mock servers; llama.cpp and Ollama requests do not use them. No measurement against live llama.cpp, vLLM or Ollama endpoints was made, because the shared gateway resource was held by another release stream. Do not read this release as having met that target.
- **Task quality.** The benchmark fixture checks execution and prompt boundaries, not task-solving or provider quality.

### Provider handling (WP-1107)

- **The server-kind cache has no expiry or invalidation.** A readable model-list refresh overwrites the cached kind. When a refresh is unavailable (503, bad JSON, dropped connection, 404 or the model not listed), the previous kind is retained, including its strict flag. If the server on that endpoint is replaced and then answers that way, the stale kind stays (the cache is process-wide and keyed only by endpoint, so a fresh client for the same endpoint inherits it), and a retained gateway kind sends the `X-Task-Class` header to the non-gateway server that replaced it on the same endpoint. The rule that standalone local servers do not receive `X-Task-Class` (REQ-PRV-109) therefore holds on the success path and for non-gateway kinds, not in that replacement case.
- **Null normalisation covers well-formed native tool calls only.** Calls that needed JSON repair, and text-mode tool calls, still reach read tracking with `null` optional fields. The normaliser also strips an explicit `null` from every optional property of every tool for all providers, including properties whose schema allows null (measured on a synthetic tool; real MCP tools were not checked).
- **Request counting can turn off.** After a transient `/version` failure, or a 404 or missing-model refresh, a retained vLLM kind no longer matches the advertised source, so the agent probably reports that request counting is unavailable.
- **Matrix provenance is not bound to the checkout content.** The provider-matrix runner verifies the installed archive digest and that a clean checkout is at the claimed commit, but it does not prove the archive was built from that checkout: any clean repository at the claimed commit passes. A matrix result is evidence about the archive only if the archive digest is pinned by the person reading it.
- **Ollama identity.** A transient `/api/version` failure on a successful refresh still drops the kind to unknown.

### Code evaluators (WP-1105)

- **Fail-open overlay (rated HIGH by the reviewer; the only HIGH finding still open).** Build and typecheck run in the baseline workspace with only candidate edits to `.ts`, `.mts`, `.cts`, `.tsx`, `.js`, `.mjs`, `.cjs`, `.jsx`, `.rs` and `.py` files overlaid. Edits to any other file (`.go`, `.c`, `.json` and so on) are invisible to the build, so a change in one of those files that breaks the build can pass. Honest changes to such inputs, for example a new JSON module, can fail.
- **Shadowing.** A candidate can still shadow the checker through `node_modules` or an in-repo build helper, because those files are overlaid as source.
- **Large workspaces.** The runner takes two full workspace snapshots even for build-only tasks. A workspace with a very large `node_modules` is refused (5 second traversal deadline, 50,000 entries).
- **No resource limits on evaluator commands** (memory, process count, disk); in-process parsers have no timeout (a 65 MB TypeScript file blocked for about 63 seconds); a command path that resolves outside the workspace through a symlink or `..` runs (the command comes from trusted configuration; low exposure); `typecheck_clean` reports a benign line shift in a diagnostic as new.
- **`typecheck_clean` recognises only coded diagnostics** (`error TS1234:` or `error[E0123]:`). Checkers that print other formats fail closed whenever the baseline already has errors, and identical recognised configuration errors on both sides (for example TS5057) still pass.
- **Build configuration edits are ignored.** Because the baseline configuration is pinned, a candidate's edits to `tsconfig.json`, `package.json` and similar files are silently ignored by build and `typecheck_clean`, without a report.
- **Other.** `node --check` exits 0 for a `.js` file written with ESM syntax even when it contains a syntax error (for example `export const a = ;`); a dangling symlink at an overlaid path fails closed with `EEXIST`, and so does a candidate symlink with a source extension; the pinned workspace is created under the system temporary directory, not the configured workspace root; `spec.candidate.cwd` is silently overridden by the pinned root; `--pretty` compiler output defeats the TypeScript diagnostic pattern (fails closed); legacy text-mode tool calls are not counted by the `toolCallSyntax` telemetry; the evaluator README is partly stale.

## Runtime requirements

Unchanged from v1.1.1: Linux x86-64 with glibc 2.35 or newer, Node.js 22 or newer, and an OpenAI-compatible inference endpoint (local or an explicitly selected provider). The archive does not include Node.js. Rust and Cargo are not required at runtime.

## Upgrade

Operation records are unchanged: operation schema version 2, as in v1.1.1. No migration runs, and v1.1.1 can read records written by v1.1.2.

No release package for the final stable version was built or acceptance-tested before the tag; the published archive is built by the release workflow.
