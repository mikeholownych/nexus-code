# Nexus Code v1.1.1

**Maturity:** Stable release for Nexus Code v1.1.1.

This release delivers the complete Nexus Code multi-agent orchestration architecture, serialized git integration with verified execution receipts, typed inter-agent communication, operation replay, and closed edge cases for cancellation idempotency, message durability, prompt submission provenance, and replay envelope protection:
- Multi-agent orchestration with deterministic parallel work units and per-resource slot reservations.
- Serialized Git integration queue with candidate digests and verified execution receipts.
- Typed inter-agent communication channels (`request`, `observation`, `artifact`, `verdict`).
- Operation timeline replay with schema version 2 persistence and safe legacy migration.
- Cancellation idempotency and late result suppression.
- Durability-positive message acknowledgment and structured retry classification.
- Proven prompt submission provenance (`isSubmittedUnitPrompt`) protecting message injection against model outputs, tool outputs, and non-Nexus user notes.
- Protected task envelope replay failure propagation across single- and multi-record queries.

## Runtime requirements

Unchanged from v1.0.0: Linux x86-64 with glibc 2.35 or newer, Node.js 22 or newer, and an OpenAI-compatible inference endpoint (local or an explicitly selected provider). The archive does not include Node.js; Rust and Cargo are not required at runtime.

## Highlights

### Deterministic parallel work units

An operation may now run more than one work unit at a time:

```json
{
  "objective": "Add a --dry-run flag",
  "policy": { "maxConcurrentUnits": 2 },
  "resources": [
    { "id": "primary", "endpoint": "https://api.example/v1", "model": "m1" },
    { "id": "secondary", "endpoint": "https://api.example/v1", "model": "m2", "maxConcurrentUnits": 1 }
  ],
  "units": [
    { "id": "impl", "role": "implementer", "prompt": "…" },
    { "id": "docs", "role": "implementer", "prompt": "…" },
    { "id": "test", "role": "tester", "dependsOn": ["impl"], "prompt": "…" },
    { "id": "review", "role": "reviewer", "dependsOn": ["impl", "test"], "requires": { "independentOf": ["impl"] } }
  ]
}
```

- The scheduler returns an ordered due-set: required units first, then the longest unfinished dependent chain, then the operation's declared unit order. The same persisted state always produces the same due-set.
- Concurrency defaults to **1**. An operation that does not opt in behaves as it did in v1.0.0: one unit in flight.
- Per-resource slots are reserved for the duration of a run, so two units pinned to one single-slot resource serialise. A unit whose qualified slots are busy stays `RUNNABLE` — it is not parked and not escalated.
- One unit's failure does not touch a batch-mate. Cancelling aborts every in-flight unit and leaves each resumable. A restart reconciles every unit that was in flight.

### Retained worktrees are named

A unit worktree with uncommitted or ignored files is kept rather than destroyed, and the event log now says which worktree was kept and why (`WORKTREE_RETAINED`). A clean lifecycle still leaves no unit worktree behind.

### Serialised git integration with evidenced receipts

Concurrent isolated units complete at unpredictable times, but they share one integration worktree. Integration is now a queue: one merge at a time, in completion order, with `INTEGRATION_QUEUED` and `INTEGRATION_SKIPPED` events. Each receipt records:

- the unit's branch and commit, and the resulting `integratedCommit`;
- the **candidate digest** of the tree that was merged (omitted, never fabricated, when the worktree was already gone);
- the **executed verifier** the unit was accepted with (omitted when it produced none);
- a 1-based **sequence** so a reviewer can reconstruct merge order.

### Typed messages between units

An operation record now carries typed messages (`request`, `observation`, `artifact`, `verdict`) addressed to a unit or to the whole operation. `*` means **each unit receives it once**, not that the first unit consumes it:

- a completed unit publishes its verified summary as an `artifact` (a reviewer publishes a `verdict`);
- a recipient receives undelivered messages at most once, in the same save that starts its run;
- `nexus operation message <op> --to <unit|*> --kind <kind> --body <text>` lets the operator publish one;
- the record is bounded (200 messages; 4,000 characters per body), and a dropped message is reported as an event.

A message is advisory context. It is never verification evidence and cannot change a `TurnResult`.

### Operation replay

`nexus operation status <op> --replay` prints the recorded timeline, oldest first, with contiguous step indices; `--replay --json` adds a `replay` document to the view. Replay never re-executes, never calls a provider, never takes the operation lock, and writes nothing. `--dag` and `--replay` are separate views and cannot be combined.

## Upgrade notes

### Operation records migrate automatically

The durable operation document is now schema version 2. On first load, a v1.0.0 record is migrated in memory (it gains `schemaVersion: 2` and nothing else), and the first write keeps a byte-for-byte copy of the original record at `<record>.pre-migration-v1`. If that copy already exists with different content, the save fails closed rather than overwriting it.

A record written by a **newer** Nexus is refused with a one-line error and is left on disk untouched — it is not corrupt and is not quarantined. Upgrade Nexus to open it.

### Rollback

A v1.1.1 build refuses a record written by a *newer* build. The reverse is **not** protected: a v1.0.0 binary has no operation-document gate, so it will open a schema-2 record, ignore the new fields, and can write it back without them. Before running a v1.0.0 binary against an operation that v1.1.1 has touched, restore that operation's `.pre-migration-v1` copy and remove the live record. There is no automatic downgrade, and this is why the pre-migration copy is written before the first v2 write rather than after.

### Stricter operation specs

Unknown keys in an operation spec are now rejected with exit 2 and a suggested key, instead of being ignored. In particular `git.publish` is rejected: PR publication is not available in v1.1.1. A spec that previously "worked" while silently ignoring a key will now fail loudly, which is the intended change.

### Context-budget decisions

A `CONTEXT_BUDGET` block now names the binding bound, the estimated tokens and the source of the bound (`operator-budget` or `agent-estimate`), and `unit.context` records the source. The estimate numbers themselves are unchanged.

## Deliberately not in v1.1.1

| Item | Why | Target |
|---|---|---|
| PR publication (`git.publish`) | Needs an operation-level egress authorization; a shell `git push` bypasses the egress boundary | v1.2 |
| TUI operation pane, in-view decisions | Needs its own PTY qualification; the CLI view is the supported surface | v1.2 |
| Semantic retrieval over operation records | Needs a local index lifecycle and an embedding-egress policy | v1.2 |
| A unit-authored message tool | Adds a tool surface and an approval effect; the operator channel ships first | v1.2 |

## Release acceptance qualification

All release acceptance criteria for v1.1.1 have been verified:
- Real process kill during a live two-unit batch tested and verified (`ACC-V11-MAO-07`).
- Crash between integration enqueue and merge resumes to exactly one receipt (`ACC-V11-GIT-02`).
- Cancellation between enqueue and drain produces clean unmerged branch disposition (`ACC-V11-GIT-04`).
- Restoring a context checkpoint then resuming fails closed as UNVERIFIED (`ACC-V11-CTX-04`).
- Cross-runner reproducibility workflow accepts immutable RC tags across release lines (`repro_workflow.test.ts`).
