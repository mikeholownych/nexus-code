## Documented limits (not defects, not closed)

- A command that runs **without a sandbox, with the operator's rights**, can fake a terminal (for example with `script`) and approve project hooks, workspace plugins and triggers, or write the approval store directly (`docs/HOOKS.md`, `docs/PLUGINS.md`, `docs/TRIGGERS.md`).
- Any other process running as the **same uid** can change the approval stores, the operator hooks file, goal state and runner state; protection there is file mode only.
- **Goal state is not signed.** Integrity rests on mode 0600 and the agent's file-tool refusals; an unsandboxed command can rewrite caps, stall counts and driver identity (`docs/v1.3.0/PA3_GOAL_LIFECYCLE.md`).
- Workspace JS plugins run in process with full process authority once approved; an absolute or dynamic load inside an approved entry is not covered (`docs/PLUGINS.md`).
- A `sha256:` plugin pin in policy covers the entry file only; a plugin file is hashed and then imported by path (`docs/MANAGED_POLICY.md`).
- Sandbox coverage: Bubblewrap on Linux and Docker; no kernel, seccomp or macOS/Windows layer is claimed. The sandbox hides the task-state root and the socket directory by mounts and pins, which were exercised on one host kernel with bwrap 0.13.1 and a local Docker daemon; other kernels, user-namespace settings and bwrap versions are unmeasured. Unattended jobs, schedules and the runner are Linux only.
- An unattended verifier the operator named runs repository-controlled and model-written code without a prompt, inside the sandbox (`docs/SCHEDULES.md`).
- A `--listen` socket is readable by an unsandboxed approved command that can read the descriptor file.
- Live inference is the project's gateway only; no gateway measurement for v1.3.0 exists in this record.
