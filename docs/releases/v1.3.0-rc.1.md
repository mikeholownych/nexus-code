# Nexus Code v1.3.0-rc.1 (release candidate) - DRAFT

**Draft.** Written against `origin/release/v1.3.0` tip `09eb0b12f` before any version bump. Nothing here is released, tagged or published; version strings are still 1.2.2. Replace the evidence SHAs and the "in flight" items at the RC commit.

**Maturity:** release candidate. Supersedes nothing; the previous stable release is [`v1.2.2`](v1.2.2.md). **External qualification is pending.** This is not a claim that Nexus Code is frontier-grade. Every test, review and measurement named here is internal validation, and results are reported as measured, including open findings. State of each gate and unit: [`v1.3.0-READINESS.md`](v1.3.0-READINESS.md) ("ledger closed for the landed units, qualification pending").

Theme (from [`docs/v1.3.0/PLAN.md`](../v1.3.0/PLAN.md)): let other programs drive Nexus and let teams govern it, without weakening the gate. Every new surface goes through the same approval and verification gates as the terminal. Experimental surfaces are marked experimental below and in their documents.

## What is new, by track

- **Protocol and embedding.** The sidecar protocol has generated JSON Schemas, a published document and version negotiation (PF-1, `docs/PROTOCOL.md`, #697 #700 #712). `nexus run --json` has a versioned result contract and documented exit codes (PF-2, #705). A library entry point and an embedding guide (PF-4, `docs/EMBEDDING.md`, #779 #786; not published to npm). Experimental: `sidecar.js --listen` accepts other clients on a private unix socket with a token, as controller or read-only observers (PF-3, #797).
- **IDE access.** `nexus acp` serves the supported subset of ACP v1 over stdio; client permission answers can approve one pending action and nothing else (AC-1, `docs/ACP.md`, #740 #741 #752). Conformance fixtures recorded from Zed 1.29.3 and CodeCompanion.nvim 20.3.0, no live model (AC-2, `docs/evidence/AC2_ACP_CONFORMANCE.md`, #749); those captures predate later ACP changes.
- **Verification layer.** `nexus verify` gives a verdict (VERIFIED, REGRESSION_FREE, UNVERIFIED, BLOCKED) on a change without running an agent (VR-1, #707). The same check is available to other harnesses through an MCP tool and ACP `_nexus/verify`; the caller cannot raise the verdict (VR-2, `docs/evidence/v1.3.0/VR2.md`, #756 #777). Sandbox denials are recorded as receipt and flight events and never raise a verdict (VR-3, #745).
- **Governance.** Managed policy with precedence system, user, project; restrict-only; a parse error in the system or user tier fails closed; `nexus policy show|check` (GV-1, `docs/MANAGED_POLICY.md`, #717 #738 #778 #783). Admin strict mode and MCP/plugin allowlists (GV-5). `nexus audit export|verify` bundles with a hash manifest, optional ed25519 signing (GV-2, `docs/AUDIT.md`, #714 #771 #772). A hash-chained flight recorder checked on replay (GV-3, #696 #701 #761). Telemetry transparency and an opt-out (GV-4, `docs/TELEMETRY.md`, #695).
- **Hooks and plugins.** `pre-tool` and `post-tool` command hooks that can deny a call and never approve one (HK-1, `docs/HOOKS.md`, #782 #805). Plugin packages with a `nexus-plugin.json` manifest, installed from a local directory and verified against an install receipt: `nexus plugins install|list-installed|remove|verify` (HK-2, #796). Per-plugin approval for workspace plugins and workspace manifest plugins that run as subprocesses (HK-3, `docs/PLUGINS.md`, #798 #808 #810). Not in this candidate from the plan text: the other hook events, git-URL installs pinned to a commit, trigger-loaded skills (see Not in this release).
- **Background and scheduled runs (experimental, Linux).** A detached runner and `nexus job`/`nexus runner` (BG-1, `docs/RUNNER.md`, #780). `nexus schedule` with `--cron`, `--every`, `--at`, each run an unattended job in a fresh worktree (BG-2, `docs/SCHEDULES.md`, #799 #801 #802). Event-trigger trust model and `nexus triggers list|approve|revoke|status` (BG-3 trust model, `docs/TRIGGERS.md`, #803). **BG-3 firing (file watcher, signed webhooks): in flight as draft PR #812; not in this candidate unless it merges before the cut.**
- **Parallel agents and goals.** `nexus operation watch` and worktree owner receipts, resource admission (PA-1, #787 #794). Merge arbitration that re-verifies the merged tree (PA-2, #785 #788 #790). Goal semantics: a goal from a dead process resumes paused, fingerprint stall counting, completion only by a verifier receipt, an optional token budget (`nexus operation budget`) (PA-3, `docs/v1.3.0/PA3_ACCEPTANCE.md`, #758 #775 #789 #806 #809 #811). `/goal`, `/loop`, `/batch` and `/team` are in the command catalogue; `nexus operation validate` checks a spec (PA-4, staged, #709 #713 #793).
- **Sandbox and tools.** Named sandbox profiles `--sandbox :workspace|:read-only|:network` (SB-1, #781 #795; further slices in flight). One tool registry binds each spec to its handler (MT-2 slices 1-2, `docs/TOOL_REGISTRY.md`, #784 #804; later slices in flight).
- **Language servers and CI.** LSP lifecycle, bounds, position encodings and project roots (LS-1, LS-2, #718 #733 #736 #739 #751). CLI suite shard fan-out under stable required check names (#742 #743 #746 #748 #750).

## Behaviour changes that need a migration note

1. **Workspace JavaScript plugins need per-file approval (HK-3).** A plugin in a workspace's `.nexus/plugins/` or `plugins/` loads only when its exact bytes were approved with `nexus plugins trust <file>` in a terminal. `nexus trust` alone no longer loads it; nothing is approved on upgrade. An approved plugin runs from a private copy of its one file, so imports of sibling files or workspace packages fail and the plugin shows `load-failed`. A workspace plugin cannot take a name of your own plugin. Your own plugin directories (`~/.nexus/plugins/`, `~/.config/nexus/plugins/`) are not loaded when Nexus starts in a directory that contains them (your home). First session prints a notice; `nexus doctor` warns `plugins.workspace`. Migration table: `docs/PLUGINS.md` "Migrating workspace plugins". (#798 #808 #810)
2. **Project hooks accept only an allowlisted command shape and run from verified copies (HK-1).** A project's `.nexus/hooks.json` command must be one of the listed forms (an explicit interpreter with a workspace script, or a script with an absolute `#!` line); `env`, `npm run`, `make`, inline code (`-c`, `-e`), other launchers are refused and the file is invalid. Approval records SHA-256 of the script and the files given to it; the hook runs from a private copy of those bytes under `~/.nexus/hook-runs/`, so `$0`, sibling imports and sourced files do not lead back to the repository. Approving needs a person at a terminal. Hooks that need anything else belong in `~/.config/nexus/hooks.json`. (`docs/HOOKS.md`, #782 #805)
3. **A name in `mcp.allow` no longer admits a workspace-defined server (GV-1).** A bare name does not pin the command; a workspace `.mcp.json` entry of that name is refused. Use `command:` or `url:` entries or `mcp.disable_workspace = true` for a boundary. `nexus policy check <file>` validates a policy before rollout; exit code 2 means Nexus would refuse to start. (`docs/MANAGED_POLICY.md`, #778 #783)
4. **A broken system or user policy file fails closed.** Nexus refuses to start (exit 2) and names the file and tier. `/etc/nexus/policy.toml` is the system tier.
5. **Unattended jobs and schedules.** They never approve a command or a network call and have no allow-always; the only command that runs without approval is the exact operator `--verifier`, in the sandbox, in the run's worktree (it runs repository and model-written code without a prompt). A `read-only` run does not run its verifier and says so (`verifier.status: NOT_RUN`). A schedule needs a trusted workspace (`nexus trust`) that is checked again at every slot. (`docs/SCHEDULES.md`, `docs/RUNNER.md`, #780 #799 #802)
6. **Schedules are UTC with a 5-minute floor.** `--cron` and `--at` are UTC, `--every` is 5 minutes to 30 days, cron slots must be at least 5 minutes apart, there is no time zone and no `@daily`. Missed runs are counted and reported; `--on-missed report` (default) runs nothing, `run-once` runs one catch-up job. At most 64 schedules.
7. **`--listen` socket (experimental).** Refused under auto approval; the socket is mode 0600 in a 0700 directory; the token comes from a 0600 descriptor file; the sidecar refuses a socket directory inside the workspace; under `--sandbox` the directory is hidden from commands. A client cannot grant allow-always or change the mode. Protocol stays 1 (new error codes `UNAUTHORIZED`, `NOT_CONTROLLER`, `NOT_PERMITTED`). (`docs/PROTOCOL.md`, #797)
8. **Goal pause semantics (PA-3).** A goal whose recorded driver (pid, host, kernel start time, boot id) is not a live process on this host resumes `PAUSED` with a reason, on the read path and the drive path. Records from builds before `activeStartTicks` pause. The operation record schema is now v7. `/team` and `nexus operation` are no longer experimental. Known gap: an unattended job or loop `prepare` can override a stale pause (#807). (`docs/v1.3.0/PA3_GOAL_LIFECYCLE.md`)
9. **`--sandbox` masks the task-state directory and pins its ancestors.** A state path through a symlink inside the workspace, or a workspace that is the state directory, is refused with an explicit error (PA-3, #811). The agent's file tools refuse `~/.nexus/tasks`.
10. **Sandbox profiles (SB-1).** `--sandbox :read-only` sets the approval mode like `--read-only`; `:network` is an explicit network request that managed `sandbox.forbid_network` refuses; profiles apply with the other clamps and cannot loosen policy.
11. **Audit export refuses a repository whose own Git configuration names a program, and a workspace with a submodule,** instead of hashing it (`binding` becomes `unavailable`; per the review record on #771 and the PR titles of #772 and #776, `docs/AUDIT.md` was not checked for this wording). (#772 #776)
12. **Budget flags.** Objective-wide tool-invocation and cumulative task-time limits exist (`--max-tool-invocations`, `--max-task-minutes`); an objective that exceeds them stops. (#699 #760 #774)
13. **BG-3 triggers.** When the firer lands, a workspace `.nexus/triggers.json` fires only while its exact bytes are approved with `nexus triggers approve`, runs read-only unattended jobs by default, and is rate-limited and quarantined; no trigger runs on upgrade. Until #812 merges, `nexus triggers` manages approvals only and nothing fires.

## Security notes and limits

- Nothing in this candidate is independent qualification. The review record (agent-run reviews posted as PR comments, with the defects they found and the follow-ups still open) is in the readiness inventory.
- A command that runs without a sandbox, with your rights, can fake a terminal and approve project hooks, workspace plugins and triggers, or write the approval stores. Run the agent sandboxed, or keep approvals on, for untrusted repositories.
- Any other process of the same user can change approval stores, goal state and runner state. Goal state is not signed.
- Workspace JS plugins run in process after approval; manifest plugins run as subprocesses with the project-hook rules.
- Sandbox: Bubblewrap and Docker only, exercised on one host kernel; no kernel-level or seccomp guarantee is claimed; other kernels and bwrap versions are unmeasured.
- A `--listen` socket and its descriptor are readable by an unsandboxed approved command.
- Open review follow-ups at the tip: #770 (process-tree sweep bound), #795 (network-state reset, doctor posture), #797 (bind-then-chmod window, `--listen` without `--sandbox`, example reader), #788 (a verifier that mutates the integration tree), and issues #800 (`startsWith("..")` containment sites) and #807. Each is to be fixed or carried here as a known limitation at the RC.
