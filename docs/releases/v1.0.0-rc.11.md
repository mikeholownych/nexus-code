# Nexus Code v1.0.0-rc.11 release candidate

**Maturity:** release candidate; prerelease, not stable.

**Status:** this candidate is for exact-artifact qualification. It does not establish independent acceptance or authorize stable v1.0.0 promotion. Qualification results must identify the workflow-produced package and its digest. No successor-RC qualification has been run yet.

This release packages the Nexus Code Linux x86-64 client: the TypeScript CLI and sidecar, production Node dependencies, Rust `harness-core`, and Ratatui `nexus-tui`. It is a version-only candidate built from current `main`; it contains the post-RC10 source changes below.

## Changes since RC10

### Durable operations

- **Test-first work units (opt-in):** `NEXUS_TDD=1` (or `AgentWorkUnitExecutor({ tdd: true })`) runs implementer units as a RED turn that must record a failing, executed verifier and a changed test, then a GREEN turn. RED evidence is a private sidecar keyed by the unit task and prompt; the verifier baseline is rebased only onto the added tests, and a RED that narrows the operator's tests or verifier is refused. See `docs/v1.0.0/TDD-WORK-UNITS.md`.
- **Read-only operation view:** `nexus operation status --dag [--json]` and `nexus operation watch` project the unit DAG, resource eligibility, open decisions and the event tail without taking the operation lock or writing a transition. Operation text is sanitised for terminal control sequences. See `docs/v1.1.0/OPERATION_OBSERVABILITY.md`.
- **Git-aware isolated operations (opt-in):** `spec.git = { isolate: true, baseRef? }` gives each unit its own worktree and branch, integrates completions into an operation branch with receipts, re-verifies the merged tree, and blocks with `MERGE_CONFLICT` / `INTEGRATION_FAILED` decisions. Recovery is idempotent and fails closed when integration history is missing or rewritten. See `docs/v1.1.0/GIT_AWARE_OPERATIONS.md`.
- **Per-unit context budget and checkpoints:** `units[].contextBudget` blocks a unit before inference when the operator's cap is the binding limit and offers to lift it; `nexus operation checkpoint|checkpoints|restore` snapshots a unit's task state and conversation journals as a hash-verified bundle, with a pre-restore backup. See `docs/v1.1.0/CONTEXT_MANAGEMENT.md`.
- **Operation policy configuration:** durable operation policy defaults can be set in the operator config; scheduler and runner internals were split (scheduler extraction, runner decomposition) with bounded diagnostics, and recovered merged operations now require verification evidence.

### Reliability and security

- Checkpoint restore is fail-closed on content mismatch; incomplete or duplicate checkpoint bundles are reused/cleaned correctly, and restoring a conversation removes stale journals.
- Configured Git hooks are guarded consistently for checkpoint and retention operations, including a fail-closed race path.
- Malformed operator configuration is reported by `nexus doctor` with recovery guidance instead of an unhandled failure.
- Clean-checkout build identity is recorded correctly, and packaged smoke startup no longer races its log.
- CLI terminal output sanitises control characters in corrupt-resume errors; batch read paths preserve lossy UTF-8 and propagate read errors instead of continuing.
- Credential handling: malformed credential origins can no longer be rebound, and credential-store writes are failure-atomic under the file guard.
- Recovery: pre-fix worktree tasks are recovered from the repository root, and upgrades recover state from the configured state directory.
- Tooling: `update_plan` no longer mutates the workspace, and ambiguous Python verifier imports are rejected.
- CI provisions the pinned evaluator toolchains for the qualification suites.

## Runtime requirements

- Linux x86-64 with glibc 2.35 or newer.
- Node.js 22 or newer.
- An OpenAI-compatible inference endpoint, local or explicitly selected provider.

The archive does not include Node.js. Rust and Cargo are not required at runtime. No other OS or architecture is claimed.

The release workflow for `v1.0.0-rc.11` is expected to produce the version-matched Linux archive, `SHA256SUMS`, SBOM, notices, installer, and provenance.
