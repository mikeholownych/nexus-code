# Nexus Code v1.1.0

**Maturity: not released.** This document is the release-notes draft for v1.1.0. No `v1.1.0` tag, release candidate or
artifact exists at the time of writing. Release-candidate qualification (`docs/v1.1.0/VALIDATION.md` §8) has not been
executed, and `docs/v1.1.0/STATUS.md` §4 is the authoritative record of what has actually been run.

Everything below describes behaviour implemented and covered by source tests at the candidate commit. It does not
describe installed-package behaviour, which is only established by the installed-RC gates.

## Runtime requirements

Unchanged from v1.0.0: Linux x86-64 with glibc 2.35 or newer, Node.js 22 or newer, and an OpenAI-compatible inference
endpoint (local or an explicitly selected provider). The archive does not include Node.js; Rust and Cargo are not
required at runtime.

## Highlights

### Deterministic parallel work units

An operation may now run more than one work unit at a time:

```json
{
  "objective": "Add a --dry-run flag",
  "policy": { "maxConcurrentUnits": 2 },
  "resources": [
    { "id": "primary", "endpoint": "https://api.example/v1", "model": "m1" },
    { "id": "secondary", "endpoint": "https://api.example/v1", "model": "m2", "maxConcurrentUnits": 1 }
  ],
  "units": [
    { "id": "impl", "role": "implementer", "prompt": "…" },
    { "id": "docs", "role": "implementer", "prompt": "…" },
    { "id": "test", "role": "tester", "dependsOn": ["impl"], "prompt": "…" },
    { "id": "review", "role": "reviewer", "dependsOn": ["impl", "test"], "requires": { "independentOf": ["impl"] } }
  ]
}
```

- The scheduler returns an ordered due-set: required units first, then the longest unfinished dependent chain, then
  the operation's declared unit order. The same persisted state always produces the same due-set.
- Concurrency defaults to **1**. An operation that does not opt in behaves as it did in v1.0.0: one unit in flight.
- Per-resource slots are reserved for the duration of a run, so two units pinned to one single-slot resource
  serialise. A unit whose qualified slots are busy stays `RUNNABLE` — it is not parked and not escalated.
- One unit's failure does not touch a batch-mate. Cancelling aborts every in-flight unit and leaves each resumable.
  A restart reconciles every unit that was in flight.

### Serialised git integration with evidenced receipts

Concurrent isolated units complete at unpredictable times, but they share one integration worktree. Integration is now
a queue: one merge at a time, in completion order, with `INTEGRATION_QUEUED` and `INTEGRATION_SKIPPED` events. Each
receipt records:

- the unit's branch and commit, and the resulting `integratedCommit`;
- the **candidate digest** of the tree that was merged (omitted, never fabricated, when the worktree was already gone);
- the **executed verifier** the unit was accepted with (omitted when it produced none);
- a 1-based **sequence** so a reviewer can reconstruct merge order.

### Typed messages between units

An operation record now carries typed messages (`request`, `observation`, `artifact`, `verdict`) addressed to a unit or
to the whole operation:

- a completed unit publishes its verified summary as an `artifact` (a reviewer publishes a `verdict`);
- a recipient receives undelivered messages at most once, in the same save that starts its run;
- `nexus operation message <op> --to <unit|*> --kind <kind> --body <text>` lets the operator publish one;
- the record is bounded (200 messages; 4,000 characters per body), and a dropped message is reported as an event.

A message is advisory context. It is never verification evidence and cannot change a `TurnResult`.

### Operation replay

`nexus operation status <op> --replay` prints the recorded timeline, oldest first, with contiguous step indices;
`--replay --json` adds a `replay` document to the view. Replay never re-executes, never calls a provider, never takes
the operation lock, and writes nothing. `--dag` and `--replay` are separate views and cannot be combined.

## Upgrade notes

### Operation records migrate automatically

The durable operation document is now schema version 2. On first load, a v1.0.0 record is migrated in memory (it gains
`schemaVersion: 2` and nothing else), and the first write keeps a byte-for-byte copy of the original record at
`<record>.pre-migration-v1`. If that copy already exists with different content, the save fails closed rather than
overwriting it.

A record written by a **newer** Nexus is refused with a one-line error and is left on disk untouched — it is not
corrupt and is not quarantined. Upgrade Nexus to open it.

### Rollback

The previous binary does not read a schema-2 operation record. It refuses it with an unsupported-version error rather
than misinterpreting it. To roll back an individual operation, restore its `.pre-migration-v1` copy with an explicit
operator action; there is no automatic downgrade.

### Stricter operation specs

Unknown keys in an operation spec are now rejected with exit 2 and a suggested key, instead of being ignored. In
particular `git.publish` is rejected: PR publication is not available in v1.1.0. A spec that previously "worked" while
silently ignoring a key will now fail loudly, which is the intended change.

### Context-budget decisions

A `CONTEXT_BUDGET` block now names the binding bound, the estimated tokens and the source of the bound
(`operator-budget` or `agent-estimate`), and `unit.context` records the source. The estimate numbers themselves are
unchanged.

## Deliberately not in v1.1.0

| Item | Why | Target |
|---|---|---|
| PR publication (`git.publish`) | Needs an operation-level egress authorization; a shell `git push` bypasses the egress boundary | v1.2 |
| TUI operation pane, in-view decisions | Needs its own PTY qualification; the CLI view is the supported surface | v1.2 |
| Semantic retrieval over operation records | Needs a local index lifecycle and an embedding-egress policy | v1.2 |
| A unit-authored message tool | Adds a tool surface and an approval effect; the operator channel ships first | v1.2 |

## Known gaps at this draft

These are tracked as owed work, not as accepted limitations:

- A real process kill during a live two-unit batch is not demonstrated; the reconciliation path is tested from a
  persisted two-`RUNNING` state.
- A crash between integration enqueue and merge is not demonstrated for a queued unit.
- A cancel between enqueue and drain (which must produce `INTEGRATION_SKIPPED`) is not demonstrated.
- Restoring a context checkpoint and resuming is not yet asserted at the turn level.

## Inherited v1.0.0 qualification state

v1.1.0 does not claim that v1.0.0 is qualified. At the time of writing, the published `v1.0.0` release body still says
acceptance is `IN_PROGRESS`, and the held-out corpus custody, M5 qualification runs, cross-runner reproducibility and
independent acceptance items remain open (issues #1, #2, #5, #6, #7, #49). A stable v1.1.0 release requires either those
gaps closed or an explicit owner decision that names each one; see `docs/v1.1.0/VALIDATION.md` §7.
