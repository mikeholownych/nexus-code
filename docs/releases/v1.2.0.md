# Nexus Code v1.2.0

**Maturity:** the v1.2.0 semantic and architectural integrity workstream is landed except for the units listed under "Not in this release". **External qualification is pending.** This is not a claim that Nexus Code is frontier-grade. Every test and scenario below is internal validation of this repository's own code; none of it is independent evaluation.

Plan, audits and per-unit status: [`docs/v1.2.0/SEMANTIC_AND_ARCHITECTURAL_INTEGRITY.md`](../v1.2.0/SEMANTIC_AND_ARCHITECTURAL_INTEGRITY.md). Candidate: [rc.1](v1.2.0-rc.1.md).

## What is in this release

- **A model acceptance cannot stand without evidence (SI-1, #493).** A reviewer ACCEPT that reaches the review with no deterministic verifier evidence is a REJECT, and the rejection says how to supply the evidence.
- **Typed requirements (SI-4, #505).** Requirements can be `constraint` or `invariant`, with an optional verifier and linked tests. An operator-declared invariant (`Invariant: ... [verify: cmd]`) cannot become `verified` without a fresh passing run of its own verifier; a verifier the model declares is advisory and the requirement stays open until you `/requirements accept` it. `authorizedScope` is now passed into review evidence, so a diff outside the declared scope fails an ACCEPT.
- **Steering cannot silently drop a requirement (SI-3, #498).** Steering that negates a numbered requirement keeps the ledger intact and asks the operator; headless runs record the conflict unresolved. A request that would replace a ledger with unmet requirements keeps a `superseded` record.
- **Verification files are guarded (SI-2, #495).** Agent edits to CI files, Makefile and similar, test configuration, verifier scripts, existing test files, `package.json` verification keys and `.nexus-security.json` need an operator decision interactively and are denied headless. Every attempt is recorded in the session export. Modes: `verificationPaths.mode` `off`, `record`, `approve` (default), `block`. `run_command` writes are record-only: this does not stop a shell-capable agent.
- **Completion works when a verifier cannot be bound (#496).** `task_completed` used to be refused in any project whose verifier definition could not be snapshotted (a `node_modules` directory, a large Makefile reference graph, deeply nested directories). The verifier now runs and the result is REGRESSION_FREE with the reason; it is never VERIFIED and never earns a receipt or a worktree merge.
- **Structured verification attempts (DV-1, #497).** Each attempt records exit code, failing tests and a redacted excerpt; environment failures (tool missing, exit 126/127, sandbox) are not candidate failures and never skip a rerun.
- **Repair loops stop (DV-2, #509).** A stalled, oscillating or diverging verifier history ends the turn BLOCKED with the attempt history attached, never as success. Threshold `NEXUS_VERIFIER_CONVERGENCE_ATTEMPTS`, default 3.
- **Language servers are honest and contained (CG-1 #494, CG-2 #499).** `lsp_diagnostics` reports `unavailable`, not success with `[]`, when no server has published for the file's current content. Servers start only in a trusted workspace with a scrubbed environment, a filtered `PATH`, drained `stderr` and a byte-based message cap.
- **Type-check evidence (CG-4, #504).** After the test verifier passes, `tsc --noEmit` or `cargo check` runs through the same approval gate; a type error in a file the task modified blocks VERIFIED. Pre-existing errors in untouched files are recorded as `PREEXISTING` and do not block. The evidence names the configuration verified and never claims the code compiles everywhere. `NEXUS_TYPECHECK=off|enforce`.
- **Evidence provenance and real receipt dependencies (CG-3, #507).** Diagnostics are structured records fenced as untrusted data; evidence carries a `tool` or `model` source in the export; receipts record toolchain versions and configuration hashes, and a changed toolchain or configuration makes a receipt stale (a probe that cannot run is "unknown", not "changed").
- **Operations require isolation under concurrency (SI-8, #503).** `nexus operation run` rejects `maxConcurrentUnits` above 1 without `git.isolate`; legacy records are clamped to one concurrent unit with a warning.
- **Tests that pin behaviour.** A kill-mid-tool-call fault-injection test (SI-7, #501: no defect found), request-shape snapshots of what the model is sent (TI-1, #506), and the CERI `semantic_integrity` domain with frozen scenarios (SI-6, #500 and #508: 23 active, 2 pending).

## Behaviour changes to know about

- Verification-file edits ask (interactive) or are denied (headless). Opt out with `verificationPaths.mode`.
- `nexus operation run` rejects `maxConcurrentUnits` above 1 without `git.isolate`.
- Projects with an unbindable verifier now complete as REGRESSION_FREE instead of erroring.
- A type error in a modified file blocks VERIFIED (`NEXUS_TYPECHECK=off` to disable).
- A reviewer ACCEPT without verifier evidence is rejected; a review unit whose dependencies ran no verifier now blocks (depend on a verifier unit, or accept manually).

## Not in this release

- SI-5 (operator-declared boundary rules), DV-3 (operator-authorised regression obligations) and DV-4 (attempt lineage and differential verification against a declared reference): deferred to a v1.2.x release.
- CERI scenario `compaction-03` (a post-compaction check that every gating requirement is still present) has no owning unit; `cumulative-change-03` needs SI-5.

## Known limitations

- Nothing here is independent qualification. The CERI scenarios and every test are internal validation; CERI baseline identity and evidence-store verification (audit F02, F06) remain unimplemented.
- `run_command` writes to verification files are record-only; the verification guard does not stop a shell-capable agent.
- A `verified` requirement is not re-checked on resume (existing behaviour, more sensitive for invariants).
- Type-check: a change that breaks a caller in a file it did not touch is recorded as `PREEXISTING` and does not block; files changed through shell commands are not counted as modified; Go and Python are not checked.
- Only the `task_completed` path triggers the convergence signal; a loop that only calls `run_tests` relies on the existing stagnation limit.
- After a restart following an unbound-verifier pass, the baseline is memory-only, so the resumed task hits the "no matching pre-change baseline" refusal and a fresh task recovers.
- Records already on disk and the library API `newOperation` are not re-validated for the isolation rule (legacy records are clamped instead).
- Language servers are never run inside a sandbox (refused when a sandbox is required); only a fake server is exercised by the tests, not rust-analyzer, tsserver, pyright or gopls.
- Live inference is the project's gateway only. The G1.1-4 tool-call validity measurement for this release is **not met**: on v1.2.0-rc.1 `engineering/lead-reasoning` was 195/200 native valid (bar 99.5%; `engineering/deep` 200/200). The five failures are "think before the call" `edit_file` prompts where the model reasons to the output cap without calling the tool. The client code is identical to v1.1.4 (which passed on a rerun), nothing was changed to get a better number, and the owner accepted shipping with this recorded. See `docs/evidence/v1.2.0/G1.1-4-rc.1.md`.
