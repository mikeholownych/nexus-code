# WP-1107 — Provider-Constrained Tool Arguments

## Specification

**User story:** As a Nexus user running a supported inference engine, I need registered tool argument schemas passed through the provider's native constrained-tool path so tool calls arrive as schema-valid JSON and require fewer syntax repairs.

**Acceptance criteria:**

- **AC1:** An identified llama.cpp endpoint receives active allowlisted schemas through its native `tools` request field and no caller-supplied top-level `grammar` while tools are active. Test: `client preserves llama.cpp native tool schemas without incompatible grammar field` (baseline behavior; add a regression guard).
- **AC2:** An identified vLLM endpoint receives `strict: true` on each active allowlisted function schema; Nexus does not substitute a response-level `response_format` constraint for tool-argument constraints. Test: `client enables vLLM strict mode for allowlisted tool schemas`.
- **AC3:** An identified Ollama endpoint receives active allowlisted schemas through its native `tools` request field and Nexus does not send response-level JSON-schema `format` as a tool-argument constraint. Test: `client preserves Ollama native tool schemas without response format constraint` (baseline behavior; add a regression guard).
- **AC4:** Unknown, unsupported, or ambiguously identified endpoints retain their current request shape; no grammar field is sent based only on a configured lane label or generic OpenAI-compatible catalog fields. Tests: `client omits constrained fields for unknown and unsupported providers`; `generic context catalog remains unknown and receives no grammar field`; `provider identity accepts llama.cpp only with its marker and valid props handshake`; `provider identity accepts vLLM only with its model owner marker and version response`; `provider identity accepts Ollama only with version and selected-model show response`; `client omits constrained fields for missing malformed or mismatched provider identity`.
- **AC5:** On each supported endpoint, the exact installed candidate completes 200 attempts: 50 for each of four fixed allowlisted tool schemas. Each attempt requests exactly one tool call. `native_valid` means the raw provider argument string parses with `JSON.parse` and satisfies that tool's active parameter schema before normalization or repair; `repaired` means raw parsing fails and the existing repair path yields parseable, schema-conforming JSON; `schema_invalid` means raw or repaired JSON parses but fails the active parameter schema; `invalid` includes provider errors, timeouts, missing calls, and arguments that remain unparseable after repair. These four categories are mutually exclusive and sum to attempts. An endpoint passes only when `native_valid * 1000 >= attempts * 995`, `schema_invalid == 0`, and `invalid == 0`; report exact integer counts and do not round percentages for the decision. Tests/evidence: `tool grammar matrix evidence schema rejects invalid counts and identity omissions`; `tool grammar matrix computes endpoint pass without percentage rounding`; `tool grammar matrix rejects schema-invalid tool arguments`; `tool grammar matrix runner records archive and per-endpoint identity`; live `WP-1107 supported-endpoint syntax and schema matrix`.
- **AC6:** On each supported endpoint, 20 of the 200 attempts (five per tool) use a pinned reasoning-capable model and exercise a tool call after non-empty `<think>...</think>` reasoning. The installed client must preserve the provider's reasoning signal and the tool arguments must satisfy the selected tool's active parameter schema in the same response. Tests/evidence: `tool grammar matrix includes hybrid attempts and rejects missing reasoning evidence`; live `WP-1107 hybrid reasoning and tool-call matrix`. This verifies reasoning/tool grammar coexistence, not reasoning quality or task correctness.

**Out of scope:** Changing tool schemas or the allowlist; applying constraints to non-tool completions; measuring task-solving quality; enabling constraints on an endpoint that does not positively identify itself.

**Dependencies:** Existing schema-derived grammar generator and `toolCallSyntax` telemetry; source implementation is otherwise independent. AC5 and AC6 depend on an approved shared inference window, pinned server/model configurations, and the exact candidate package.

**Scope reconciliation:** The user selected the full failed v1.1.0 WP-1101–WP-1108 roadmap for v1.1.2. This explicit scope supersedes the older deferral in `ROADMAP-REVIEW.md` §2.5. It does not waive the required provider references, test gates, review, or G1.1-4 endpoint evidence.

**Roadmap contract reconciliation:** Keep the existing dynamic GBNF compiler and its allowlist/schema tests as the deterministic schema-to-grammar implementation. Provider transport must use each server's compatible native tool path: llama.cpp rejects a caller grammar beside native tools but builds a dynamic tool grammar from their schemas; vLLM consumes `strict: true` through its structural-tag tool parser; Ollama carries tool schemas in `tools`, separately from response-level `format`. The hybrid `<think>...</think>` + tool-call requirement is not dropped: AC6 and the live matrix require a reasoning-plus-tool attempt on each exact endpoint. The provider's model/template/parser must build or accept that hybrid grammar; any endpoint that cannot pass AC6 remains unsupported and blocks G1.1-4. Do not claim that successful JSON syntax alone satisfies schema validity.

## Implementation plan

**Chunk 1 — Provider request adapter**

- Add a typed adapter mapping provider kinds to documented native tool-schema behavior only after a provider-specific positive identity check. A configured lane label or `context_length`/`max_model_len` alone is insufficient.
- For vLLM, clone each active allowlisted function schema and set its documented `strict` property to `true`. For llama.cpp and Ollama, preserve the existing native `tools` schema request and never add a top-level grammar or response-format field alongside tools. Unknown providers retain their current request unchanged.
- Files: `cli/src/core/tool_grammar_provider.ts` (new), `cli/src/core/provider_capabilities.ts`, `cli/test/client_tool_grammar.test.ts` (new), `cli/test/provider_capabilities.test.ts`.
- Tests: AC1–AC4 request-shape and identity tests above, including positive provider-handshake fixtures and generic/missing/malformed/mismatched negative cases. AC1 and AC3 are baseline-preserving regression guards; AC2 is expected to fail before implementation.
- Identity contract: llama.cpp requires the exact `/v1/models` `owned_by: "llamacpp"` marker or its `meta.n_ctx_train` marker plus a successful `/props` response matching the existing llama.cpp schema; Ollama requires its `/api/version` response with a non-empty `version` string and a successful `/api/show` response for the selected model; vLLM requires the selected `/v1/models` entry to have `owned_by: "vllm"` (case-insensitive) and a successful `GET /version` returning a non-empty JSON `version` string (`wp1107-vllmserve` `basic.py:54-55`). Generic `context_length` or `max_model_len` fields describe capacity only; a generic `/version` response without the vLLM owner marker is not identity evidence. These are provider self-identification handshakes on the operator-configured endpoint, not cryptographic server authentication; any mismatch, missing probe, or malformed response disables provider-specific adaptation.
- Retrieved request contracts: llama.cpp rejects caller `grammar` when native tools are supplied and builds the tool grammar from submitted schemas (`tools/server/server-common.cpp:1380-1450`; `common/chat-auto-parser-generator.cpp:47-83`). Its reasoning PEG is prepended to the tool parser, and tool grammar generation uses the schema-bearing tool fields (`common/chat-auto-parser-generator.cpp:137-153,226-238`). Ollama carries `Tools` and `Format` as distinct fields and forwards them distinctly (`api/types.go:136-150`; `server/routes.go:3468-3480`); its docs distinguish tool calling from response-level structured output (`docs/api.md:519-527`). vLLM uses `FunctionDefinition.strict` (`vllm/entrypoints/openai/chat_completion/protocol.py:208-211`; `vllm/entrypoints/generate/base/protocol.py:298-313`) and resolves tool strictness from that flag in its structural-tag registry (`vllm/tool_parsers/structural_tag_registry.py:151-175`). Its response-level `response_format` is a separate structured-output path (`vllm/entrypoints/openai/chat_completion/protocol.py:852-880`). The vLLM response-template grammar accepts separate `thinking` and tool-call schema fields and can require reasoning before a strict tool call (`vllm/parser/response_template_grammar.py:865-1003`).

## Risks and reference queries

- `llama.cpp` caller `grammar` cannot accompany native tools; its chat parser builds tool grammars from the supplied function schemas. Do not pass the generated per-tool GBNF as a top-level request field.
- Ollama's `format` constrains the assistant response, while native tool calls use `tools`. Do not treat response-level JSON schema as tool-argument grammar.
- vLLM's `strict: true` depends on its strict-tool parser path and server configuration. The request capture test proves serialization, while the exact installed endpoint matrix is required to prove that the chosen server configuration enforces the tool schema.
- The approved plan's previous request-field assumptions were superseded by primary-source findings. Independent review approved the provider fixture, cache, and snapshot corrections before implementation resumed.
- G1.1-4 requires a real endpoint matrix (real inference through the gateway, DEC-16). A loopback mock proves serialization only and cannot satisfy the 99.5% metric.
- The provider lane’s immutable server and model identities are not yet confirmed because the shared `GATEWAY` claim is still held by the RC15 stream. Treat them as a pre-run gate: record and peer-review the three exact identities/configurations in the matrix plan before starting any provider call; do not substitute mutable tags or infer identity from an endpoint URL.
