# Sidecar protocol schema

The protocol reference for client authors is [`../PROTOCOL.md`](../PROTOCOL.md): transport, negotiation, every command and event, error codes and compatibility rules. This page is about the schema file and how it is kept current.

`sidecar-v1.schema.json` is the JSON Schema (draft 2020-12) of the Nexus sidecar protocol, version 1: the newline-delimited JSON a client exchanges with the Node sidecar. `$defs.SidecarEvent` is every message the sidecar sends, `$defs.SidecarCommand` every message a client sends. Each is a `oneOf` over the message variants, told apart by the constant `type`; every message also carries `v`, the protocol version.

The file is generated from the types in `cli/src/protocol.ts` by the TypeScript type checker. Do not edit it by hand: change the types, then regenerate.

```bash
cd cli
node scripts/gen_protocol_schema.mjs           # rewrite docs/protocol/sidecar-v1.schema.json
node scripts/gen_protocol_schema.mjs --check   # exit 1 when the schema or the ledger is stale
```

`cli/test/protocol_schema.test.ts` runs the same comparison, so CI fails when a protocol type changes and the schema does not.

## Recording a version decision

`VERSIONS.json` is the version ledger: entries `{ "protocol", "schemaSha256", "note" }`, newest last. The newest entry must carry the SHA-256 of the checked-in schema and the current `PROTOCOL_VERSION`. A type change therefore needs two things: a regenerated schema and a new ledger entry whose `note` states the decision, either the same version because the change is additive and compatible (a new optional field, a new message an older peer ignores), or a bumped `PROTOCOL_VERSION`. Append entries; leave earlier ones as they are.

## Extra properties are allowed

No object in the schema sets `additionalProperties: false`. A newer sidecar may add an optional field to an event, and an older client must ignore it, so a schema that forbade unknown fields would reject messages the protocol means to accept. Commands are open for the same reason in the other direction: `parseCommand` reads the fields it knows and drops the rest. The schema checks what is required and the type of every field it names. `additionalProperties` appears only where a type has an index signature, where it gives the type of every value.

A tuple (`ReceiptRow`) is the exception: its length is fixed, as in the type.

## What the generator does with each type

- An interface or type alias declared under `cli/src` is written once under `$defs` and referenced with `$ref`. An instantiated generic (`Pick<SlashSpec, ...>`) and an intersection that forms a message (`models.catalog`) are written out in place.
- A union of string literals is an `enum`; `T | null` is `anyOf` with `{"type": "null"}`; an optional property is left out of `required`.
- JSDoc comments on types and properties become `description`.
- Definitions, properties, `required` lists, enum values and variants are sorted, so the output is the same on every run.
- A type with no JSON form (a function, an enum, a tuple with optional elements) stops the generator with an error naming the property.

## Samples and recordings derived from the schema

- `cli/test/fixtures/protocol_v1_schema_samples.jsonl` holds a minimal and a full sample of every message, generated from the schema by `node cli/scripts/gen_protocol_samples.mjs` (`--check` exits 1 when it is stale). The Rust client's tests parse the event samples, so regenerate it after regenerating the schema.
- `cli/test/fixtures/protocol_v1_rust_commands.jsonl` holds the lines the Rust client serializes. A Rust test keeps it equal to the client's output (`NEXUS_UPDATE_PROTOCOL_FIXTURES=1 cargo test --bin nexus-tui rust_commands` rewrites it); `cli/test/protocol_parity.test.ts` validates it against the schema.
- `cli/test/fixtures/wire/*.json` are recorded sessions replayed against the real sidecar by `cli/test/protocol_wire.test.ts`. `NEXUS_WIRE_RECORD=1` on that test rewrites them from the sidecar's real output; `cli/test/helpers/wire_fixture.ts` documents the format.

## The `nexus run --json` document

`run-result-v1.schema.json` is the JSON Schema of the one document `nexus run --json` prints (`RunJsonOutput` in `cli/src/run_contract.ts`: a result, or an error document without `turn`). It is generated by the same `SchemaBuilder`, so everything above about open objects and type mapping applies to it.

```bash
cd cli
node scripts/gen_run_result_schema.mjs           # rewrite docs/protocol/run-result-v1.schema.json
node scripts/gen_run_result_schema.mjs --check   # exit 1 when the schema or its ledger is stale
```

Its ledger is `RUN_RESULT_VERSIONS.json`, entries `{ "schema_version", "schemaSha256", "note" }`, newest last, under the same rule: the newest entry carries the SHA-256 of the checked-in schema and the current `RUN_RESULT_SCHEMA_VERSION`. An added optional member keeps the version; a removed or renamed member, or a changed type or meaning, bumps it. The schema covers every type the result reaches (`TurnResult`, `ValidationReceipt` and the rest), so a change to any of them needs a regenerated schema and an entry. `cli/test/run_json_contract.test.ts` runs the comparison. The manual (`docs/USER_MANUAL.md`, "`nexus run --json`") describes the document and the exit codes.

## The `nexus verify --json` document

`verify-result-v3.schema.json` is the current JSON Schema of the one document `nexus verify --json` prints and `--receipt <file>` writes (`VerifyJsonOutput` in `cli/src/verify_contract.ts`: a result with `verdict`, or an error document without one). It is generated by the same `SchemaBuilder`; the two command-result generators share `cli/scripts/result_schema.mjs`. The v1 and v2 schemas and their ledger entries remain as prior contracts; v3 changes the meaning of `review` from always `NOT_RUN` to a structured verdict and adds the `REVIEW_REJECTED` reason.

```bash
cd cli
node scripts/gen_verify_result_schema.mjs           # rewrite docs/protocol/verify-result-v<N>.schema.json
node scripts/gen_verify_result_schema.mjs --check   # exit 1 when the schema or its ledger is stale
```

Its ledger is `VERIFY_RESULT_VERSIONS.json`, entries `{ "schema_version", "schemaSha256", "note" }`, newest last, under the same rule as the run-result ledger with `VERIFY_RESULT_SCHEMA_VERSION`. The schema reaches `VerificationEvidence` and `TypecheckEvidence` (`cli/src/core/turn.ts`) and the guard's classes and modes (`cli/src/security.ts`), so a change to any of them needs a regenerated schema and an entry here as well as for the run result. `cli/test/verify_schema.test.ts` runs the comparison, and every result document the `nexus verify` tests produce is validated against the schema. The manual (`docs/USER_MANUAL.md`, "`nexus verify`") describes the document and the exit codes.

## The audit bundle

`audit-bundle-v1.schema.json` is the JSON Schema of the two documents an audit bundle carries (`AuditBundleDocument` in `cli/src/audit_contract.ts`): `manifest.json` (`AuditManifest`) and the detached signature envelope `manifest.sig.json` (`AuditSignatureEnvelope`). `audit-verify-result-v1.schema.json` is the schema of the one document a verification of a bundle prints (`AuditVerifyOutput`: a result with `result`, or an error document without one). Both are generated by the same `SchemaBuilder` through `cli/scripts/result_schema.mjs`.

```bash
cd cli
node scripts/gen_audit_schema.mjs           # rewrite both schemas
node scripts/gen_audit_schema.mjs --check   # exit 1 when a schema or its ledger is stale
```

Their ledgers are `AUDIT_BUNDLE_VERSIONS.json` and `AUDIT_VERIFY_RESULT_VERSIONS.json`, entries `{ "schema_version", "schemaSha256", "note" }`, newest last, under the same rule as the run-result ledger with `AUDIT_BUNDLE_SCHEMA_VERSION` and `AUDIT_VERIFY_RESULT_SCHEMA_VERSION`. The bundle schema reaches `ChainLink` (`cli/src/core/hash_chain.ts`), so a change there needs a regenerated schema and an entry. `cli/test/audit_schema.test.ts` runs the comparison and pins the exit-code table (`AUDIT_EXIT_CODES`); every manifest written and every result produced in `cli/test/audit_bundle.test.ts` is validated against the schemas.

A schema describes a document's shape only. What makes a bundle verify is defined in `cli/src/core/audit_bundle.ts`: `manifest.json` is exactly the canonical JSON of the manifest (keys sorted at every depth, no whitespace) and one newline; a file's `sha256` is over its bytes; each entry of `files` is linked to the one before it with `linkRecord`; `root_sha256` is the SHA-256 of the canonical JSON of the manifest without that member. Optional `manifest.sig.json` signs the exact manifest bytes with an Ed25519 key and a domain separator. The public key is never embedded; verification is signed only when a caller supplies and matches its own trusted public key.

## The managed policy document

`policy-v1.schema.json` is the JSON Schema of a managed policy document (`ManagedPolicyFile` in `cli/src/core/managed_policy.ts`, plan unit GV-1). A policy file is TOML (`policy.toml`); the schema describes the same data as a JSON document, with each table an object, for an operator's editor or linter. It is generated by the same `SchemaBuilder` through `cli/scripts/result_schema.mjs`.

```bash
cd cli
node scripts/gen_policy_schema.mjs           # rewrite docs/protocol/policy-v1.schema.json
node scripts/gen_policy_schema.mjs --check   # exit 1 when the schema or its ledger is stale
```

Its ledger is `POLICY_VERSIONS.json`, entries `{ "schema_version", "schemaSha256", "note" }`, newest last, under the same rule as the run-result ledger with `POLICY_SCHEMA_VERSION`. The version rule is stricter than for the result documents: every added, removed or changed key bumps `POLICY_SCHEMA_VERSION`, because a reader refuses a policy whose version it does not support instead of ignoring what it does not know. `cli/test/managed_policy_schema.test.ts` runs the comparison, checks that the schema and the validator name the same tables and keys, and validates generated documents and every example of `docs/MANAGED_POLICY.md` against both.

The schema describes shape only and is looser than the validator (`validatePolicyDocument`): like every schema here it never sets `additionalProperties: false`, so it does not reject an unknown table or key, which the validator does; it does not check the form of list items (a command prefix, a host name, an `mcp.allow` entry); and a whole number is `number`. A file that passes the schema may still be refused. `docs/MANAGED_POLICY.md` describes the format, the tiers and the errors. In this change the policy is a library: `nexus` does not read a policy file yet.

## The command-hook documents

`hooks-v1.schema.json` is the JSON Schema of the command-hook contract (`HooksDocument` in `cli/src/core/hooks.ts`, plan unit HK-1). `$defs.HooksFile` is a hooks file (`~/.config/nexus/hooks.json`, `<workspace>/.nexus/hooks.json`), `$defs.HookInput` the one JSON object a hook reads on standard input, `$defs.HookOutput` what it may print on standard output, and `$defs.ExtensionTrustStore` the approval store `~/.config/nexus/extension_trust.json`. It is generated by the same `SchemaBuilder` through `cli/scripts/result_schema.mjs`.

```bash
cd cli
node scripts/gen_hooks_schema.mjs           # rewrite docs/protocol/hooks-v1.schema.json
node scripts/gen_hooks_schema.mjs --check   # exit 1 when the schema or its ledger is stale
```

Its ledger is `HOOKS_VERSIONS.json`, entries `{ "schema_version", "schemaSha256", "note" }`, newest last, under the same rule as the run-result ledger with `HOOKS_SCHEMA_VERSION`. A hooks file carries the version as `version`, and the reader refuses any other value, so a removed or renamed key, or a changed meaning, bumps it; an added optional member of the hook input keeps it. `cli/test/hooks_schema.test.ts` runs the comparison.

The schema describes shape only and is looser than the reader (`parseHooksFile`): it does not reject an unknown or duplicate key, a pattern in `tools`, a repeated hook name or a `timeout_secs` out of range, all of which the reader refuses.

## The detached runner's job record and receipt

`job-v1.schema.json` is the JSON Schema of the record the detached runner keeps for each job (`JobRecordDocument` in `cli/src/core/runner_store.ts`, plan unit BG-1: `runner/jobs/<id>/job.json` under the state directory). `runner-files-v1.schema.json` is the schema of the runner's other files (`RunnerFileDocument` in the same module), told apart by `format`: a client's request in `runner/inbox/`, the runner record `runner.json`, and a job's `worker.json`, `result.json` and `spec.json`. `job-receipt-v1.schema.json` is the schema of the receipt the runner writes when a job ends (`JobReceiptDocument` in `cli/src/core/job_receipt.ts`: `receipt.json` beside the record), and `job-status-v1.schema.json` the schema of the one document `nexus job status <id> --json` prints (`JobStatusDocument` in the same module: the record, a summary of the job's operation, and the receipt). All four are generated by the same `SchemaBuilder` through `cli/scripts/result_schema.mjs`.

```bash
cd cli
node scripts/gen_job_schema.mjs                   # rewrite docs/protocol/job-v1.schema.json and runner-files-v1.schema.json
node scripts/gen_job_receipt_schema.mjs           # rewrite docs/protocol/job-receipt-v1.schema.json and job-status-v1.schema.json
node scripts/gen_job_schema.mjs --check           # exit 1 when a schema or its ledger is stale
node scripts/gen_job_receipt_schema.mjs --check
```

Their ledgers are `JOB_VERSIONS.json`, `RUNNER_FILE_VERSIONS.json`, `JOB_RECEIPT_VERSIONS.json` and `JOB_STATUS_VERSIONS.json`, entries `{ "schema_version", "schemaSha256", "note" }`, newest last, under the same rule as the run-result ledger with `JOB_RECORD_VERSION`, `RUNNER_FILE_VERSION`, `JOB_RECEIPT_SCHEMA_VERSION` and `JOB_STATUS_SCHEMA_VERSION`. The job record and the runner's files carry their version in the member `version`; the ledgers key it as `schema_version` like every other ledger here. Their version rule is the policy document's: the readers (`parseJobRecord`, `parseRunnerRequest` and the rest) refuse any other version and any key they do not know, so every added, removed or changed member bumps the version. A receipt and a status document are reports for other tools, so an added optional member keeps their version. `cli/test/runner_store.test.ts` and `cli/test/job_receipt_schema.test.ts` run the comparisons and validate sample documents.

These schemas describe shape only. In the job record, in a start request and in the receipt `unattended` is the constant `true`: a job is a run with no operator present, and its receipt's `approval_mode` is `review` or `read-only`, never `auto`.
