## Decision taken (D22)

D22 in [`docs/v1.3.0/PLAN.md`](../../v1.3.0/PLAN.md) section 7 is taken as written: ship `:workspace`, `:read-only` and `:network`; the interactive default stays today's engine defaults until the operator names a profile; managed policy may force a stricter confinement and never a looser one.

What the code does for each part, as landed in #781 (contract), #795 and #814 (wiring and follow-ups) and #816 (posture, denials, docs):

| Part of D22 | On tip |
|---|---|
| The three names | `--sandbox [engine]:profile` accepts exactly `:workspace`, `:read-only`, `:network`; anything else is refused and nothing falls back to an unconfined run (`cli/src/sandbox_profile.ts`) |
| Interactive default unchanged | With no profile, `expandSandboxProfile` returns the options object untouched for every legacy value; the posture label is derived from the settings in force |
| Managed policy stricter only | `sandbox.required` refuses `--sandbox none` and switches a sandbox on; `sandbox.forbid_network` refuses `:network`. A managed-policy key that names a profile does **not** exist: policy forces the sandbox on and the network off, it does not select a profile by name |

2. **`TMPDIR=/var/tmp`.** `verify_sandbox` 10/11 (the real Bubblewrap box test saw the caller's checkout and wrote the test `HOME`) and `verify_hostile` 45/46 (`REGRESSION_FREE` instead of `VERIFIED`; the message says the verifier definition could not be bound because of nesting deeper than 5 levels, an unreadable directory or too many project files, and the likely cause is the deeper `/var/tmp` path, which was not isolated). `verify_sandbox` assumes a temporary directory under `/tmp` (its own comment says so). With the default `TMPDIR` the same two files passed 11/11 and 46/46. This is a property of where the tests put their scratch trees, not a profile defect, but it was not investigated further. The `/var/tmp` runs are not counted above.

## Acceptance clauses

| Clause | Evidence | Status |
|---|---|---|
| CLI and doctor show the effective profile | `sandbox_profiles` "a named profile reads the same on session.state, the REPL status line and the doctor report" and the no-profile case; `doctor` posture tests; `examples/sandbox-profiles` | Met |
| A profile cannot grant allow-always or change an approval | `sandbox_profiles` "every profile × engine expands to exactly the legacy flag bundle and touches nothing else" (`yes`, `approve`, `mode`, `fullAccess` unchanged for all profile and engine pairs; the source options are not mutated); `managed_policy_always` | Met |
| A profile cannot disable verification-path protection or bypass G-3 | Structural: `sandbox_profile.ts` is imported by `config.ts`, `doctor.ts`, `repl.ts` and `sidecar.ts` only, not by dispatch, approval, verify or the gates, and `nexus verify --sandbox` refuses profiles. Hostile profile strings are refused (`sandbox_profiles` "hostile and malformed values are refused"). The G-3 and verification suites above pass on tip | Met by structure and the suites; see "Not claimed" |
| A profile composes with managed policy and is never looser | `sandbox_profiles` "a profile is never looser than itself or than the policy" and "composition is monotone" | Met |
| Existing sandbox tests pass under profile aliases | `sandbox_confine`, `sandbox_docker`, `sandbox_cancel`, `sandbox_quoting`, `sandbox_custom_state_root`, `verify_sandbox` pass; `sandbox_profiles` asserts each alias expands to exactly the legacy flag bundle, so those tests exercise the same flags | Met by equivalence, not by re-running each file once per alias |
| Residual holes documented beside the profile | [`docs/SANDBOX_PROFILES.md`](../../SANDBOX_PROFILES.md) "Residual holes"; `PROFILE_SPECS` carries them and `nexus doctor` prints them (`sandbox_profiles` "every profile documents its residual holes") | Met |

**SB-1 acceptance is met for the RC on this tip, with the residual holes listed in [`docs/SANDBOX_PROFILES.md`](../../SANDBOX_PROFILES.md).** They include: no seccomp filter under Bubblewrap; commands run as the operator's own user; MCP servers and plugins are not sandboxed; broad host reads and a writable `.git` and ignored trees under `:workspace` and `:network`; unrestricted egress under `:network`; the whole workspace is readable under `:read-only`; and an unconfined native worker under engine `auto` with no engine available.

## Not claimed

- No claim that a sandbox profile makes a run safe against a hostile command. A profile is a mount and network namespace, not a second account.
- No test runs a verification-path edit or an approval request end to end under each of the nine profile and engine combinations. The "cannot disable" clauses rest on the import structure, the expansion test and the existing G-3 suites, not on a profile-by-profile campaign.
- No managed-policy key selects a profile by name. "Stricter, never looser" is shown for `sandbox.required` and `sandbox.forbid_network` only.
- The existing sandbox files were not re-run once per alias.
- No macOS or Windows run, Node 22 only for the two sets above and not the full suite, and no run on a host without `bwrap` or Docker beyond the cases the tests themselves cover.
- No hosted CI result for this evidence commit; the CI named above is for the tip it was measured on.
- Nothing here is external qualification, and nothing is a frontier-grade claim.
