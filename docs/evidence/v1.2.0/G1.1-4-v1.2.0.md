On rc.1 (`G1.1-4-rc.1.md`) the failures were five hybrid ("think before the call") `edit_file` prompts that ran to the output cap. This run is a different failure: 45 plain `read_file` prompts. All 200 `lead-reasoning` requests completed as requests (no failed receipts), so the 45 invalid answers were completions that were not exactly one correct native call.

A probe straight after the run (`probe-lead-reasoning-read_file-2026-11-15.txt`) shows what the model returns for the plain `read_file` prompt: no native tool call, and content that is literally `read_file(path="README.md")` (python-style function-call text), 10 of 10 times. Earlier the same day the same alias answered this prompt with a native call (rc.1 attempt 3, 06:32Z to 07:05Z: `read_file` 50/50), so the pool's serving behaviour changed in between. The gateway is outside the product's control.

## What the client does with that, and the follow-up

The client treats a reply that is "the call written as text" as a failed attempt, tells the model and asks again, then forces `tool_choice`: that path is why `deep` ends 200/200. It recognises only strictly parseable JSON text (an object with a name and arguments, or an arguments object for the single offered tool, plain or in one fence; `cli/src/core/content_tool_call.ts`), not function-call-style text, so for `lead-reasoning` the safe retry never engages and the reply is plain text. The follow-up is v1.2.1 unit WM-4 (recognise a whole-content call to an offered tool written as `name(arg="value")`, or inside a `[...]` list, as a call-as-text so the existing retry applies; recognition only, never execution). It is not claimed to fix anything until a matrix is taken on a build that contains it.

## Standing
